# 자소서 작성과 검토

자소서 작업은 **설계 → 인터뷰 → 작성 → 검토**의 네 패스로 진행한다. 이 문서는 각 패스의 순서, 입력, 산출물과 저장·버전 관리를 다룬다. 패스마다 읽는 문서가 다르다. 작성 패스에 검증 규정을 함께 넣지 않는 것이 이 구조의 핵심이다.

| 패스 | 하는 일 | 읽는 문서 | 산출물 |
| --- | --- | --- | --- |
| 1. 설계 | 문항 분해, 소재 선택, 사실 매핑 | [주장과 문맥](essay-composition.md)의 중심 주장·소재 절, [체크포인트](essay-checkpoints.md) | `작성설계.md` (pre_draft) |
| 2. 인터뷰 | 문항에 필요한 미확인 판단·의미 확인 | [인터뷰](essay-interview.md) | 공통자료에 확인된 사실 추가 |
| 3. 작성 | 본문만 쓴다 | [문장 쓰기](essay-craft.md), [예시](../assets/examples/), 워크스페이스 선호·예시 파일 | 본문 초안 |
| 4. 검토 | 독자 검토, 사실 대조와 수정, 본문 검사, 기록과 최종 검사 | [주장과 문맥](essay-composition.md), [본문 독자 검토](essay-reader-rubric.md), [체크포인트](essay-checkpoints.md), [문항별 규칙](essay-rules.md) | `작성본.md` (draft_review), 필요하면 `면접대비_메모.md` |

검토에서 문제가 나오면 이슈 목록을 들고 3번으로 돌아간다. 판단 이유나 사실이 부족하면 2번으로 돌아간다. 같은 대화에서 고칠 수 있는 문제는 사용자에게 넘기지 않고 고친다.

## 요청별 진행

| 요청 | 진행 범위 |
| --- | --- |
| 처음 작성 | 네 패스를 모두 진행하고 검토를 마친 초안을 제시한다. 기본 검토를 다음 요청으로 미루지 않는다. |
| 피드백 수정 | 기준 버전과 사용자 의도를 확인하고 아래 피드백 절차로 필요한 범위만 고친다. 새 사실·주장·소재가 생기면 설계와 근거도 갱신한다. |
| 재검토 | 검토 패스만 진행한다. 이전 설계·통과 기록으로 정당화하지 않고 현재 문항과 본문을 먼저 읽은 뒤 원본과 대조한다. 문제가 없으면 새 버전을 만들지 않는다. |

## 작성 패스를 분리하는 방법

하위 에이전트를 띄울 수 있는 환경(Claude Code의 Agent 도구, Codex의 하위 에이전트 등)에서는 작성 패스를 새 하위 에이전트에 맡긴다. 대화 이력을 상속하지 않는 새 하위 에이전트에게 다음만 전달한다. 도구가 이력 상속을 기본으로 하면 끈다(예: `fork_turns="none"`).

- 문항 원문과 글자 수 기준, 기업 형식 요구
- 문항별 `writing_brief`, `detail_selection`의 선택 결정, 그 주장을 뒷받침하는 사실 발췌·출처 위치와 필수 범위 조건을 함께 전달한다. 발췌를 뜻을 보존해 요약했다면 원문 인용과 구분한다.
- 지원동기·활용에 필요한 JD와 기업 리서치의 확인된 업무·서비스 정보 및 출처
- `references/essay-craft.md`, `assets/examples/`의 경로
- 워크스페이스에 있으면 `공통자료/사용자_작성선호.md`, `공통자료/자소서_좋은예시.md`, 해당 기업의 `03_검토기록/작성방향.md`
- 피드백 수정이라면 기준 버전 본문과 수정할 이슈

전체 사실 원본은 메인 작업이 보존하고 사실 대조에 사용한다. 작성자는 전달된 발췌로 쓰며 부족한 사실은 메인 작업에 요청한다. 원본에서 덜어낸 기술 이력을 다시 찾아 본문에 추가하지 않는다. 시험과 실제 운영, 표본과 전체, 개인과 팀 성과의 구분은 선별 과정에서도 유지한다. 체크포인트, 검사 명령, 버전 규칙은 전달하지 않는다. 하위 에이전트는 본문만 돌려주고, 저장과 사실 대조·검토 결과 처리는 메인 작업이 한다. 본문 독자 검토는 아래 검토 패스에서 별도로 수행한다.

하위 에이전트를 쓸 수 없으면 같은 맥락에서 진행하되, 작성하는 동안에는 위 자료만 기준으로 삼고 체크포인트 작성은 검토 패스로 미룬다.

## 사실 원본

자소서 문장은 공통자료의 확인된 사실과 사용자가 지정한 원본에서만 만든다.

- 프로젝트 최종 원고
- 작업 기록
- 이슈와 티켓
- 커밋과 코드 리뷰 메시지
- 테스트와 운영 로그
- 사용자가 직접 작성한 상세 사례
- 인터뷰에서 사용자가 확인한 판단 이유와 이후 변화

출처 파일을 현재 환경에서 읽을 수 없으면 존재했다는 설명만 사실로 받아들이고 세부 내용을 재구성하지 않는다.

## 1. 설계 패스

### 소재 준비

각 사례는 필요한 만큼 다음 항목을 채운다. 실제 정보가 부족하면 [경험 수집 질문](experience-questions.md)을 참고한다.

1. 상황, 목표와 맡은 책임
2. 문제를 인식한 계기, 중요하게 본 이유와 예상 영향
3. 선택한 행동과 실행 방법, 다른 선택지보다 이를 택한 이유
4. 피드백, 실패한 가설과 판단 수정이 실제로 있었다면 그 과정
5. 검증 방법, 결과와 수치, 본인 기여와 팀 기여의 구분
6. 사건에서 생긴 기준과 이를 반영한 이후의 실제 행동 또는 향후 계획

판단·의미를 설명하는 데 필요한 개인 사실이 없으면 인터뷰 패스에서 확인한다. 이후 행동 변화는 문항이 요구하거나 핵심 주장을 뒷받침할 때 묻는다. 이미 확인된 선택과 이해로 답할 수 있으면 새로운 변화 사례를 요구하지 않는다. 감정, 동기와 판단 이유는 코드, 로그와 결과만 보고 추정하지 않는다. 갈등이나 실패를 모든 사례에 억지로 만들지 않는다.

소재를 모으는 단계에서는 글자 수에 맞춰 사례를 삭제하지 않는다. 상세 사례를 충분히 보존한 뒤 기업별 문항에서 선택한다.

### 작성 설계

스킬 내부의 [작성설계 양식](../assets/templates/자소서_작성설계.md)과 [작성본 양식](../assets/templates/자소서_작성본.md)을 참고한다. 빈 양식을 취업 폴더에 먼저 복사하지 않는다.

직무의 업무·모집 범위, 문항 원문·출처·형식·글자 수 기준과 기존 채택본을 확인하고 필수 하위 질문을 분해한다. 문항이 공개되지 않았으면 임의로 만들지 않는다. 문항 수집은 [공고와 연결 서비스](posting-and-connectors.md)의 범위를 따른다. 전체 문항 요청을 지원서 전체 입력 항목으로 확대하지 않는다.

[주장과 문맥](essay-composition.md)에 따라 중심 주장을 정하고 소재의 사실성과 적합성을 판단한다. `writing_brief`에 문항에 필요한 문제·판단·행동·결과의 관계를 먼저 정한다. 그 관계에 필요한 사실과 필수 범위 조건을 선택하고 `evidence_map`의 각 주장을 실제 뒷받침하는 출처 위치에 연결한다. 하위 질문마다 모든 출처를 일괄 연결하지 않는다. 수치·조건의 의미가 앞의 표나 정의에 의존하면 그 위치도 근거에 포함한다. `detail_selection`에는 이번 문항에서 무엇을 유지·설명·제외하기로 했는지와 이유를 기록한다. 설계의 문항별 선택을 그대로 작성 입력으로 사용하며 별도의 대량 소재 모음을 다시 만들지 않는다.

전달 전에 선택한 주장과 발췌를 함께 읽어, 제외한 구현 이력이 섞이지 않았고 각 근거의 대상·역할·결과 범위가 유지되는지 아래 사실 대조 방식으로 확인한다. 제목 사이를 크게 자르는 작업은 자료 탐색이며 정보 선택을 대신하지 않는다. 코드로 저장·변환할 때도 선택 결정과 주장별 근거 연결을 보존한다. pre_draft 검사는 기록 형식을 확인하므로 이 판단의 완료 증거로 사용하지 않는다.

사실 대조는 작성한 요약을 정답으로 두지 않고 원본에서 누가 무엇을 어떤 조건에서 했고 어떤 결과를 관측했는지 먼저 읽은 뒤 비교한다. 특히 숫자를 새 명사에 붙이거나 생략된 단위를 풀어 쓴 부분은 표의 제목·행·열·셀 및 인접 정의로 대상과 집계 단위를 확인한다. 원본이 뒷받침하지 않는 단위는 구체화하지 않는다. 원본 안에서도 경험 사실, 사용자가 확인한 해석, 작성 안내를 구분한다. 작성 안내를 당시 판단이나 사후 배움으로 바꾸지 않는다. 발췌를 전달할 때도 이 구분을 유지한다. 출처 존재나 문구 일치가 의미 일치를 대신하지 않으며, 발견한 차이는 기존 evidence_map과 검토 기록에 반영한다. 이 대조는 전달 자료와 기존·수정 본문에 동일하게 적용하고 별도 필드나 전수 대조표를 만들지 않는다.

글자 수와 형식이 기본값과 다르면 `01_공고_JD/자소서_규칙.json`에 문항별로 기록한다. 분량 상하한도 같은 파일의 `min`, `max`에 둔다. 자세한 형식은 [문항별 규칙](essay-rules.md)을 따른다.

근거가 부족하면 지정 원본 재확인 → 다른 적합한 소재 검토 → 필요한 개인 사실 질문 순서로 처리한다. 질문은 인터뷰 패스와 묶어서 최대 3개씩 한다.

새 설계는 버전 2 pre_draft로 전체 문항을 등록하고 다음 검사를 통과시킨다.

```bash
python scripts/essay_check.py --plan "작성설계.md" --rules "01_공고_JD/자소서_규칙.json"
```

규칙 파일이 없으면 `--rules`를 생략하고 `--limit "1:0:1000"`처럼 문항ID:최소:최대를 직접 넘길 수 있다.

일부 문항에만 사용자 사실이 필요하면 해당 문항은 deferred로 두고 본문을 만들지 않는다. 나머지는 부분초안으로 보존한다. 모두 보류면 확인 질문만 남긴다. 상태와 JSON 형식은 [체크포인트](essay-checkpoints.md)를 따른다.

## 2. 인터뷰 패스

[인터뷰](essay-interview.md)를 따른다. 설계에서 나온 사실 질문과 판단·의미 질문을 한 번에 묶는다. 답이 오면 공통자료에 반영하고 해당 문항의 `writing_brief`와 필요한 action·근거 매핑을 갱신한 뒤 설계 검사를 다시 실행한다. 이미 확인된 정보가 충분하거나 사용자가 질문 없이 진행하길 원하면 건너뛴다.

## 3. 작성 패스

[문장 쓰기](essay-craft.md)를 따른다. 위의 "작성 패스를 분리하는 방법"대로 입력을 제한한다. 작성자는 문항 ID가 붙은 `text` 블록으로 본문만 돌려준다.

````markdown
```text question=1
[핵심 요약]
본문
```
````

## 4. 검토 패스

### 독자에게 전달할 입력

하위 에이전트를 사용할 수 있으면 작성자와 다른 새 에이전트에 [본문 독자 검토](essay-reader-rubric.md)를 맡긴다. 대화 이력을 상속하지 않는다(예: `fork_turns="none"`). 접근 도구가 같아도 아래 파일만 읽도록 범위를 제한한다.

- 문항 원문, 해당 답변 본문, 분량과 필수 형식 조건을 추출한 임시 입력
- `essay-reader-rubric.md`

전체 작성본 경로 대신 본문만 추출한 사본을 전달한다. 설계·원본·체크포인트·사용자 피드백·이전 판정·결함 예시·기대 답은 제외한다. 독자는 사실 원본 검색, 본문 수정, 통과 플래그 작성을 하지 않는다. 메인 작업이 독자에게 특정 문제를 찾으라고 암시하지 않는다.

하위 에이전트를 사용할 수 없으면 같은 입력 사본으로 재독하고 기록에 `같은 맥락의 재독`이라고 밝힌다. 배경을 이미 아는 검토를 독립 검토라고 보고하지 않는다.

### 결과 처리 순서

1. **독자 결과 확보**: 원문 순서에서 발견한 연결·정보 배치의 문제와 전체 문항 충족 판정을 받는다. 독자의 요약이 매끄럽다는 이유로 본문도 그렇다고 판단하지 않는다. 처음 결과를 보존한 뒤 수정한다.
2. **사실 대조와 수정**: 독자 지적을 실제 구절과 대조하고, 검토 대상 본문에 있는 행동·결과·판단·배움을 설계 절의 원본 우선 대조 방식으로 확인한다. 이전 초안이나 설계에 있다는 이유로 근거를 인정하지 않는다. 사용자 선호도 대조하며, 수정 요청에는 아래 피드백 절차로 근거 부족과 수정 범위를 처리한다. 이슈의 채택·비채택 이유를 남긴다. 검토만 요청받았다면 본문을 수정하지 않는다.
3. **재독과 전후 비교**: 독자는 고친 답변 전체를 같은 입력 범위와 기준으로 다시 읽고, 메인은 이전 본문과 비교해 해결한 문제와 새 문제, 문항에 필요한 행동·기여·근거의 손실을 판단한다. 독립 독자의 지적이 없었다는 이유만으로 개선을 확정하지 않는다. 새 맥락의 검토를 했는지 기록하며, 필수 기준이 충족되고 선택 사항만 남으면 종료한다. 새 근거 없이 같은 지적이 반복되면 아래 피드백 절차에 따라 설계로 돌아가거나 남은 판단을 보고한다.
4. **본문 사전 검사**: 아래 `--body-only`로 체크포인트 없이 형식·분량·표현 후보를 확인한다. 검사 때문에 의미가 바뀌면 해당 답변을 다시 검토한다.
5. **결과 기록**: 독자 결과와 사실 대조, 실제 사전 검사 뒤 draft_review, style_review, revision을 작성한다. 독자에게 전달한 입력 범위·이력 상속 여부·수행 주체는 기존 검토 기록에 짧게 남긴다. 결과를 긍정적인 설명으로 바꾸거나 남은 이슈를 누락하지 않는다. 실행하지 않은 검토는 true로 두지 않는다.
6. **최종 통합검사**: 체크포인트를 포함한 작성본을 `essay_check.py`로 검사한다. 이는 형식과 기록의 검사이며 내용 품질을 증명하지 않는다. 통과한 초안을 제시하되 자동 채택하지 않는다.

### 형식·분량 검사

검토 기록 전에는 설계와 본문만으로 실행한다.

```bash
python scripts/essay_check.py --plan "작성설계.md" --draft "작성본.md" --rules "01_공고_JD/자소서_규칙.json" --body-only
```

이 결과의 `check_scope: body_only`와 `valid`는 본문 형식·분량에만 해당한다. 내용·사실 검토나 최종 체크포인트의 완료 판정이 아니다. `style_blocks`의 표현 후보도 실제 문맥에서 검토한다. 체크포인트가 아직 없거나 검사 플래그가 false여도 이 단계는 실행할 수 있다.

결과를 기록한 다음 같은 파일·규칙으로 최종 검사를 실행한다.

```bash
python scripts/essay_check.py --plan "작성설계.md" --draft "작성본.md" --rules "01_공고_JD/자소서_규칙.json"
```

규칙 파일이 없으면 `--rules`를 생략하고 `--limit "1:0:1000"`처럼 실제 분량을 전달한다. 두 검사에 같은 규칙과 제한을 사용한다. `essay_check.py`는 최종 단계에서 설계와 작성본의 체크포인트, 작성·보류 결정, 문항 ID, 근거 인용, `memorable_line`, 형식과 분량을 검사한다. 검토 플래그가 false이면 분량 결과를 반환하더라도 최종 통과시키지 않는다. 상태 파일을 쓰지 않으므로 서로 다른 지원 건의 검사는 독립적이다.

기록 후 표현만 다시 확인하려면 `validate_essay_style.py --strict --rules "규칙.json" "작성본.md"`도 사용할 수 있다. 분량의 최종 판정은 `essay_check.py` 결과를 따른다.

`validate_essay_style.py`는 아래 표현 후보를 JSON으로 돌려준다. 후보별로 유지·수정을 판단하고 결과를 짧게 기록한다.

| 검사 후보 | 확인할 사항 |
| --- | --- |
| 가운데점 | 공식 고유명사·인용은 보존하고 장식적인 나열은 문장으로 바꾼다. |
| 곡선 작은따옴표 `‘ ’` | 일반 작은따옴표 `'`로 바꾼다. |
| 영어·구현 용어 | 판단을 설명하는 데 필요한지 보고, 바뀐 문맥에서 주체·대상이 이해되는지 확인한다. |
| 연결어미 뒤 쉼표 | 의미 구분과 호흡에 필요한 것만 남긴다. 일괄 삭제하지 않는다. |
| 대괄호 요약 | 문항에서 허용되는 형식·개수를 지키고 본문 밖 성과를 만들지 않는다. |
| 목록 행 | 기업이 요구한 목록은 유지하고 일반 본문의 개조식은 서술식으로 바꾼다. |
| 상투 표현 `stock_phrases` | "이 경험을 통해 ~ 배웠습니다", "~가 되겠습니다", "성장하겠습니다", "맞닿아", "단정하지 않고" 등. 사건에 묶인 표현이나 구체적인 행동으로 바꿀 수 있는지 본다. [피할 문체](../assets/examples/피할-문체.md)를 참고한다. |
| 같은 종결 연속 `repeated_ending_run` | "~했습니다."가 네 문장 이상 이어진다. 판단·이유·전환 문장을 섞거나 문장을 합친다. |

스크립트를 실행할 수 없는 환경에서는 같은 항목을 수동으로 대조하고, 자동 검사는 미실행으로 보고한다. 실행하지 않은 검사 값을 true로 바꾸지 않는다.

## 피드백을 반영하는 수정

1. 기준 버전, 사용자 의도, 유지할 소재·주장·표현을 확인한다. 피드백을 사실·역할 정정, 주장·소재 변경, 설명 누락, 표현 선택으로 구분한다. 명확한 단어 교체는 그 범위만 처리한다. 강조 요청을 소재 교체로 확대하지 않는다.
2. 수정 대상 본문에서 검증할 주장을 잡고 원본을 먼저 이해한 뒤 대조한다. 명확한 표현 교체는 바뀐 의미와 연결 범위만, 전체 개선 요청은 유지할 기존 문장까지 확인한다. 작성 안내를 개인 경험으로 옮겼거나 근거가 빠진 주장은 기존 evidence_map에서 바로잡는다. 원본에 있는 설명이 본문에만 빠졌다면 보완하며, 문항을 증명하는 행동을 설명이 부족하다는 이유만으로 삭제하지 않는다.
3. 근거 자체가 부족하면 원본 재확인과 다른 소재 검토 후 필요한 개인 사실만 묻는다. 이미 확인을 거쳤는데도 근거가 늘지 않으면 같은 질문이나 윤문을 반복하지 않고 설계로 돌아간다. 문항의 요구와 사용자 지정 방향을 지키면서 입증 가능한 수준으로 주장을 좁히거나 사례 비중을 줄이고 다른 확인된 소재와 비교한다. 그래도 필수 답을 뒷받침하지 못하면 보류한다. 선택적 보완만 남으면 한계를 밝히고 제시한다.
4. 고친 뒤 바뀐 답변 전체를 검토 패스로 다시 읽고 메인이 수정 전후를 비교한다. 같은 문제의 재발, 다른 문항과 결론의 중복, 필요한 행동·본인 기여·사실 범위의 손실을 확인한다. 기존 수정 기록에 문제 구절, 실제 변경과 효과, 필요한 근거의 유지 여부를 남겨 해결·부분 해결·사실 확인 대기로 표시한다. 분량이나 이슈 수의 증감 자체를 개선 근거로 삼지 않는다. 사용자가 채택한 표현과 제외 방향은 유지한다.
5. 이전 통과 판정을 바꾸면 새 사실·이전 검토 누락·해석 변경 중 이유와 현재 본문 근거를 기록한다. 새 버전으로 저장하고 중요한 변경, 남은 문제, 사용자 선택을 짧게 보고한다. 필수 기준을 충족하고 선택 사항만 남으면 검토를 마친다.

## 초안 저장

검토를 통과한 본문은 별도 작성본에 문항 ID를 붙인 `text` 블록으로 저장한다. 작성 설계와 답변을 같은 파일에 만들지 않는다. 검사를 통과한 결과만 번호가 붙은 초안 또는 부분초안으로 보존한다. 검사 결과가 좋다는 이유로 자동 채택하지 않는다.

## 버전과 리뷰

초안과 주요 수정본은 `02_작성중`에서 `application_workspace.py next-draft`로 새 번호를 받는다.

### 사용자 수정 이력과 채택 문안

- 현재 문항과 관련된 사용자 피드백, 직접 고친 문장과 채택 버전을 초안 전에 먼저 읽는다. 새로 확인된 소재·강조점·제외 방향은 해당 기업의 `03_검토기록/작성방향.md`에 이유와 적용 문항을 짧게 남긴다.
- 사용자가 명시적으로 채택한 문안은 `application_state.py select --kind essay`로 기록해 다음 수정의 기준점으로 삼는다.
- 사용자가 채택하거나 직접 고친 답변 중 문장이 좋았던 것은 사용자에게 확인한 뒤 `공통자료/자소서_좋은예시.md`에 추가한다. 이 파일은 다른 지원서에서 **문체와 구조의 참고**로만 쓰고, 소재·강조점·글자 수 전략은 자동으로 옮기지 않는다.
- 버전 차이에서 추측한 취향은 사용자가 확인하기 전까지 영구 규칙으로 만들지 않는다. 여러 공고에 적용하기로 한 선호는 `공통자료/사용자_작성선호.md`에 남긴다.
- 채택 문안이라도 사실 오류, 역할 과장, 필수 요구 누락, 제출 조건 위반은 근거와 함께 설명하고 필요한 범위만 고친다.
- 새 버전마다 이전 버전, 수정 목적, 관련 이슈 번호, 판단·정보·구조의 실제 변화, 해결 및 미해결 이슈, 글자 수 영향을 기록한다.

각 고유 이슈에 `R1`, `R2`처럼 번호를 붙인다. 같은 문장이 여러 영역에 영향을 줘도 한 이슈로 집계한다. 상단 요약의 이슈 수는 고유 번호 수와 일치해야 한다.

새 버전을 저장하기 전 `revision` 체크포인트에 전체 이슈 검토 여부와 남은 치명 이슈를 기록한다. `all_identified_issues_reviewed`가 참이 아니거나 `remaining_fatal_issues`가 비어 있지 않으면 검사를 통과할 수 없다.

## 글자 수

문항의 최소·최대 분량과 계산 기준을 지킨다. 상한은 목표가 아니다. 남은 분량이 많다는 이유로 사례·기술·시험 이력을 추가하지 않는다. 대괄호 요약과 실제 입력할 소제목도 포함해 계산한다.

단독 계산이 필요하면 다음을 사용한다.

```bash
python scripts/count_essay_characters.py "작성본.md"
```

공백 포함 여부와 제목 포함 여부가 불명확하면 실제 지원 폼을 확인하고 미확인 상태를 기록한다.

## humanize-korean

내용, 사실과 문항 검토가 끝난 뒤에만 선택적으로 사용한다.

권장 입력:

- 장르: 공적
- 강도: 보수
- 최소심각도: S1

처리 순서:

1. 최신 작성본을 보존한다.
2. macOS와 Linux에서는 `mktemp -d`, Windows에서는 안전한 임시 디렉터리 기능으로 시스템 임시 폴더를 만든다.
3. 원문은 전체 경로로 참조하고 임시 폴더를 작업 위치로 삼아 `humanize-korean`을 실행한다.
4. 생성된 `_workspace`의 결과를 임시 후보로만 다루고 바로 제출 폴더로 옮기지 않는다.
5. 원문과 수치, 날짜, 고유명사, 기술 용어, 역할, 인과관계와 결론을 대조한다.
6. 글자 수를 다시 계산한다.
7. 모든 변경을 전체 diff 또는 빠짐없는 변경 목록으로 사용자에게 보여준다. 일부 예시만 보여주고 전체 후보를 폐기하지 않는다.
8. 사용자가 채택할 때까지 임시 후보를 유지한다. 다음 대화에서 임시 후보를 읽을 수 없으면 같은 조건으로 다시 실행하고 동일한 변경인지 검증한다.
9. 사용자가 채택하면 `next-draft`로 번호를 다시 확인하고 다음 작성본으로 `02_작성중`에 저장한다.
10. 검토 내역을 보존할 필요가 있으면 해당 기업의 `03_검토기록`을 그때 만들고 출처 초안, 검토 종류와 날짜를 알 수 있는 이름으로 저장한다.
11. 채택본 저장과 검증이 끝나거나 사용자가 후보를 거절한 뒤 임시 폴더와 그 안의 `_workspace`를 정리한다.

워크스페이스나 시즌 폴더를 `humanize-korean`의 작업 위치로 사용하지 않는다. 이미 그 위치에 `_workspace`가 생겼다면 결과의 출처와 채택 여부를 확인한 뒤 보존할 결과만 기업별 `03_검토기록`으로 옮기고 남은 임시 파일을 정리한다. 번호가 붙은 작성본에 채택 내용이 모두 남아 있다면 같은 전문을 중복 저장하지 않고 검토 요약만 보존해도 된다.

의미가 바뀌거나 변경 범위가 과하면 해당 변경을 롤백한다. `humanize-korean`이 없으면 연결어미 뒤 쉼표, 종결어미 반복, 번역투, 접속사 남발과 상투 표현만 보수적으로 점검한다.

도구의 등급을 높이는 것 자체를 목표로 추가 윤문 도구나 넓은 수정 모드를 제안하지 않는다. 내용과 사실 검토가 끝났고 남은 변경이 취향에 가까우면 현재 후보를 사용자 선택에 맡긴다.
