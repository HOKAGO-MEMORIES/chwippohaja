# 자소서 작성과 검토

자소서 소재를 모으거나 문항을 분석하고 초안을 만들 때 읽는다.

## 사실 원본

자소서 문장은 공통자료의 확인된 사실과 사용자가 지정한 원본에서만 만든다.

- 프로젝트 최종 원고
- 작업 기록
- 이슈와 티켓
- 커밋과 코드 리뷰 메시지
- 테스트와 운영 로그
- 사용자가 직접 작성한 상세 사례

출처 파일을 현재 환경에서 읽을 수 없으면 존재했다는 설명만 사실로 받아들이고 세부 내용을 재구성하지 않는다.

## 소재 준비

각 사례는 필요한 만큼 다음 항목을 채운다.

1. 상황과 목표
2. 문제와 제약
3. 본인의 판단
4. 선택한 해결 방법
5. 담당 역할
6. 협업 또는 의견 조율
7. 실패한 가설과 수정
8. 검증 방법
9. 결과와 수치
10. 배운 점

소재를 모으는 단계에서는 글자 수에 맞춰 사례를 삭제하지 않는다. 상세 사례를 충분히 보존한 뒤 기업별 문항에서 선택한다.

## 문항 분석

문항 원문과 글자 수 기준을 그대로 기록한다. 복합 문항은 하위 질문으로 분해한다.

각 하위 질문에 대해 다음을 정한다.

- 요구하는 역량
- 사용할 사실과 사례
- 본인의 행동
- 결과
- JD와 연결할 지점
- 답하지 못한 부분

각 하위 질문에는 이를 뒷받침하는 구체적인 사실이나 사용자 확인을 함께 연결한다. 기술명, 업종 또는 JD의 키워드가 같다는 이유만으로 적합한 소재로 판정하지 않는다.

초안을 쓰기 전에 문항별 작성 설계를 남긴다.

```text
문항 유형:
하위 질문:
핵심 메시지:
주 소재:
보조 소재:
본인의 행동:
결과와 검증:
JD 연결:
문체:
대괄호 핵심 요약 허용 여부:
핵심 요약 문구:
추가 소제목 허용 여부:
글자 수 기준:
하위 질문별 근거:
소재 적합도:
부족한 정보:
초안 상태:
```

사용자가 정한 소재와 강조 순서가 있으면 우선한다. 필요한 사실이 부족하면 확인 가능한 자료를 먼저 찾고 그래도 초안을 완성할 수 없을 때만 최대 3개의 구체적인 질문을 순서대로 묻는다.

문항이 공개되지 않았으면 임의로 만들어 초안을 쓰지 않는다.

자소서 문항만 확인하는 요청에서는 [공고와 연결 서비스](posting-and-connectors.md)의 범위별 출처 선택을 따른다. `전체 문항`이라는 표현만으로 공식 지원 페이지의 전체 입력 항목을 수집하지 않는다.

## 문항과 소재의 적합성 게이트

초안을 쓰기 전에 문항의 각 필수 하위 질문과 소재의 사실을 일대일로 대조한다.

- `직접 적합`: 소재의 실제 행동, 판단과 결과가 문항에서 묻는 경험이나 역량을 직접 증명한다.
- `조건부 적합`: 핵심 일부는 증명하지만 확인된 보조 사실이나 다른 짧은 근거가 있어야 문항 전체에 답할 수 있다.
- `부적합`: 기술, 업종 또는 키워드만 비슷하거나, 문항에 맞추려면 확인되지 않은 동기, 갈등, 역할, 감정이나 결론을 만들어야 한다.

다음 연결은 적합성의 근거로 인정하지 않는다.

- 같은 기술을 사용했다는 사실만으로 협업, 도전, 고객 관점 같은 다른 역량을 증명하는 연결
- 팀 성과만 있고 본인의 선택과 행동이 확인되지 않은 사례
- JD의 단어를 반복한 뒤 `기여할 수 있다`고 끝내는 연결
- 문항이 요구한 실패, 조율, 판단 이유나 배운 점을 빼고 구현과 성과만 나열하는 답변

필수 하위 질문 중 하나라도 `부적합`이거나 근거가 없으면 완성된 초안을 만들었다고 보고하지 않는다. 더 적합한 소재를 먼저 제안하고, 확인 가능한 자료를 찾은 뒤에도 부족하면 최대 3개의 구체적인 질문을 묻는다. 사용자가 답을 보류하면 확인된 부분만 `부분 초안`으로 작성하고 누락된 하위 질문을 문서와 보고에 명시한다.

문항별 검토 기록에는 최소한 다음 항목을 남긴다.

```text
하위 질문:
선정 소재:
직접 근거:
적합도: 직접 적합 | 조건부 적합 | 부적합
부족한 정보:
초안 상태: 작성 설계 | 부분 초안 | 유효 초안 | 수정본 | 최종 후보
```

상태는 다음 의미로만 사용한다.

- `작성 설계`: 문항 분해와 소재 배치까지만 끝난 상태
- `부분 초안`: 읽을 수 있는 문장은 있으나 필수 하위 질문, 근거 또는 결론이 남은 상태
- `유효 초안`: 모든 필수 하위 질문에 답했고 소재 적합성, 사실, 역할, 글자 수와 기본 구조를 검토한 상태
- `수정본`: 유효 초안을 바탕으로 피드백을 반영한 상태
- `최종 후보`: 사실과 문항 검토, 표현 검토와 제출 형식 검증까지 끝난 상태

`파일 생성 완료`와 `내용상 유효 초안`을 구분한다. 문서가 존재하거나 목표 글자 수에 도달했더라도 다음 최소 기준을 모두 충족하지 못하면 `유효 초안` 또는 `완료`라고 보고하지 않는다.

- 문항 원문과 글자 수 조건을 확인했다.
- 모든 필수 하위 질문에 답했다.
- 주 소재가 직접 적합하거나 확인된 보조 근거로 조건부 적합을 해소했다.
- 사실, 수치, 기간과 본인 역할에 확인 가능한 근거가 있다.
- 답변 본문에 `TBD`, 빈 자리 또는 임시 문구가 없다.
- 실제 계산 기준으로 글자 수 제한을 지켰다.
- 경험을 묻는 문항은 결과 뒤에 그 경험으로 달라진 판단, 배운 점 또는 느낀 점이 있다.
- 필수 구조와 표현 검토를 마쳤다.

## 소재 배분

- 문항의 하위 질문과 증명해야 할 역량을 기준으로 소재를 고른다.
- 같은 프로젝트를 여러 문항에서 사용할 수 있지만 같은 문제, 행동과 결과를 반복하지 않는다.
- 프로젝트 이름이 같다는 이유만으로 중복이라고 판단하지 않는다. 서로 다른 에피소드와 판단을 증명하는지 확인한다.
- 한 프로젝트에서 모든 역량을 억지로 뽑지 않는다.
- 긴 문항에서 사례를 두 개 사용할 때는 서로 다른 역량을 보완하거나 복합 문항의 각 질문에 답하도록 배치한다.
- 소재를 추가해도 새로운 정보가 생기지 않으면 사례 수를 늘리지 않는다.

## 기본 구조

문항에 별도 형식이 없으면 다음 흐름을 기본값으로 사용한다. 모든 단계를 기계적으로 한 문단씩 만들지 말고 문항과 분량에 맞춰 합치거나 생략한다.

```text
[핵심 요약 문구]
→ 핵심 답변
→ 상황과 해결할 문제
→ 원인과 제약에 대한 판단
→ 본인이 선택하고 실행한 행동
→ 검증과 결과
→ 배운 점, 느낀 점 또는 달라진 판단 기준
→ 직무 또는 질문과의 연결
```

기술 이름을 먼저 나열하지 않는다. 왜 그 기술이나 구조가 필요했고 어떤 기준으로 선택했으며 실제로 어떻게 검증했는지를 설명한다.

## 개조식과 서술식

작성 설계, 소재 정리와 검토 기록은 항목을 빠르게 대조할 수 있도록 개조식으로 작성할 수 있다. 실제 지원서에 붙여 넣는 답변 본문은 기업이 개조식이나 목록 형식을 요구하지 않는 한 서술식으로 작성한다.

- 답변 본문은 완결된 문장과 자연스럽게 이어지는 문단으로 구성한다.
- `-`, `*`, `1.`로 시작하는 목록이나 `기술 / 역할 / 성과`처럼 슬래시로 이어진 목록을 본문 구조로 사용하지 않는다.
- 소제목을 허용하는 화면에서도 소제목 아래 내용은 서술식으로 쓴다.
- 수치와 기술은 주장을 증명하는 데 필요한 만큼만 문장 안에 넣고 목록 자체가 답변을 대신하지 않게 한다.

경험을 묻는 문항은 기본적으로 `상황과 목표 → 문제와 제약 → 판단과 행동 → 결과 → 배운 점 또는 변화`가 이어져야 한다. 마지막은 기술과 성과를 다시 자랑하는 문장이 아니라 다음 중 하나를 구체적으로 밝힌다.

- 그 경험에서 실제로 느낀 점
- 새로 배운 원칙
- 이전과 달라진 판단 기준
- 이후 프로젝트에서 바꾼 행동

`협업이 중요하다는 것을 배웠습니다`처럼 어느 사례에도 붙일 수 있는 문장은 충분한 마무리가 아니다. 앞선 사건의 어떤 판단이나 결과 때문에 무엇이 달라졌는지 드러나야 한다. JD 연결이나 입사 후 포부는 배운 점을 대신할 수 없으며, 문항에 필요하면 그 뒤에 짧게 덧붙인다. 확인된 자료에 해당 변화가 없으면 임의로 만들지 말고 사용자에게 확인하거나 `부분 초안`으로 남긴다.

### 대괄호 핵심 요약

지원 화면에서 대괄호와 줄바꿈을 허용하면 각 문항 답변의 첫 줄에 `[핵심 요약 문구]` 하나를 둔다.

- 본문보다 먼저 배치하고 한 줄로 작성한다.
- 문장 대신 명사형 구절로 작성한다. `했습니다`, `합니다`, `입니다`, `됩니다` 같은 서술형 종결과 마침표를 사용하지 않는다.
- 문항의 핵심 행동, 판단이나 결과를 압축한다.
- `도전과 성장`, `함께 만든 성과`처럼 어느 지원자에게나 적용되는 표현은 피한다.
- 본문에 없는 성과나 수치를 요약 문구에서 새로 만들지 않는다.
- 한 답변에 사례가 여러 개여도 최상단 요약은 하나가 기본이다. 사례별 추가 소제목은 구조상 꼭 필요하고 지원 화면이 허용할 때만 사용한다.
- 대괄호 문구도 지원 화면의 글자 수에 포함되는 것으로 보고 계산한다.
- 지원 화면이 특수문자나 소제목을 금지하거나 사용자가 다른 형식을 지정하면 해당 요구를 우선한다.

예시 형식:

```text
[실패 원인을 분리해 배포 안정성을 높인 경험]
본문 첫 문장부터 문항의 핵심 답변을 이어서 작성합니다.
```

좋은 예시:

- `[실패 원인을 분리한 15명 통합 검증]`
- `[반례를 받아들여 기준을 고친 경험]`

피해야 할 예시:

- `[운영 가능한 시스템을 만들었습니다]`
- `[반례를 받아들여 기준을 고쳤습니다.]`

## 문항 유형별 구조

### 지원동기

지원동기는 사용 가능한 근거에 따라 다음 중 하나를 고른다. 회사 칭찬이나 장기근속 의지를 의무적으로 넣지 않는다.

**경험과 전환 계기 중심**

```text
이전 경험
→ 관심이 커진 계기
→ 직접 수행한 행동
→ 역량과 생각의 변화
→ 직무 선택 이유
→ 성장 방향
```

**산업과 직무 적합 중심**

```text
직무에 대한 관심
→ 관련 프로젝트와 역할
→ 문제와 원인 분석
→ 본인의 행동과 선택
→ 결과와 형성된 역량
→ 직무에서의 활용
```

**기업 방향성 연결 중심**

```text
기업의 실제 사업, 서비스 또는 기술
→ 연결되는 본인의 경험
→ 직접 수행한 행동과 결과
→ 기업과 경험의 연결 근거
→ 지원 이유와 기여 방향
```

기업 방향성은 공식 자료와 공고에서 확인된 내용만 사용한다.

### 직무 전문성과 프로젝트

```text
보유 역량에 대한 핵심 답변
→ 프로젝트의 문제와 제약
→ 원인 분석과 선택 기준
→ 본인의 구현과 검증
→ 결과
→ JD 업무에서의 활용
```

### 협업과 의견 조율

```text
공동 목표와 의견 차이
→ 충돌의 원인과 제약
→ 본인이 제시한 기준 또는 조율 행동
→ 합의와 실행
→ 결과와 이후의 변화
```

갈등이 있었다는 사실보다 합의를 만들기 위해 본인이 무엇을 확인하고 바꿨는지를 중심으로 쓴다.

### 문제 해결

```text
문제와 영향
→ 원인 가설
→ 검증 과정
→ 실패한 시도와 판단 수정
→ 최종 해결
→ 재현 가능한 결과 또는 배운 점
```

### AI 활용

단순 질의응답을 AI 활용 경험으로 포장하지 않는다.

```text
에이전트에 부여한 목표
→ 제공한 코드, 로그와 데이터
→ 작업 범위와 권한 제한
→ 에이전트가 만든 결과
→ 사람이 실제 환경에서 검증한 방법
→ 틀린 가설과 실패 결과
→ 수정한 판단
→ 최종 성과
```

## 문체

- 지원 화면이나 사용자가 다른 형식을 요구하지 않으면 정중한 문어체와 `습니다체`를 기본으로 한다.
- 첫 문장이나 첫 문단에서 문항에 대한 핵심 답변을 제시한다.
- 한 문장에는 하나의 중심 내용을 두고 지나치게 긴 문장은 나눈다.
- 추상적인 역량 표현 뒤에는 이를 증명하는 실제 행동을 둔다.
- 팀의 결과와 본인의 행동을 구분한다.
- `저는`은 불필요하게 반복하지 않되 자연스러운 문장까지 금지하지 않는다.
- `을 통해`, `경험을 바탕으로`와 같은 연결 표현을 반복하지 않는다.
- 과도한 미사여구, 회사 칭찬과 상투적인 포부로 분량을 채우지 않는다.
- 공식 고유명사와 표준 기술 용어는 보존한다.
- 가운데점은 문체 장식으로 사용하지 않는다. 공식 고유명사에 포함된 경우에만 원문을 보존한다.
- 의미를 정확히 유지할 수 있으면 영어 약어, 내부 저장소명과 구현 용어보다 쉬운 한국어를 우선한다.
- 번역하면 의미가 달라지는 공식 기술명과 표준 용어는 유지하되, 채용 담당자가 바로 이해하기 어려운 지표와 약어는 첫 등장에 짧은 한국어 설명을 붙인다.
- 세부 규격이 역량 증명에 필요하지 않으면 상위 개념으로 줄인다. 예를 들어 코덱 조합은 `MP4 영상`, `OOM`은 `메모리 부족으로 인한 종료`, `Read Model`은 `조회 모델`로 표현할 수 있다.
- 기술 용어를 한국어로 바꿀 때 사실의 범위가 넓어지거나 의미가 달라지면 원어를 유지하고 설명을 덧붙인다.
- 최상단 대괄호 핵심 요약은 기본 스타일로 사용한다. 그 밖의 소제목은 핵심 내용을 빠르게 이해시키는 데 필요할 때만 추가한다.

## 필수 표현 검증

초안과 모든 주요 수정본은 내용 검토 뒤 다음 검사를 수행한다. `humanize-korean` 사용 여부와 관계없이 생략하지 않는다.

```bash
python scripts/validate_essay_style.py 회사/02_작성중/자소서.md
```

검사 결과는 후보를 찾는 도구이며 자동 합격 판정이 아니다. 다음 항목을 답변 본문별로 빠짐없이 판정한다.

1. 모든 가운데점
   - 공식 고유명사 또는 문항 원문 인용이면 유지한다.
   - 기술, 역할, 조치와 성과를 나열하는 가운데점이면 쉼표, 조사 또는 문장 분리로 바꾼다.
2. 모든 영어 표현 후보
   - 회사명, 제품명과 표준 기술명처럼 그대로 써야 하는지 확인한다.
   - 내부 저장소명, 코드 변수, 생소한 지표, 약어와 구현 세부사항이면 쉬운 한국어로 바꾸거나 첫 등장에 설명한다.
   - 기술명 수가 많으면 각 이름의 필요성을 다시 확인하고 문제, 판단, 행동과 검증을 중심으로 줄인다.
3. 연결어미 뒤 쉼표 후보
   - 문장 호흡상 꼭 필요하지 않은 `하고,`, `했으며,`, `하지만,` 형태의 쉼표를 제거한다.
   - 쉼표를 일괄 삭제하지 않고 의미 구분에 필요한 경우는 유지한다.
4. 대괄호 핵심 요약
   - 지원 화면이 허용하는 경우 각 답변의 첫 줄에 하나만 있는지 확인한다.
   - 명사형인지 확인하고 서술형 종결이나 마침표가 있으면 고친다.
   - 본문에 없는 성과를 만들지 않았고 글자 수에 포함됐는지 확인한다.
5. 개조식 본문 후보
   - 기업이 목록 형식을 요구하지 않았다면 실제 답변의 목록 행을 완결된 문장과 문단으로 바꾼다.
   - 작성 설계와 검토 기록의 개조식은 검사 대상 답변 블록과 분리한다.

검토 기록에는 단순히 `검사 통과`라고 쓰지 않는다. 발견 개수, 각 후보의 유지 또는 수정 판단과 최신 본문에서 남은 예외를 기록한다. 가운데점이 남았다면 해당 공식 고유명사나 인용 원문을 함께 적는다. 영어 표현이 남았다면 그대로 유지해야 하는 이유 또는 붙인 설명을 확인한다. 서술형 요약과 개조식 본문 후보가 0건인지도 기록한다.

도구는 문항과 소재가 실제로 어울리는지, 배운 점이 사건에서 타당하게 도출되는지 판단하지 못한다. 이 두 항목은 문항별 작성 설계와 의미 검토에서 반드시 별도로 판정한다.

## 초안

- 각 문항 답변의 첫 줄에 해당 답변 전체를 대표하는 명사형 `[핵심 요약 문구]` 하나를 작성한다.
- 기업이 다른 형식을 요구하지 않는 한 실제 답변 본문은 개조식이 아닌 서술식으로 작성한다.
- 필요한 역량을 먼저 설명하고 기술 이름만 나열하지 않는다.
- 프로젝트에서 왜 그 기술이나 구조가 필요했는지 연결한다.
- 소재 수와 분량은 문항의 요구, 사용자의 전략과 사례의 깊이에 따라 정한다.
- 글자 수 제한은 상한이며 항상 95퍼센트를 채워야 하는 목표가 아니다.
- 회사와의 연결은 JD가 실제로 요구한 업무 범위 안에서만 한다.
- 경험 문항은 결과 뒤에 그 경험에서 실제로 도출된 배운 점, 느낀 점, 달라진 판단 기준 또는 이후 행동을 쓴다.
- 초안에 사용한 소재, 미사용 소재와 답하지 못한 하위 질문을 함께 기록한다.

## 버전과 리뷰

초안과 주요 수정본은 `02_작성중`에서 새 번호를 사용한다.

리뷰는 다음 순서로 진행한다.

1. 사실 정합성
2. 문항과 소재의 적합성
3. 문항 충실도
4. 직무와 JD 연결
5. 본인 역할과 차별성
6. 소재 중복
7. 구조와 표현

구조 검토에서는 대괄호 핵심 요약이 답변 최상단에 하나만 있는지, 명사형인지, 본문과 같은 내용을 말하는지, 글자 수에 포함됐는지 확인한다. 기업의 별도 요구가 없다면 본문이 개조식 목록이 아닌 서술식인지도 확인한다.

경험 문항의 의미 검토에서는 결과 뒤의 배운 점이나 변화가 앞선 사건에서 자연스럽게 도출되는지 확인한다. 배운 점이 없거나 어느 사례에도 붙일 수 있는 일반론이면 `치명`으로 분류하고 `유효 초안`으로 판정하지 않는다.

표현 검토에서는 `scripts/validate_essay_style.py` 결과의 모든 후보를 확인한다. 가운데점과 영어 표현 후보가 검토 기록에서 누락되면 표현 검토를 완료한 것으로 보고하지 않는다.

이슈 등급:

- `치명`: 사실 오류, 역할 과장, 문항 누락, 필수 하위 질문과 소재의 부적합, 경험 문항의 배운 점이나 변화 누락, 글자 수 초과
- `권장`: 근거가 약한 연결, 모호한 행동, 중요한 결과 누락
- `선택`: 리듬, 어휘와 취향에 가까운 표현

각 고유 이슈에 `R1`, `R2`처럼 번호를 붙인다. 같은 문장이 사실 정합성, 문항 충실도와 표현 영역에 모두 영향을 주더라도 한 이슈로 집계하고 관련 영역만 함께 표시한다. 상단 요약의 이슈 수는 고유 번호 수와 일치해야 한다.

표현 검토가 사실 검토보다 앞서지 않게 한다.

## 글자 수

다음 기준은 문항에 별도 요구가 없을 때의 권장 전략이며 완료 조건이 아니다.

| 글자 수 제한 | 권장 소재와 깊이 |
| --- | --- |
| 500자 이하 | 핵심 주장 1개와 사례 1개 |
| 501자에서 1000자 | 주 사례 1개를 문제, 행동과 결과까지 설명 |
| 1001자에서 1500자 | 주 사례 1개를 깊게 쓰고 짧은 보조 근거를 선택적으로 추가 |
| 1501자 이상 | 깊은 사례 1개 또는 서로 보완하는 사례 2개를 문항 구조에 따라 선택 |

- 초안은 대체로 제한의 85퍼센트에서 95퍼센트 사이에서 핵심 내용이 완결되도록 작성한다.
- 최종본은 충분한 사실이 있을 때 제한의 90퍼센트에서 100퍼센트 사이로 조정한다.
- 목표 비율을 맞추기 위해 의미 없는 문장, 일반적인 포부와 중복 사례를 추가하지 않는다.
- 글자 수보다 문항의 모든 하위 질문에 답했는지를 먼저 확인한다.
- 기업이 최소 글자 수나 다른 기준을 제시하면 해당 기준을 우선한다.
- 대괄호 핵심 요약과 답변 내부에 실제로 입력할 소제목도 글자 수에 포함한다.

제출 문안이 Markdown의 ```text` 블록에 있으면 `scripts/count_essay_characters.py`로 코드 블록별 글자 수를 센다.

```bash
python scripts/count_essay_characters.py 회사/02_작성중/자소서.md
```

공백 포함 여부와 제목 포함 여부가 불명확하면 실제 지원 폼을 확인하고 미확인 상태를 기록한다.

## humanize-korean

내용, 사실과 문항 검토가 끝난 뒤에만 선택적으로 사용한다.

권장 입력:

- 장르: 공적
- 강도: 보수
- 최소심각도: S1

처리 순서:

1. 최신 작성본을 보존한다.
2. macOS와 Linux에서는 `mktemp -d`, Windows에서는 안전한 임시 디렉터리 기능으로 시스템 임시 폴더를 만든다.
3. 원문은 전체 경로로 참조하고 임시 폴더를 작업 위치로 삼아 `humanize-korean`을 실행한다.
4. 생성된 `_workspace`의 결과를 임시 후보로만 다루고 바로 제출 폴더로 옮기지 않는다.
5. 원문과 수치, 날짜, 고유명사, 기술 용어, 역할, 인과관계와 결론을 대조한다.
6. 글자 수를 다시 계산한다.
7. 모든 변경을 전체 diff 또는 빠짐없는 변경 목록으로 사용자에게 보여준다. 일부 예시만 보여주고 전체 후보를 폐기하지 않는다.
8. 사용자가 채택할 때까지 임시 후보를 유지한다. 다음 대화에서 임시 후보를 읽을 수 없으면 같은 조건으로 다시 실행하고 동일한 변경인지 검증한다.
9. 사용자가 채택하면 `next-draft`로 번호를 다시 확인하고 다음 작성본으로 `02_작성중`에 저장한다.
10. 검토 내역을 보존할 필요가 있으면 해당 기업의 `03_검토기록`을 그때 만들고 출처 초안, 검토 종류와 날짜를 알 수 있는 이름으로 저장한다.
11. 채택본 저장과 검증이 끝나거나 사용자가 후보를 거절한 뒤 임시 폴더와 그 안의 `_workspace`를 정리한다.

워크스페이스나 시즌 폴더를 `humanize-korean`의 작업 위치로 사용하지 않는다. 이미 그 위치에 `_workspace`가 생겼다면 결과의 출처와 채택 여부를 확인한 뒤 보존할 결과만 기업별 `03_검토기록`으로 옮기고 남은 임시 파일을 정리한다. 번호가 붙은 작성본에 채택 내용이 모두 남아 있다면 같은 전문을 중복 저장하지 않고 검토 요약만 보존해도 된다.

의미가 바뀌거나 변경 범위가 과하면 해당 변경을 롤백한다. `humanize-korean`이 없으면 연결어미 뒤 쉼표, 종결어미 반복, 번역투, 접속사 남발과 상투 표현만 보수적으로 점검한다.

도구의 등급을 높이는 것 자체를 목표로 추가 윤문 도구나 넓은 수정 모드를 제안하지 않는다. 내용과 사실 검토가 끝났고 남은 변경이 취향에 가까우면 현재 후보를 사용자 선택에 맡긴다.
