# 자소서 작성과 검토

자소서 소재를 모으거나 문항을 분석하고 초안을 만들 때 읽는다.

## 사실 원본

자소서 문장은 공통자료의 확인된 사실과 사용자가 지정한 원본에서만 만든다.

- 프로젝트 최종 원고
- 작업 기록
- 이슈와 티켓
- 커밋과 코드 리뷰 메시지
- 테스트와 운영 로그
- 사용자가 직접 작성한 상세 사례

출처 파일을 현재 환경에서 읽을 수 없으면 존재했다는 설명만 사실로 받아들이고 세부 내용을 재구성하지 않는다.

## 소재 준비

각 사례는 필요한 만큼 다음 항목을 채운다.

1. 상황과 목표
2. 문제와 제약
3. 본인의 판단
4. 선택한 해결 방법
5. 담당 역할
6. 협업 또는 의견 조율
7. 실패한 가설과 수정
8. 검증 방법
9. 결과와 수치
10. 배운 점

소재를 모으는 단계에서는 글자 수에 맞춰 사례를 삭제하지 않는다. 상세 사례를 충분히 보존한 뒤 기업별 문항에서 선택한다.

## 문항 분석

문항 원문과 글자 수 기준을 그대로 기록한다. 복합 문항은 하위 질문으로 분해한다.

각 하위 질문에 대해 다음을 정한다.

- 요구하는 역량
- 사용할 사실과 사례
- 본인의 행동
- 결과
- JD와 연결할 지점
- 답하지 못한 부분

초안을 쓰기 전에 문항별 작성 설계를 남긴다.

```text
문항 유형:
하위 질문:
핵심 메시지:
주 소재:
보조 소재:
본인의 행동:
결과와 검증:
JD 연결:
문체:
소제목 허용 여부:
글자 수 기준:
```

사용자가 정한 소재와 강조 순서가 있으면 우선한다. 필요한 사실이 부족하면 확인 가능한 자료를 먼저 찾고 그래도 초안을 완성할 수 없을 때만 최대 3개의 구체적인 질문을 순서대로 묻는다.

문항이 공개되지 않았으면 임의로 만들어 초안을 쓰지 않는다.

## 소재 배분

- 문항의 하위 질문과 증명해야 할 역량을 기준으로 소재를 고른다.
- 같은 프로젝트를 여러 문항에서 사용할 수 있지만 같은 문제, 행동과 결과를 반복하지 않는다.
- 프로젝트 이름이 같다는 이유만으로 중복이라고 판단하지 않는다. 서로 다른 에피소드와 판단을 증명하는지 확인한다.
- 한 프로젝트에서 모든 역량을 억지로 뽑지 않는다.
- 긴 문항에서 사례를 두 개 사용할 때는 서로 다른 역량을 보완하거나 복합 문항의 각 질문에 답하도록 배치한다.
- 소재를 추가해도 새로운 정보가 생기지 않으면 사례 수를 늘리지 않는다.

## 기본 구조

문항에 별도 형식이 없으면 다음 흐름을 기본값으로 사용한다. 모든 단계를 기계적으로 한 문단씩 만들지 말고 문항과 분량에 맞춰 합치거나 생략한다.

```text
핵심 답변
→ 상황과 해결할 문제
→ 원인과 제약에 대한 판단
→ 본인이 선택하고 실행한 행동
→ 검증과 결과
→ 직무 또는 질문과의 연결
```

기술 이름을 먼저 나열하지 않는다. 왜 그 기술이나 구조가 필요했고 어떤 기준으로 선택했으며 실제로 어떻게 검증했는지를 설명한다.

## 문항 유형별 구조

### 지원동기

지원동기는 사용 가능한 근거에 따라 다음 중 하나를 고른다. 회사 칭찬이나 장기근속 의지를 의무적으로 넣지 않는다.

**경험과 전환 계기 중심**

```text
이전 경험
→ 관심이 커진 계기
→ 직접 수행한 행동
→ 역량과 생각의 변화
→ 직무 선택 이유
→ 성장 방향
```

**산업과 직무 적합 중심**

```text
직무에 대한 관심
→ 관련 프로젝트와 역할
→ 문제와 원인 분석
→ 본인의 행동과 선택
→ 결과와 형성된 역량
→ 직무에서의 활용
```

**기업 방향성 연결 중심**

```text
기업의 실제 사업, 서비스 또는 기술
→ 연결되는 본인의 경험
→ 직접 수행한 행동과 결과
→ 기업과 경험의 연결 근거
→ 지원 이유와 기여 방향
```

기업 방향성은 공식 자료와 공고에서 확인된 내용만 사용한다.

### 직무 전문성과 프로젝트

```text
보유 역량에 대한 핵심 답변
→ 프로젝트의 문제와 제약
→ 원인 분석과 선택 기준
→ 본인의 구현과 검증
→ 결과
→ JD 업무에서의 활용
```

### 협업과 의견 조율

```text
공동 목표와 의견 차이
→ 충돌의 원인과 제약
→ 본인이 제시한 기준 또는 조율 행동
→ 합의와 실행
→ 결과와 이후의 변화
```

갈등이 있었다는 사실보다 합의를 만들기 위해 본인이 무엇을 확인하고 바꿨는지를 중심으로 쓴다.

### 문제 해결

```text
문제와 영향
→ 원인 가설
→ 검증 과정
→ 실패한 시도와 판단 수정
→ 최종 해결
→ 재현 가능한 결과 또는 배운 점
```

### AI 활용

단순 질의응답을 AI 활용 경험으로 포장하지 않는다.

```text
에이전트에 부여한 목표
→ 제공한 코드, 로그와 데이터
→ 작업 범위와 권한 제한
→ 에이전트가 만든 결과
→ 사람이 실제 환경에서 검증한 방법
→ 틀린 가설과 실패 결과
→ 수정한 판단
→ 최종 성과
```

## 문체

- 지원 화면이나 사용자가 다른 형식을 요구하지 않으면 정중한 문어체와 `습니다체`를 기본으로 한다.
- 첫 문장이나 첫 문단에서 문항에 대한 핵심 답변을 제시한다.
- 한 문장에는 하나의 중심 내용을 두고 지나치게 긴 문장은 나눈다.
- 추상적인 역량 표현 뒤에는 이를 증명하는 실제 행동을 둔다.
- 팀의 결과와 본인의 행동을 구분한다.
- `저는`은 불필요하게 반복하지 않되 자연스러운 문장까지 금지하지 않는다.
- `을 통해`, `경험을 바탕으로`와 같은 연결 표현을 반복하지 않는다.
- 과도한 미사여구, 회사 칭찬과 상투적인 포부로 분량을 채우지 않는다.
- 공식 고유명사와 표준 기술 용어는 보존한다.
- 가운데점은 문체 장식으로 사용하지 않는다. 공식 고유명사에 포함된 경우에만 원문을 보존한다.
- 소제목은 지원 화면에서 허용되고 핵심 내용을 빠르게 이해시키는 경우에만 사용한다.

## 초안

- 필요한 역량을 먼저 설명하고 기술 이름만 나열하지 않는다.
- 프로젝트에서 왜 그 기술이나 구조가 필요했는지 연결한다.
- 소재 수와 분량은 문항의 요구, 사용자의 전략과 사례의 깊이에 따라 정한다.
- 글자 수 제한은 상한이며 항상 95퍼센트를 채워야 하는 목표가 아니다.
- 회사와의 연결은 JD가 실제로 요구한 업무 범위 안에서만 한다.
- 초안에 사용한 소재, 미사용 소재와 답하지 못한 하위 질문을 함께 기록한다.

## 버전과 리뷰

초안과 주요 수정본은 `02_작성중`에서 새 번호를 사용한다.

리뷰는 다음 순서로 진행한다.

1. 사실 정합성
2. 문항 충실도
3. 직무와 JD 연결
4. 본인 역할과 차별성
5. 소재 중복
6. 구조와 표현

이슈 등급:

- `치명`: 사실 오류, 역할 과장, 문항 누락, 글자 수 초과
- `권장`: 근거가 약한 연결, 모호한 행동, 중요한 결과 누락
- `선택`: 리듬, 어휘와 취향에 가까운 표현

표현 검토가 사실 검토보다 앞서지 않게 한다.

## 글자 수

다음 기준은 문항에 별도 요구가 없을 때의 권장 전략이며 완료 조건이 아니다.

| 글자 수 제한 | 권장 소재와 깊이 |
| --- | --- |
| 500자 이하 | 핵심 주장 1개와 사례 1개 |
| 501자에서 1000자 | 주 사례 1개를 문제, 행동과 결과까지 설명 |
| 1001자에서 1500자 | 주 사례 1개를 깊게 쓰고 짧은 보조 근거를 선택적으로 추가 |
| 1501자 이상 | 깊은 사례 1개 또는 서로 보완하는 사례 2개를 문항 구조에 따라 선택 |

- 초안은 대체로 제한의 85퍼센트에서 95퍼센트 사이에서 핵심 내용이 완결되도록 작성한다.
- 최종본은 충분한 사실이 있을 때 제한의 90퍼센트에서 100퍼센트 사이로 조정한다.
- 목표 비율을 맞추기 위해 의미 없는 문장, 일반적인 포부와 중복 사례를 추가하지 않는다.
- 글자 수보다 문항의 모든 하위 질문에 답했는지를 먼저 확인한다.
- 기업이 최소 글자 수나 다른 기준을 제시하면 해당 기준을 우선한다.

제출 문안이 Markdown의 ```text` 블록에 있으면 `scripts/count_essay_characters.py`로 코드 블록별 글자 수를 센다.

```bash
python scripts/count_essay_characters.py 회사/02_작성중/자소서.md
```

공백 포함 여부와 제목 포함 여부가 불명확하면 실제 지원 폼을 확인하고 미확인 상태를 기록한다.

## humanize-korean

내용, 사실과 문항 검토가 끝난 뒤에만 선택적으로 사용한다.

권장 입력:

- 장르: 공적
- 강도: 보수
- 최소심각도: S1

처리 순서:

1. 최신 작성본을 보존한다.
2. `humanize-korean` 결과를 임시 후보로 받는다.
3. 결과 파일을 바로 제출 폴더로 옮기지 않는다.
4. 원문과 수치, 날짜, 고유명사, 기술 용어, 역할, 인과관계와 결론을 대조한다.
5. 글자 수를 다시 계산한다.
6. 사용자가 채택하면 다음 번호의 작성본으로 저장한다.

의미가 바뀌거나 변경 범위가 과하면 해당 변경을 롤백한다. `humanize-korean`이 없으면 연결어미 뒤 쉼표, 종결어미 반복, 번역투, 접속사 남발과 상투 표현만 보수적으로 점검한다.
