# 자소서 작성과 검토

자소서 작업의 자료 준비, 저장, 검사와 버전 관리를 다룬다. **작성 전과 내용 검토 때 [주장과 문맥](essay-composition.md)을 읽는다.** 의미 판단 기준은 그 문서 한 곳에서 관리한다. 체크포인트는 설계·검토 기록 작성 시, 문항별 규칙은 형식·분량 검사 시 읽는다.

초안 작성 전과 초안 검토 후에는 [자소서 체크포인트](essay-checkpoints.md)를 함께 읽고 전용 검사기를 실행한다. 실행 가능한 환경에서는 통과 후 진행한다. 스크립트 실행이 불가능하면 같은 항목을 수동 검토해 본문을 제공하고 자동 검사는 미실행으로 남긴다. 훅·Drive·Notion 유무와 관계없이 아래 내용 검토 순서는 유지한다. 워크스페이스에 프로젝트 훅을 설치한 경우에는 [자소서 훅](essay-hooks.md)도 읽고 실행 상태를 먼저 등록한다.

## 사실 원본

자소서 문장은 공통자료의 확인된 사실과 사용자가 지정한 원본에서만 만든다.

- 프로젝트 최종 원고
- 작업 기록
- 이슈와 티켓
- 커밋과 코드 리뷰 메시지
- 테스트와 운영 로그
- 사용자가 직접 작성한 상세 사례

출처 파일을 현재 환경에서 읽을 수 없으면 존재했다는 설명만 사실로 받아들이고 세부 내용을 재구성하지 않는다.

## 소재 준비

각 사례는 필요한 만큼 다음 항목을 채운다.

1. 상황, 목표와 맡은 책임
2. 문제를 인식한 계기, 중요하게 본 이유와 예상 영향
3. 당시의 생각이나 느낌이 문항에 필요하다면 그 근거
4. 선택한 행동과 실행 방법, 다른 선택지보다 이를 택한 이유
5. 피드백, 실패한 가설과 판단 수정이 실제로 있었다면 그 과정
6. 검증 방법, 결과와 수치, 본인 기여와 팀 기여의 구분
7. 사건에서 도출된 구체적인 이해와 이를 반영한 이후의 실제 행동 또는 향후 계획

감정, 동기와 판단 이유는 코드, 로그와 결과만 보고 추정하지 않는다. 갈등, 실패나 극적인 생각의 변화를 모든 사례에 억지로 만들 필요도 없다. 기존 원칙을 유지한 사례라도 그 원칙이 왜 중요한지 더 분명히 이해한 근거가 있다면 경험의 의미가 될 수 있다.

소재를 모으는 단계에서는 글자 수에 맞춰 사례를 삭제하지 않는다. 상세 사례를 충분히 보존한 뒤 기업별 문항에서 선택한다.

## 작성 설계와 정보 부족

문항 원문·출처·형식·글자 수 기준과 기존 채택본을 확인하고 필수 하위 질문을 분해한다. 문항이 공개되지 않았으면 임의로 만들지 않는다. 문항 수집은 [공고와 연결 서비스](posting-and-connectors.md)의 범위를 따른다. 전체 문항 요청을 지원서 전체 입력 항목으로 확대하지 않는다.

[주장과 문맥](essay-composition.md)에 따라 중심 주장을 정하고 소재의 사실성과 적합성을 별도로 판단한다. 기존 writing_brief에 문제·확인할 사항·행동·결과가 연결되는 짧은 설명을 남기고, evidence_map과 detail_selection에 필요한 근거와 선택을 기록한다. JSON과 별도 장문 설계에 같은 내용을 중복하지 않는다.

근거가 부족하면 지정 원본 재확인 → 다른 적합한 소재 검토 → 필요한 개인 사실 질문 순서로 처리한다. 구조·설명·표현처럼 현재 자료로 해결할 수 있는 문제는 먼저 고친다. 사용자에게는 실제 경험·당시 판단·가치관만 어느 문항에 왜 필요한지 설명해 묻는다. 이미 확인된 정보를 재질문하거나 회사에 맞는 답을 유도하지 않는다. 최대 3개의 필요한 질문을 묶고 앞 답에 따라 다음 질문이 달라질 때만 순차적으로 묻는다.

새 설계는 버전 2 pre_draft로 전체 문항을 등록한다. 실행 가능한 환경에서는 다음 검사 후 별도 쓰기 작업으로 답변을 만든다.

```bash
python scripts/validate_essay_checkpoint.py 작성설계.md
```

일부 문항에만 사용자 사실이 필요하면 해당 문항은 deferred로 두고 본문을 만들지 않는다. 나머지는 검토 후 부분초안으로 보존한다. 모두 보류면 확인 질문을 남긴다. 사용자가 답하면 다음 번호에서 전체 문항을 확인하되 새 사실과 무관한 유효 문장을 불필요하게 다시 쓰지 않는다. 상태와 JSON 형식은 [체크포인트](essay-checkpoints.md)를 따른다.

## 답변 형식

설계·검토 기록에는 항목식을 쓸 수 있다. 실제 답변은 기업이 목록을 요구하지 않는 한 완결된 문장과 문단으로 작성하고, 기술·역할·성과의 목록으로 설명을 대신하지 않는다. 첫 문장이나 문단에서 핵심 답변을 제시하되 문단 수와 순서는 문항에 맞춘다.

### 대괄호 핵심 요약

지원 화면에서 대괄호와 줄바꿈을 허용하면 각 문항 답변의 첫 줄에 `[핵심 요약 문구]` 하나를 둔다.

- 본문보다 먼저 배치하고 한 줄로 작성한다.
- 문장 대신 명사형 구절로 작성한다. `했습니다`, `합니다`, `입니다`, `됩니다` 같은 서술형 종결과 마침표를 사용하지 않는다.
- 문항의 핵심 행동, 판단이나 결과를 압축한다.
- `도전과 성장`, `함께 만든 성과`처럼 어느 지원자에게나 적용되는 표현은 피한다.
- 본문에 없는 성과나 수치를 요약 문구에서 새로 만들지 않는다.
- 한 답변에 사례가 여러 개여도 최상단 요약은 하나가 기본이다. 사례별 추가 소제목은 구조상 꼭 필요하고 지원 화면이 허용할 때만 사용한다.
- 대괄호 문구도 지원 화면의 글자 수에 포함되는 것으로 보고 계산한다.
- 지원 화면이 특수문자나 소제목을 금지하거나 사용자가 다른 형식을 지정하면 해당 요구를 우선한다.

예시 형식:

```text
[실패 원인을 분리해 배포 안정성을 높인 경험]
본문 첫 문장부터 문항의 핵심 답변을 이어서 작성합니다.
```

좋은 예시:

- `[실패 원인을 분리한 15명 통합 검증]`
- `[반례를 받아들여 기준을 고친 경험]`

피해야 할 예시:

- `[운영 가능한 시스템을 만들었습니다]`
- `[반례를 받아들여 기준을 고쳤습니다.]`

## 문체

- 지원 화면이나 사용자가 다른 형식을 요구하지 않으면 정중한 문어체와 `습니다체`를 기본으로 한다.
- 첫 문장이나 첫 문단에서 문항에 대한 핵심 답변을 제시한다.
- 한 문장에는 하나의 중심 내용을 두고 지나치게 긴 문장은 나눈다.
- 추상적인 역량 표현 뒤에는 이를 증명하는 실제 행동을 둔다.
- 팀의 결과와 본인의 행동을 구분한다.
- `저는`은 불필요하게 반복하지 않되 자연스러운 문장까지 금지하지 않는다.
- `을 통해`, `경험을 바탕으로`와 같은 연결 표현을 반복하지 않는다.
- 과도한 미사여구, 회사 칭찬과 상투적인 포부로 분량을 채우지 않는다.
- 공식 고유명사와 표준 기술 용어는 보존한다.
- 가운데점은 문체 장식으로 사용하지 않는다. 공식 고유명사에 포함된 경우에만 원문을 보존한다.
- 의미를 정확히 유지할 수 있으면 영어 약어, 내부 저장소명과 구현 용어보다 쉬운 한국어를 우선한다.
- 번역하면 의미가 달라지는 공식 기술명과 표준 용어는 유지하되, 채용 담당자가 바로 이해하기 어려운 지표와 약어는 첫 등장에 짧은 한국어 설명을 붙인다.
- 세부 규격이 역량 증명에 필요하지 않으면 상위 개념으로 줄인다. 예를 들어 코덱 조합은 `MP4 영상`, `OOM`은 `메모리 부족으로 인한 종료`, `Read Model`은 `조회 모델`로 표현할 수 있다.
- 기술 용어를 한국어로 바꿀 때 사실의 범위가 넓어지거나 의미가 달라지면 원어를 유지하고 설명을 덧붙인다.
- 최상단 대괄호 핵심 요약은 기본 스타일로 사용한다. 그 밖의 소제목은 핵심 내용을 빠르게 이해시키는 데 필요할 때만 추가한다.

## 필수 표현 검증

초안과 모든 주요 수정본은 내용 검토 뒤 다음 검사를 수행한다. 기업이나 사용자의 형식 예외가 있으면 [문항별 규칙](essay-rules.md)에 따라 동일한 `--rules` 파일을 검사기와 훅에 전달한다. `humanize-korean` 사용 여부와 관계없이 생략하지 않는다.

```bash
python scripts/validate_essay_style.py --strict 회사/02_작성중/자소서.md
```

구조 오류가 있으면 종료 코드 2로 실패한다. 가운데점, 영어와 쉼표는 문맥에 따라 유지할 수 있으므로 후보를 찾은 뒤 다음 항목을 답변 본문별로 빠짐없이 판정한다.

1. 모든 가운데점
   - 공식 고유명사 또는 문항 원문 인용이면 유지한다.
   - 기술, 역할, 조치와 성과를 나열하는 가운데점이면 쉼표, 조사 또는 문장 분리로 바꾼다.
2. 모든 영어 표현 후보
   - 회사명, 제품명과 표준 기술명처럼 그대로 써야 하는지 확인한다.
   - 내부 저장소명, 코드 변수, 생소한 지표, 약어와 구현 세부사항이면 쉬운 한국어로 바꾸거나 첫 등장에 설명한다.
   - 기술명 수가 많으면 각 이름의 필요성을 다시 확인하고 문제, 판단, 행동과 검증을 중심으로 줄인다.
3. 연결어미 뒤 쉼표 후보
   - 문장 호흡상 꼭 필요하지 않은 `하고,`, `했으며,`, `하지만,` 형태의 쉼표를 제거한다.
   - 쉼표를 일괄 삭제하지 않고 의미 구분에 필요한 경우는 유지한다.
4. 대괄호 핵심 요약
   - 지원 화면이 허용하는 경우 각 답변의 첫 줄에 하나만 있는지 확인한다.
   - 명사형인지 확인하고 서술형 종결이나 마침표가 있으면 고친다.
   - 본문에 없는 성과를 만들지 않았고 글자 수에 포함됐는지 확인한다.
5. 개조식 본문 후보
   - 기업이 목록 형식을 요구하지 않았다면 실제 답변의 목록 행을 완결된 문장과 문단으로 바꾼다.
   - 작성 설계와 검토 기록의 개조식은 검사 대상 답변 블록과 분리한다.

검토 기록에는 단순히 `검사 통과`라고 쓰지 않는다. 발견 개수, 각 후보의 유지 또는 수정 판단과 최신 본문에서 남은 예외를 기록한다. 가운데점이 남았다면 해당 공식 고유명사나 인용 원문을 함께 적는다. 영어 표현이 남았다면 그대로 유지해야 하는 이유 또는 붙인 설명을 확인한다. 적용한 문항별 규칙에 어긋나는 요약이나 본문 형식이 남았는지도 기록한다. 기업이 요구한 목록은 오류로 집계하지 않는다.

도구는 문항과 소재가 실제로 어울리는지, 경험에서 제시한 이해가 사건에서 타당하게 도출되는지 판단하지 못한다. 이 두 항목은 문항별 작성 설계와 의미 검토에서 반드시 별도로 판정한다.

## 초안 저장

검토를 통과한 본문은 별도 작성본에 문항 ID를 붙인 text 블록으로 저장한다. 문항별 코드 블록과 기업별 형식은 [문항별 규칙](essay-rules.md)을 따른다. 작성 설계와 답변을 같은 파일이나 같은 쓰기 작업으로 만들지 않는다.

초안 전과 검토 체크포인트, 표현, 분량 검사를 통과한 결과만 번호가 붙은 초안 또는 부분초안으로 보존한다. 검사 결과가 좋다는 이유만으로 자동 채택하지 않는다.

## 버전과 리뷰

초안과 주요 수정본은 `02_작성중`에서 새 번호를 사용한다.

### 사용자 수정 이력과 채택 문안

- 현재 문항과 관련된 사용자의 명시적 피드백, 직접 고친 문장과 채택한 버전이 있으면 초안 전에 먼저 읽는다.
- 사용자가 명시적으로 채택한 문안은 application_state.py select --kind essay로 기록해 다음 수정의 기준점으로 삼고, 일반적인 모범답안이나 검사 점수를 이유로 제거한 내용을 다시 넣지 않는다.
- 버전 차이에서 추측한 취향은 사용자가 확인하기 전까지 영구 규칙으로 만들지 않는다. 특정 회사의 소재 배치와 글자 수 전략도 다른 지원서에 자동 적용하지 않는다.
- 채택 문안을 존중한다는 이유로 사실 오류, 역할 과장, 문항의 필수 요구 누락이나 제출 조건 위반을 그대로 두지 않는다. 문제가 확인되면 근거와 영향을 설명하고 필요한 범위만 고친다.
- 새 버전마다 이전 버전, 이번 수정의 주목적, 관련 이슈 번호, 판단·정보·구조의 실제 변화, 해결 및 미해결 이슈, 문항별 글자 수 영향을 기록한다. 단순한 문구 교체 목록만으로 수정 기록을 대신하지 않는다.
- 우선순위가 높은 세 건처럼 임의의 개수만 고친 뒤 검토를 끝내지 않는다. 발견한 이슈를 모두 판정하고, 치명 이슈는 전부 해결하거나 해당 문항을 보류하기 전까지 유효 초안으로 저장하지 않는다.
- 사용자가 의도적으로 삭제하거나 축소한 내용을 일반 체크리스트를 맞추기 위해 다시 넣지 않는다. 다시 필요하다고 판단하면 먼저 문항 누락, 사실 오류 또는 설득력 저하의 근거를 제시한다.

본문만으로 연결 검토와 수정을 거친 뒤 다음 항목을 원본과 대조한다. 이미 남긴 독해 이슈는 중복 집계하지 않는다.

1. 사실 정합성
2. 문항과 소재의 적합성
3. 문항 충실도
4. 직무와 JD 연결
5. 본인 역할과 차별성
6. 소재 중복
7. 구조와 표현

구조와 표현은 위 답변 형식 및 문항별 규칙으로 확인한다.

경험의 의미는 [주장과 문맥](essay-composition.md)의 기준으로 확인하고 다음 등급을 적용한다.

- 문항이 배움이나 느낀 점을 직접 요구했는데 답하지 않으면 `치명`이며 유효 초안으로 판정하지 않는다.
- 확인되지 않은 생각, 감정, 동기, 역할이나 결과를 만들면 `치명`이다.
- 판단 변화나 경험의 의미가 본문에 구체적으로 드러나면 별도 교훈 문장이 없어도 문제로 보지 않는다.
- 문항이 이를 직접 요구하지 않았고 다른 필수 질문에는 답했지만 기술과 성과만 나열돼 경험의 의미가 없으면 `권장`이다. 유효 초안으로 남길 수 있으나 최종 후보 전에는 보완한다.
- 어느 사례에도 붙일 수 있는 일반론은 `권장`이다. 다만 그것이 문항이 직접 요구한 배움이나 느낀 점에 대한 유일한 답이면 필수 질문 누락으로 다시 평가한다.

표현 검토에서는 `scripts/validate_essay_style.py` 결과의 모든 후보를 확인한다. 가운데점과 영어 표현 후보가 검토 기록에서 누락되면 표현 검토를 완료한 것으로 보고하지 않는다.

이슈 등급:

- `치명`: 핵심 답·본인 기여·인과관계를 이해할 수 없는 설명 누락, 사실 오류, 역할 과장, 문항 누락, 필수 하위 질문과 소재의 부적합, 문항이 직접 요구한 배움이나 느낀 점 누락, 글자 수 초과
- `권장`: 근거가 약한 연결, 모호한 행동, 중요한 결과 누락, 문항이 직접 요구하지 않았더라도 경험의 구체적인 의미가 없는 답변
- `선택`: 문항이 요구하지 않은 교훈이나 포부의 추가, 리듬, 어휘와 취향에 가까운 표현

각 고유 이슈에 `R1`, `R2`처럼 번호를 붙인다. 같은 문장이 사실 정합성, 문항 충실도와 표현 영역에 모두 영향을 주더라도 한 이슈로 집계하고 관련 영역만 함께 표시한다. 상단 요약의 이슈 수는 고유 번호 수와 일치해야 한다.

새 버전을 저장하기 전에는 `revision` 체크포인트에 전체 이슈 검토 여부와 남은 치명 이슈를 기록한다. `all_identified_issues_reviewed`가 참이 아니거나 `remaining_fatal_issues`가 비어 있지 않으면 검사를 통과할 수 없다.

표현 검토가 사실 검토보다 앞서지 않게 한다.

사용자가 채택한 문안이 필수 기준과 제출 조건을 모두 충족하면 검토를 종료한다. 더 복잡한 사례, 더 많은 기술이나 더 큰 수치를 넣을 수 있다는 이유만으로 다시 쓰지 않는다. 다만 채택본의 사실 오류와 문항 누락은 취향 문제가 아니므로 근거와 함께 알리고 바로잡는다.

## 글자 수

문항의 최소·최대 분량과 계산 기준을 지킨다. 그 범위 안에서는 짧은 설명의 연결을 먼저 완성한 뒤 필요한 근거만 확장한다. 제한이 없거나 남은 글자 수가 많다는 이유로 사례·기술·시험 이력을 추가하지 않는다. 분량의 일정 비율이나 사례 수를 채우는 것을 완료 조건으로 삼지 않는다. 대괄호 요약과 실제 입력할 소제목도 포함해 계산한다.

제출 문안이 Markdown의 ```text` 블록에 있으면 `scripts/count_essay_characters.py`로 코드 블록별 글자 수를 센다.

```bash
python scripts/count_essay_characters.py 회사/02_작성중/자소서.md
```

공백 포함 여부와 제목 포함 여부가 불명확하면 실제 지원 폼을 확인하고 미확인 상태를 기록한다.

## humanize-korean

내용, 사실과 문항 검토가 끝난 뒤에만 선택적으로 사용한다.

권장 입력:

- 장르: 공적
- 강도: 보수
- 최소심각도: S1

처리 순서:

1. 최신 작성본을 보존한다.
2. macOS와 Linux에서는 `mktemp -d`, Windows에서는 안전한 임시 디렉터리 기능으로 시스템 임시 폴더를 만든다.
3. 원문은 전체 경로로 참조하고 임시 폴더를 작업 위치로 삼아 `humanize-korean`을 실행한다.
4. 생성된 `_workspace`의 결과를 임시 후보로만 다루고 바로 제출 폴더로 옮기지 않는다.
5. 원문과 수치, 날짜, 고유명사, 기술 용어, 역할, 인과관계와 결론을 대조한다.
6. 글자 수를 다시 계산한다.
7. 모든 변경을 전체 diff 또는 빠짐없는 변경 목록으로 사용자에게 보여준다. 일부 예시만 보여주고 전체 후보를 폐기하지 않는다.
8. 사용자가 채택할 때까지 임시 후보를 유지한다. 다음 대화에서 임시 후보를 읽을 수 없으면 같은 조건으로 다시 실행하고 동일한 변경인지 검증한다.
9. 사용자가 채택하면 `next-draft`로 번호를 다시 확인하고 다음 작성본으로 `02_작성중`에 저장한다.
10. 검토 내역을 보존할 필요가 있으면 해당 기업의 `03_검토기록`을 그때 만들고 출처 초안, 검토 종류와 날짜를 알 수 있는 이름으로 저장한다.
11. 채택본 저장과 검증이 끝나거나 사용자가 후보를 거절한 뒤 임시 폴더와 그 안의 `_workspace`를 정리한다.

워크스페이스나 시즌 폴더를 `humanize-korean`의 작업 위치로 사용하지 않는다. 이미 그 위치에 `_workspace`가 생겼다면 결과의 출처와 채택 여부를 확인한 뒤 보존할 결과만 기업별 `03_검토기록`으로 옮기고 남은 임시 파일을 정리한다. 번호가 붙은 작성본에 채택 내용이 모두 남아 있다면 같은 전문을 중복 저장하지 않고 검토 요약만 보존해도 된다.

의미가 바뀌거나 변경 범위가 과하면 해당 변경을 롤백한다. `humanize-korean`이 없으면 연결어미 뒤 쉼표, 종결어미 반복, 번역투, 접속사 남발과 상투 표현만 보수적으로 점검한다.

도구의 등급을 높이는 것 자체를 목표로 추가 윤문 도구나 넓은 수정 모드를 제안하지 않는다. 내용과 사실 검토가 끝났고 남은 변경이 취향에 가까우면 현재 후보를 사용자 선택에 맡긴다.
