# 예외 시나리오

같은 기업의 여러 공고, 공고 변경, 마감 예외, 출처 충돌 또는 연결 서비스 재처리가 발생했을 때 읽는다. 일반적인 한 건의 지원에는 불필요한 구조를 미리 만들지 않는다.

## 지원 건 식별

지원 건은 회사 폴더 이름이 아니라 실제 제출 단위를 기준으로 구분한다.

- 하나의 지원서에서 1지망과 2지망 직무를 함께 고르면 한 지원 건이다.
- 직무마다 별도 지원서를 제출하면 각각 다른 지원 건이다.
- 같은 회사와 직무라도 공고 원문이나 모집 시기가 다르면 다른 지원 건일 수 있다.

공고 제목이나 마감일만으로 동일한 공고라고 판단하지 않는다. 다음 항목을 함께 확인한다.

- 기업 또는 법인명
- 공고명
- 지원 직무
- 공식 공고 URL
- 출처가 제공하는 공고 ID
- 모집 시기와 전형

공고 분석 문서 상단에 최초 확인일, 마지막 확인일과 위 식별 정보를 남긴다. 외부 ID가 없으면 임의의 ID를 만들지 않고 `없음`으로 기록한다.

## 폴더 충돌

시즌 안에 같은 회사 폴더가 없으면 기존처럼 `회사명`을 사용한다. 구분이 필요한 두 번째 지원 건부터 `회사명_직무`를 사용하고 같은 직무의 다른 공고까지 있으면 공식 공고 ID 또는 짧은 공고 구분명을 덧붙인다.

```text
회사명/
회사명_IT/
회사명_IT_R261762/
```

- 마감일은 바뀔 수 있으므로 폴더 식별자로 사용하지 않는다.
- 기존 폴더는 새 규칙에 맞추려고 이름을 바꾸지 않는다.
- 폴더를 만들기 전에 기존 공고 분석 문서와 Notion 항목을 검색해 중복을 확인한다.
- 운영체제에서 사용할 수 없는 문자는 안전한 구분자로 바꾼다.

지원 건 생성에는 `scripts/application_workspace.py`를 사용한다. 같은 기업과 직무의 새 지원 건에는 공식 공고 ID를 `--posting-key`로 전달하며, 공고 ID가 없으면 도구로 임의 값을 만들지 말고 사용자에게 구분명을 확인한다.

## 공고 변경과 재게시

공고를 처음 확보할 때 확인일을 기록한다. 작성 시작 전과 제출 직전에 공식 공고를 다시 확인한다.

다음 항목이 달라졌으면 기존 원본과 분석을 덮어쓰지 않는다.

- 마감일과 시간대
- 지원 직무와 주요 업무
- 자격요건과 우대사항
- 전형 절차
- 자소서 문항과 글자 수
- 필수 첨부 파일
- JD 파일 내용

새 원본에는 확인 날짜를 붙이고 `공고_변경이력.md`에 이전 값, 새 값, 확인일과 출처를 기록한다. 표현이나 화면 배치만 바뀌고 지원 판단에 영향이 없으면 새 원본을 만들지 않고 마지막 확인일만 갱신한다.

재게시 공고는 공식 공고 ID와 지원 가능 여부를 확인한다. 기존 지원의 수정인지 별도 지원 기회인지 확정할 수 없으면 사용자에게 알리고 합치지 않는다.

## 마감 예외와 상태

- 수시채용은 존재하지 않는 마감일을 만들지 않고 `수시`로 기록한다.
- 마감일이 공개되지 않았으면 `TBD`와 확인일을 남긴다.
- 시간대가 없으면 지역을 근거로 추측하지 않고 지원 화면에서 확인한다.
- 제출 전 공고가 조기 종료되면 파일을 삭제하지 않고 사유를 `공고 종료`로 기록하고 지원 상태는 `지원 안 함`으로 둔다.
- 사용자가 제출 전에 지원하지 않기로 결정했거나 마감까지 제출하지 않은 경우 `지원 안 함`을 사용한다.
- `종료`는 실제 제출 뒤 불합격, 전형 종료 또는 제출 후 철회한 지원 건에만 사용한다.
- 지원을 다시 시작하면 기존 자료를 보존하고 상태만 갱신한다.

Notion에 `지원 안 함`이 없으면 데이터 소스의 현재 선택지와 영향을 확인하고 사용자 승인을 받은 뒤 추가한다. 승인 전에는 가장 가까운 상태로 덮어쓰지 않고 본문에 실제 상황과 미반영 상태를 기록한다.

## 기업과 법인 구분

브랜드명, 채용 주체와 실제 법인명이 다르면 모두 기록한다. 인재상과 최근 동향은 지원서를 받는 법인과 해당 조직을 우선한다. 모회사나 계열사의 자료를 지원 기업의 사실처럼 사용하지 않는다.

## 첨부 파일 예외

- 링크가 만료됐으면 원래 URL과 확인일을 남기고 공식 대체 출처를 찾는다.
- 암호가 필요한 파일은 우회하지 않고 사용자에게 필요한 입력을 요청한다.
- 다운로드 파일의 형식과 이름은 응답 메타데이터나 실제 파일을 확인해 정한다.
- JD를 구하지 못해도 공고 화면에서 확인한 내용과 미확인 항목을 구분해 분석할 수 있다.

## 연결 서비스 재처리

Notion이나 Drive 반영이 필요한데 연결 또는 권한 문제로 실패하면 해당 지원 건의 `01_공고_JD/연결_미반영.md`에 다음만 기록한다.

- 실패한 서비스와 작업
- 대상 공고와 로컬 파일
- 실패 확인 시점
- 필요한 사용자 조치

토큰, 계정 정보, 외부 서비스 ID와 오류 응답의 민감한 값은 기록하지 않는다.

사용자가 연결을 복구했거나 새 작업에서 연결 상태가 달라졌을 때 미반영 문서를 먼저 확인한다. 작업을 한 번 실행하고 결과를 다시 가져와 검증한 뒤 완료 항목을 제거한다. 같은 실패가 계속되면 반복 호출하지 않고 남은 항목을 보고한다. 모든 항목이 반영되면 문서를 삭제할 수 있다.

## 제출 상태 충돌

상태 판단 우선순위는 다음과 같다.

1. 사용자의 실제 제출 확인
2. 공식 지원 페이지의 접수 완료 상태
3. 접수증과 완료 화면
4. `99_최종제출`의 실제 제출 지원서와 제출 첨부 파일
5. Notion 상태
6. 작성 중 파일 이름

Notion이 `지원 완료`여도 사용자 확인이나 공식 접수 완료 근거가 없으면 완료로 확정하지 않는다. 지원서 PDF가 없는 것만으로 실제 제출을 미완료로 되돌리지 않으며, 해당 사이트의 PDF 미제공 여부와 확보한 접수 증빙을 확인한다. 재제출은 기존 제출 파일과 증빙을 보존하고 새 버전과 제출일을 구분한다.
