# 워크스페이스와 상태

지원 작업을 시작하거나 재개할 때만 읽는다.

## 위치 발견

절대 경로를 가정하지 않는다. 현재 작업 위치를 기준으로 다음 순서로 찾는다.

1. 가장 가까운 `.chwippohaja/workspace.json`
2. 표식의 활성 시즌과 연결 상태
3. 상위 공통자료와 증빙서류
4. 회사별 폴더
5. 존재하는 로컬 `AGENTS.md`와 사용자 고유 설정

사용자가 별도 구조를 지정하면 기존 구조를 존중한다. 찾지 못한 경로를 임의로 생성하기 전에 현재 파일 목록과 대화를 확인한다.

표식이 없으면 [온보딩](onboarding.md)의 발견 절차를 따른다. 기존 자료가 있으면 초기화하지 말고 가져오기 후보로 분류한다.

현재 위치가 시즌이나 회사 폴더이고 상위 폴더에 `공통자료`와 `증빙서류`가 함께 있으면 상위 폴더를 워크스페이스 가져오기 후보로 우선한다. `AGENTS.md`의 존재 여부로 워크스페이스를 확정하지 않는다.

## 권장 역할 분리

```text
취업/
├── .chwippohaja/
│   └── workspace.json
├── 공통자료/
├── 증빙서류/
└── 시즌명/
    └── 회사명/
        ├── 01_공고_JD/
        ├── 02_작성중/
        ├── 03_검토기록/  # 필요한 경우에만 생성
        └── 99_최종제출/
```

`workspace.json`에는 저장 방식, 활성 시즌, 정보 설정 상태와 선택한 연결 기능만 기록한다. 계정, 인증 정보, 외부 서비스 ID, 개인 사실과 로컬 절대 경로는 기록하지 않는다.

기존 환경을 가져올 때는 표식에 개별 하위 폴더 경로를 기록하지 않는다. 현재 자료와 증빙 폴더를 확인해 의미가 분명한 기존 폴더를 사용한다. 권장 이름과 다르다는 이유로 새 폴더를 만들지 않는다.

### 자료와 적용할 지침

`AGENTS.md`와 사용자의 명시적 지시는 준수한다. 별도 운영 문서가 없으면 만들거나 요구하지 않는다. 기존 문서에서는 저장 위치·연결 설정과 사용자가 정한 선호·제약을 확인한다. 파일 이름이 작성 기준이라는 이유로 일반적인 글쓰기 방법을 추가 지침으로 읽어 적용하지 않는다.

일반 작성·검토 원칙은 현재 스킬을 기준으로 삼는다. 기존 문서의 고정 작성 순서, 테스트·수치·JD 연결 강제나 분량 채우기 규칙을 중첩하지 않는다. 공식 제출 조건과 사용자의 명시적 요청이 기본 작성법보다 우선한다. 서로 양립할 수 없는 명시적 요구가 있으면 영향을 설명하고 필요한 사항만 확인한다.

기존 양식 폴더를 정리할 때는 실제 답변·개인 선호와 빈 양식·일반 규칙을 구분한다. 사용자 자료는 해당 공통자료나 지원 건에 보존하고, 일반 규칙은 현행 스킬과 대조한다. 온보딩은 기존 파일을 자동 삭제하지 않는다.

### 정보 설정 상태

- `empty`: 확인된 개인 사실을 아직 모으지 않음
- `in_progress`: 일부 사실을 확인해 정리 중
- `ready`: 사용자가 현재 지원 작업에 필요한 사실이 충분하다고 확인함

기존 표식에 `profile_status`가 없으면 `empty`로 해석한다. 파일 수나 템플릿의 존재만으로 `ready`를 추측하지 않는다. 자세한 전환 기준은 [정보 온보딩](profile-onboarding.md)을 따른다.

### 연결 상태

- `disabled`: 사용자가 해당 연결 기능을 사용하지 않음
- `pending`: 사용할 예정이거나 기존 연결에 인증, 권한 또는 대상 선택 문제가 있음
- `enabled`: 현재 작업에서 읽기와 필요한 쓰기 권한을 실제로 확인함

도구가 목록에 보이는 것만으로 `enabled`를 추측하지 않는다. 상태가 바뀌면 `scripts/workspace_setup.py integration-status`로 해당 서비스만 갱신한다.

### 공통자료

- 기업과 무관하게 바뀌면 안 되는 확인된 개인 사실
- 학력, 교육, 경력, 기술과 프로젝트 사실
- 측정 조건을 포함한 성과와 수치
- 협업, 갈등 조율과 AI 활용 상세 사례

기업명, 직무, JD 키워드, 지원동기, 강조 순서와 글자 수 조건은 넣지 않는다.

### 스킬 내부 양식

빈 양식과 경험 수집 질문은 스킬 내부에서 관리한다. 필요한 양식에 답한 자료만 공통자료 또는 기업별 폴더에 저장한다. 워크스페이스에 별도 양식 폴더나 일반 작성 기준의 복사본을 만들지 않는다.

- 자소서 설계와 본문: [자소서 작성](essay-workflow.md)에서 필요한 양식을 선택한다.
- 경험 수집: [정보 온보딩](profile-onboarding.md)의 질문을 필요한 사실에만 사용한다.
- 포트폴리오 구성 요청: [포트폴리오 양식](../assets/templates/포트폴리오_구성.md)을 참고해 기업별 작업본을 만든다. 일반 작성·검토 기준은 이 스킬을 따른다.

### 증빙서류

- 학력
- 자격증과 어학
- 교육과 수상
- 경력과 병역
- 사진과 서명
- 민감서류

새 워크스페이스의 기본 하위 폴더는 `학력`, `자격증_어학`, `교육_수상`, `경력_병역`, `사진_서명`, `민감서류`다. 기존 워크스페이스에서는 `자격증`과 `어학`, `경력`과 `병역`처럼 분리된 구조도 같은 역할로 인정한다.

민감서류는 기업에서 명시적으로 요구할 때만 사용한다.

### 회사별 폴더

- `01_공고_JD`: 공고 원문, JD, 입력 가이드와 직무 분석
- `02_작성중`: 지원서 입력 초안, 자소서, 이력서와 포트폴리오 작업본
- `03_검토기록`: 윤문 결과, 사실 검토와 글자 수 점검처럼 나중에 확인할 가치가 있는 검토 산출물
- `99_최종제출`: 사용자가 실제로 제출한 파일과 공식 접수증 또는 완료 화면

`03_검토기록`은 기본 폴더가 아니다. 보존할 검토 산출물이 처음 생길 때만 해당 기업 폴더 아래에 만든다. 채택한 본문과 주요 수정본은 계속 `02_작성중`의 번호가 붙은 파일로 관리하며, 일반 초안이나 도구의 임시 파일을 `03_검토기록`에 섞지 않는다.

워크스페이스 또는 시즌 폴더의 `_workspace` 같은 도구 전용 출력 경로는 임시 공간으로만 취급한다. 가능하면 시스템 임시 폴더에서 도구를 실행하고 작업이 끝나면 정리한다. 결과를 보존해야 하면 출처 초안, 검토 종류와 날짜를 알아볼 수 있는 이름으로 `03_검토기록`에 옮긴다.

`02_작성중`에서는 Markdown을 기본 내용 원본으로 사용한다. Google Docs, DOCX와 다른 문서 형식은 사용자가 해당 형식을 원하거나 제출 서식 편집이 필요할 때 사용하며, 어떤 파일이 내용 원본인지 혼동되지 않게 구분한다.

기본적으로 폴더 하나가 실제 지원서 한 건에 대응한다. 같은 기업의 여러 직무와 공고가 충돌하면 [예외 시나리오](exception-scenarios.md)의 식별 규칙을 따른다.

새 지원 건은 스킬 루트의 도구로 생성 계획을 먼저 확인한다.

```bash
python scripts/application_workspace.py plan \
  --root "워크스페이스 경로" \
  --company "회사명" \
  --role "직무명"
```

요청에 포함된 새 지원 건 생성은 계획을 확인한 뒤 같은 인자로 `apply`를 실행한다. 기존 구조의 가져오기 여부가 불명확한 경우에만 사용자에게 확인한다. 기존 기업 폴더를 해당 지원 건으로 가져올 때만 `--adopt-existing`을 사용한다. 같은 회사와 직무의 별도 공고는 `--new-application`과 공식 `--posting-key`를 함께 사용한다.

## 버전 규칙

`02_작성중`의 새 작성 파일과 주요 수정본은 사용하지 않은 다음 두 자리 번호로 시작한다.

```text
01_회사명_직무_지원서_입력_초안.md
02_회사명_직무_자소서_초안.md
03_회사명_직무_자소서_초안.md
```

- 번호를 재사용하지 않는다.
- 주요 수정은 기존 버전을 덮어쓰지 않는다.
- 사용자가 특정 버전을 직접 수정하라고 명시한 소규모 보정만 같은 파일에 적용한다.
- 재제출 파일은 `_v2`처럼 제출 버전을 구분한다.

다음 작성 번호는 직접 추측하지 않고 도구로 확인할 수 있다.

```bash
python scripts/application_workspace.py next-draft \
  --application "지원 건 폴더" \
  --name "회사명_직무_자소서_초안" \
  --extension md
```

한 번에 여러 작성 파일을 만들 때는 각 파일을 독립적으로 미리 조회하지 않는다. 첫 파일을 생성한 뒤 `next-draft`를 다시 실행해 다음 번호를 확인하는 순서로 진행한다.

## 재개 판단

기존 작업이 있으면 파일명만 보고 상태를 추측하지 않는다.

1. `application_state.py status`에서 사용자가 채택한 작성본과 현재 공고 분석을 먼저 확인한다. 상태 기록이 없는 기존 지원 건만 파일과 대화에서 채택 여부를 확인한다. 가장 높은 번호를 자동으로 채택하지 않는다.
2. 체크리스트와 `TBD`를 찾는다.
3. `99_최종제출`에 실제 제출 파일이나 공식 접수 증빙이 있는지 확인한다.
4. Notion의 현재 지원 단계와 파일 링크를 확인한다.
5. 서로 다르면 실제 제출 자료와 사용자 확인을 우선하고 기록을 정정한다.

완료된 산출물을 다시 만들지 않고 필요한 다음 단계부터 진행한다.

## 현재 기준 파일과 독립적인 상태

지원 건의 `01_공고_JD/.application-state.json`은 선택한 파일, 파일 해시, 선택 근거와 이력 및 단계별 상태를 기록한다. 기존 `.application.json`과 `workspace.json`은 그대로 사용한다. 새 상태 파일이 없는 환경도 지원한다.

새로운 공고 분석이나 리서치를 검토한 뒤, 또는 사용자가 작성본을 채택한 뒤 기준 파일을 지정한다. 파일 내용은 변경하지 않는다.

```bash
python scripts/application_state.py select --application "지원 건" \
  --kind posting_analysis --file "01_공고_JD/새_공고분석.md" --note "변경된 공식 공고를 대조한 현재 분석"
python scripts/application_state.py select --application "지원 건" \
  --kind essay --file "02_작성중/02_자소서.md" --note "사용자가 채택한 버전"
python scripts/application_state.py status --application "지원 건"
```

파일 종류는 `posting_analysis`, `company_research`, `essay`, `application`이다. 사용자가 이전 버전을 채택할 때도 같은 명령으로 정확한 파일을 지정한다. 이전 선택과 파일을 보존한다. 선택 이후 파일 내용이 달라지면 다시 검토하고 재선택해야 한다. 파일을 선택했다는 사실만으로 품질 검증이나 제출 상태가 바뀌지는 않는다.

조사 검사기는 지정한 현재 파일만 검사한다. 미지정 상태에서 해당 종류의 파일이 하나면 기존 방식으로 읽는다. 여러 개면 최신 번호나 날짜를 추정하지 않고 명시적인 선택을 요구한다. 과거 분석의 미확인 사항은 과거 기록으로 보존한다.

### 자료 준비, 작성 검증과 실제 제출

필요한 단계가 끝났을 때 확인 근거와 함께 각각 기록한다.

```bash
python scripts/application_state.py stage --application "지원 건" \
  --stage writing --status valid_draft --evidence "현재 작성본의 문항, 사실, 역할과 형식 검증 완료"
python scripts/application_state.py stage --application "지원 건" \
  --stage submission --status confirmed --evidence "사용자의 실제 제출 확인과 확인일"
```

| 단계 | 상태 |
| --- | --- |
| materials | pending, partial, ready |
| writing | pending, partial_draft, valid_draft, final_candidate |
| submission | not_submitted, confirmed, evidence_saved |

자료 준비와 작성 검증 기록은 당시 현재 파일 해시에 연결된다. 내용이나 선택 파일이 달라지면 상태 조회의 `effective_status`가 재검토 필요로 표시될 수 있다. 제출 상태는 역사적 사실이므로 이후 작성본 변경만으로 되돌리지 않는다. `confirmed`는 실제 제출 확인, `evidence_saved`는 공식 접수 증빙 보관까지 확인한 경우에만 기록한다. 이 명령은 외부 상태를 조회하거나 제출을 수행하지 않는다.

### 외부 반영과 재검증

외부 도구로 실제 메타데이터나 Notion 페이지를 재조회한 다음 그 결과를 기록한다.

```bash
python scripts/application_state.py sync --application "지원 건" \
  --service notion --status verified --scope research --note "페이지 재조회로 현재 공고 정보와 파일 링크 확인"
```

서비스는 `google_drive` 또는 `notion`, 범위는 `research` 또는 `application`이다. 실패와 미반영은 `--status pending`과 구체적인 사유를 기록한다. `verified`는 기록 시점의 현재 파일 목록과 해시에 연결되므로 문서나 채택본이 바뀌면 다시 확인해야 한다. 기록 명령의 성공을 외부 반영 성공으로 대신하지 않는다.

상태 파일에는 확인에 필요한 근거만 적고 개인 입력값, 계정 정보와 인증 응답을 복사하지 않는다. 상태 변경 명령은 같은 지원 건에서 순서대로 실행한다.
