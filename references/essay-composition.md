# 자소서의 주장과 문맥

자소서 작성 전과 내용 검토 때 읽는다. 소재 선택, 설명의 연결과 독해 판정은 이 문서에서 관리한다. 파일·버전·검사 순서는 [작성 흐름](essay-workflow.md), 기록 형식은 [체크포인트](essay-checkpoints.md)를 따른다.

## 중심 주장과 소재

직무의 실제 업무와 모집 범위를 확인한 뒤 문항 원문을 하위 질문으로 나누고 무엇을 증명해야 하는지 정한다. 익숙한 소재에 맞춰 직무 범위나 질문의 뜻을 좁히지 않는다. `writing_brief.direct_answer`에는 확인된 사실로 뒷받침할 핵심 답변을 적는다. 자료가 자세하거나 검증 기록이 많다는 이유로 원래 문제를 시험 실적이나 다른 역량의 이야기로 바꾸지 않는다. 사용자가 지정한 소재와 강조점은 우선하되 문항에 맞지 않으면 근거와 대안을 설명한다.

각 하위 질문이 요구하는 것과 이를 증명할 실제 행동을 대조한다. 주제는 관련돼도 요구한 행동의 근거가 부족하면 그 차이를 적고 소재를 다시 검토한다. 행동이 문항의 핵심 동사를 증명하면 직접 적합, 확인된 보조 사실로 부족한 부분을 해소하면 조건부 적합, 새로운 동기나 역할을 만들어야 연결되면 부적합이다. `material_fit_reason`에는 이 판단을, `evidence_map`에는 하위 질문별 출처 위치와 확인된 주장을 남긴다. 기술명·업종·JD 키워드의 유사성은 적합성의 근거가 아니다.

문항 유형은 다음처럼 연결의 초점을 바꾸는 데 사용한다. 정해진 문단 수나 모든 칸을 채우는 틀로 쓰지 않는다.

| 문항이 요구하는 것 | 사실로 설명할 연결 |
| --- | --- |
| 높은 목표와 성취 | 기존 수준과 추가 목표, 어려웠던 이유, 이를 위한 행동과 실제 달성 범위. 목표 축소만으로 탁월함을 주장하지 않는다. 복합 제약을 충족한 난도는 근거가 있으면 설명할 수 있다. |
| 학습 | 몰랐던 것과 선택한 학습 방법, 적용한 행동과 결과. 교육명·자격·완성 시스템만으로 학습 과정을 대신하지 않는다. |
| 원칙 | 지킬 기준과 이유, 다른 선택도 가능한 상황에서 감수한 불편과 실제 행동. 큰 갈등이나 불이익을 만들지 않는다. |
| 소통·협업 | 서로 달랐던 정보나 의견, 주고받은 내용과 본인의 반응, 그로 인한 이해·행동·합의의 변화. 문서 개수만 성과로 쓰거나 설득 성공을 강제하지 않는다. |
| 개선·문제 해결 | 원래의 불편과 영향, 선택한 대안과 이유, 그 행동으로 달라진 상태. 원인 가설·실패·판단 수정은 실제로 있었을 때 설명한다. |
| 직무 준비·전문성 | 준비한 역량을 실제로 사용한 상황과 행동, 결과, 해당 직무에서 활용할 지점. 과거 수행과 향후 계획을 구분한다. |
| 지원동기·조직관 | 확인된 관심·기준·경험과 기업의 실제 업무 사이의 연결. 회사·직무 선택 이유와 포부를 각각 요구하면 모두 답한다. 회사 칭찬·장기근속 의지·전환 계기를 강제하지 않는다. |
| AI 활용 | 어떤 문제를 해결하려 AI에 무슨 일을 맡겼는지, 제공한 자료·작업 범위와 AI의 산출물, 본인이 판단·수정·확인한 일과 결과. 단순 질의응답이나 AI와 무관한 자동화를 근거로 포장하지 않는다. |

## 짧은 설명에서 초안으로

경험형은 기존 `writing_brief` 필드를 이어 읽었을 때 **해결할 문제 → 확인하거나 결정해야 했던 사항 → 이를 위한 행동 → 그 문제에 답하는 결과**가 이해되게 쓴다. 각 칸을 독립적인 경력 요약으로 채우지 않는다.

- `context`: 서비스·활동의 용도와 필요한 처리 대상을 먼저 알 수 있게 하고, 당시 수준과 해결할 문제·제약을 설명한다. 원본을 모르면 알 수 없는 배경만 필요한 만큼 남긴다.
- `judgment_action`: 무엇을 알아보거나 바꾸기 위해 어떤 행동을 했는지 설명한다. 확인된 선택 이유를 포함한다.
- `outcome`: 그 행동으로 앞의 문제에 대해 무엇을 확인하거나 해결했는지 설명한다. 시험 완료 자체를 목표 달성으로 대신하지 않는다.

이 짧은 설명이 성립한 뒤 필요한 근거로 본문을 확장한다. 별도의 장문 설계나 내부 문답 전체를 추가하지 않는다. 가치관·향후 계획처럼 경험이 필요 없는 문항은 직접 답변과 그 근거를 설명하며 사건·실험·성과를 만들지 않는다.

행동을 넣을 때는 **앞의 어떤 문제 때문에 필요한 행동인지**, 결과를 넣을 때는 **앞의 어떤 의문에 답하는 결과인지** 확인한다. 원본에는 근거가 있지만 본문에 연결이 빠졌다면 설명을 보완한다. 원본에도 없으면 맥락을 상식으로 지어내지 않는다. 같은 소재에 함께 기록되거나 앞뒤로 나열된 사건도 원인·반박·합의의 관계가 확인된 것은 아니다. 개별 사실과 사건 사이의 관계를 구분해 근거를 확인하고, 관계가 불분명하면 확인된 흐름을 선택하거나 별개의 논의로 설명한다. 근거가 부족할 때의 자료 확인과 사용자 질문은 작성 흐름을 따른다.

예를 들어 목표가 여러 작업을 한 서버에서 실행하는 것이라면, 부하 시험은 동시에 실행해도 감당하는지 확인할 필요가 있어서 등장해야 한다. 시험 도구에 문제가 생긴 과정은 그 확인을 어떻게 가능하게 했는지를 설명할 때만 남긴다. 결과는 어떤 동시 작업이 어떤 조건에서 동작했는지에 답해야 한다. 이는 가상 연결 예시이며 실제 목표·시험 목적은 원본으로 확인한다.

## 사례와 세부사항 선택

- 두 사례를 함께 쓰려면 각각 핵심 주장이나 서로 다른 필수 하위 질문에 직접 기여해야 한다. AI·자동화·운영이라는 공통 단어만으로 묶지 않는다. 추가 사례를 빼면 어떤 답이나 근거가 부족해지는지 확인하고, 이미 충분하면 덜어낸다. 사례를 유지하려고 처음 정한 주장을 넓히거나 사용자 강조점을 바꾸지 않는다. 'AI를 활용한 자동화'라는 주장에는 실제 AI 활용의 근거가 필요하다. 서로 다른 준비 역량이 필요한 문항이라면 각 사례의 역할을 설명한다.
- 여러 문항을 쓰기 전 각 답변이 추가로 보여줄 역량·판단을 비교한다. 작성 후에도 실제 본문에서 그 차이가 드러나는지 확인한다. 서로 다른 사건을 써도 모두 시험·검증 성과로 끝나면 학습 방법, 상대 의견에 대한 반응, 기준을 지킨 이유 등 각 문항이 요구한 행동에 설명 비중을 맞춘다. 같은 프로젝트라도 문제·행동·결과가 다르면 사용할 수 있으며, 비중을 조정해도 같은 설명과 성과가 반복되면 다른 적합한 소재와 비교한다. 다양성만을 위해 약한 소재로 바꾸거나 특정 프로젝트를 금지하지 않는다. 중요한 배치 이유만 해당 문항의 `detail_selection`에 남기며 후보 전수 분석이나 사용자 승인을 별도 단계로 만들지 않는다.
- '이 내용을 빼면 문제·선택 이유·본인 기여·결과를 이해하기 어려워지는가?'로 주요 정보의 필요를 판단한다. `detail_selection`에는 중요한 유지·제외 결정과 이유만 적는다. 기술 토큰별로 별도 표를 만들지 않는다.
- 기술명은 역량을 증명할 때 유지하고 역할·대상이 불분명한 표현은 구체화한다. 예를 들어 “계정”이 글을 읽는 프로그램의 실행 계정이라면 그 역할을 밝힌다. 쉬운 말로 바꾼 “묶음”도 무엇을 묶는지 모르면 설명이 아니다. 용어마다 정의를 붙이거나 다른 추상어로 치환하지 않는다.
- 숫자는 관계를 설명할 때 남긴다. 수치를 빼거나 단순화하면서 팀 성과를 개인 성과, 단일 관찰을 평균, 시험 조건을 상시 운영 성능으로 바꾸지 않는다. 상세 측정 조건은 원본에 보존하고 오해를 막는 최소 조건은 관련 결과와 함께 설명한다.
- 수치가 없어도 제거된 반복 작업, 보존한 정보, 합의된 기준이나 독립적으로 바꿀 수 있게 된 범위는 확인 가능한 결과다. 적합한 일상 사례를 더 복잡한 기술 사례로 바꾸지 않는다.
- 분량 제한이 없거나 자료가 많아도 불필요한 구현·시험 이력을 늘리지 않는다. 확장 후에도 처음 정한 주장이 중심인지 확인한다. 고정 분량·문단·사례 수를 목표로 삼지 않는다.

## 내용 검토

작성자는 원본을 이미 알고 있다. 문항과 본문만 평가 대상으로 삼아 다음 순서로 읽고, 설계나 원본에서 알게 된 정보를 본문에 있다고 간주하지 않는다. 특정 도구나 별도 에이전트는 필수가 아니며, 같은 작업의 재독을 독립 검증이라고 보고하지 않는다.

| 순서 | 본문에서 확인할 것 | 문제가 있으면 할 일 |
| --- | --- | --- |
| 방향 | 본문의 실제 행동이 문항에서 요구한 역량·판단을 증명하는가? 사용자 강조점과 맞고 답변 전체에서 같은 주장으로 이어지는가? | 주제만 관련되거나 다른 성과로 중심이 옮겨갔다면 주장·소재 선택부터 고친다. 문장이 자연스럽다는 이유로 적합하다고 인정하지 않는다. |
| 연결 | 각 주요 행동은 앞의 어떤 문제 때문에 필요했는가? 결과는 그 문제에 무엇을 답하는가? | 실제 구절과 빠진 이유를 짚는다. 근거가 있는 목적·관계를 설명하거나 관련 없는 행동을 덜어낸다. |
| 선택 | 사례·수치·구현 이력을 빼면 핵심 답이나 근거가 부족해지는가? | 부족해지는 내용이 없으면 줄인다. 사례나 수치를 유지하기 위해 주장을 넓히지 않는다. 필요한 시험과 복수 사례는 남긴다. |
| 독자 이해 | 서비스·활동의 용도, 행동이 필요한 이유, 주체와 처리 대상이 본문에서 이해되는가? | 빠진 배경과 대상의 관계를 보완한다. 용어 교체 뒤에도 문단 전체를 읽고 같은 정보가 빠져 있지 않은지 확인한다. |

네 항목을 새 체크박스나 장문 보고서로 늘리지 않는다. 기존 `reader_review.summary`에는 본문에서 읽히는 연결을 짧게 재구성하고, `question_fit`에는 **판단에 사용한 실제 본문 구절과 그것이 문항에 답하는 이유**를 남긴다. 요약할 때 본문에 없는 이유·대상·의견 사이의 관계를 보충했는지 확인한다. 보충이 필요했다면 해당 구절과 빠진 설명을 이슈로 남기고, 원본의 관계 근거를 확인해 본문을 고친 뒤 다시 읽는다. 검토 요약만 명료하게 고치거나 문장에 '그래서'가 있다는 이유로 통과시키지 않는다.

발견한 문제의 실제 구절·판단 이유·수정 후 재독 결과를 기존 검토 기록에 남긴다. 등급별 필드와 R번호 연결은 [체크포인트](essay-checkpoints.md)를 따른다. 문제를 발견하지 못했다면 빈 배열이 가능하지만, 설계 문장을 복사한 요약이나 모든 값의 일괄 true 지정은 내용 검토의 근거가 아니다.

수정 후 원본과 사실·역할·성과 범위를 대조한다. 연결을 만들기 위해 근거에 없는 동기·인과관계를 보태지 않는다. 필요한 사실이 없으면 자료를 재확인하고 다른 소재를 검토한 뒤 사용자에게 확인한다. 설명이나 선택 문제를 사용자 소재 수정으로 떠넘기지 않는다. 내용과 사실 검토를 끝낸 뒤 표현·형식·분량을 검사한다.

## 판정과 검토 종료

- **치명:** 핵심 답·본인 기여·인과관계를 이해할 수 없는 누락, 사실 오류·역할 과장, 필수 질문 누락·소재 부적합, 제출 조건 위반. 해결하거나 필요한 사실을 확인하기 전 해당 문항은 valid가 될 수 없다.
- **권장:** 핵심 답은 이해되지만 연결 근거·행동·결과가 약하거나 불필요한 설명이 남아 있음. 현재 자료로 고칠 수 있으면 수정한다. 남은 문제를 취향으로 낮추거나 기록에서 빼지 않는다.
- **선택:** 기본 이해와 문항 충족이 확보된 상태에서의 강조 비중·설명 깊이·어휘·리듬·결론 어조. 문항이 요구하지 않은 별도 교훈·포부 문단도 여기에 해당한다. 사용자가 선택하면 반영하되 의미·사실 범위를 지키고, 미확인 감정이나 동기는 만들지 않는다.

경험의 의미는 아래 기준으로 판단한다. 문항이 직접 요구한 성찰의 누락은 치명이다. 직접 요구하지 않더라도 기술·성과만 나열하거나 일반론만 있으면 권장으로 남기고 최종 후보 전 보완한다. 구체적 판단이나 이해가 드러나면 별도 교훈 문장은 필요 없다.

초안은 사실·역할·필수 질문·기본 맥락과 형식이 확인된 제안이다. 발견한 권장 문제는 현재 자료로 보완하고, 남기면 구절·이유·다음 조치를 명시한다. 초안이라는 이유로 치명 문제를 허용하거나 모든 검토를 통과시키려 권장 문제를 선택 사항으로 낮추지 않는다. 최종 후보는 권장 문제까지 처리한 뒤 제시한다.

발견한 문제는 모두 판정하되 개수를 채우지 않는다. 수정 후에는 해결한 항목뿐 아니라 바뀐 답변 전체의 문항 적합성·맥락·사실 범위를 확인한다. 과거 해결 기록은 현재 본문을 재검토하지 않아도 된다는 근거가 아니다. 기본 요건이 충족되고 남은 결정이 선택 사항이면 초안을 제시하며, 완벽한 표현을 찾기 위한 반복 수정은 하지 않는다. 자동 검사기는 기록의 형식과 모순을 확인하며 글의 설득력을 판정하지 않는다.

## 경험의 의미

경험에서 확인된 판단 변화, 더 분명해진 기준, 이유가 연결된 느낀 점이나 이후 행동은 앞의 사건과 연결한다. 어느 사례에도 붙는 교훈이나 이유 없는 감상으로 대신하지 않는다. 생각의 변화를 강제하지 않으며 당시 판단·사후 이해·이후 행동·앞으로의 계획을 구분한다. JD 연결이나 포부가 경험의 의미를 자동으로 충족하지는 않는다.

문항이 성찰을 직접 요구하면 확인된 사실로 답한다. 요구하지 않았다면 별도 교훈 문장이나 마지막 문장 위치는 강제하지 않는다. 미확인 감정·동기는 만들어 넣지 않는다. 등급과 검토 종료는 위 판정 기준을 따른다.

## 실패 예시

아래는 가상 문장이다. 실제 경험이나 고정 문구로 재사용하지 않는다.

| 문장 | 확인할 문제와 수정 방향 |
| --- | --- |
| '한 서버에서 여러 작업을 실행했습니다. 시험 도구가 종료돼 프로세스를 분리했고 시험을 완료했습니다.' | 시험 목적과 서버 운영 목표의 관계가 없다. 무엇을 확인하려는 시험인지부터 근거로 설명하고 그 질문에 답하는 결과를 선택한다. |
| 'AI로 업무를 자동화했습니다. 블로그 글과 프로그램 배포도 분리했습니다.' | 두 번째 사례에 AI 활용의 근거가 없다. 같은 주장의 근거로 쓰지 않는다. 별도 역량이 문항에 필요한 근거인지 확인하고, 사례를 유지하려고 주장을 넓히지 않는다. |
| '목표 40개 중 20개를 검증하며 높은 목표를 달성했습니다.' | 축소된 목표를 탁월함으로 정당화하지 않는다. 기존 수준·제약·달성 범위를 확인하고 없으면 소재를 바꾸거나 질문한다. |
| '식별자 12개, 출력 16개, 480초 해석에 성공했습니다.' | 수치의 대상·관계·효과를 알 수 없다. 서비스 동작과 관련 결과를 먼저 설명하고 필요한 숫자만 남긴다. |
| '초기 분석은 안전하다고 판단했지만 50초가 삭제됐습니다.' | 누가 어떤 문제를 해결하려 제안한 기준인지, 무엇이 삭제됐는지 빠졌다. 그 배경과 처리 대상을 명시한다. |
| '분류 신뢰도가 높은 문의를 자동 배정하자고 했습니다. 동료는 같은 단어가 여러 부서의 문의에 나온다고 했고, 저는 신뢰도 기준을 철회했습니다.' | 신뢰도 기준과 단어 기준의 관계가 빠져 있다. 각 발언이 사실이어도 하나의 반박 과정으로 볼 근거를 확인해야 한다. 검토 요약에서 그 관계를 만들어 통과시키지 않는다. |
| '갱신에 38초가 걸려 개선했습니다.' | 비교 기준 없는 속도 개선 주장이다. 확인된 변화가 반복 작업 제거라면 그 전후 작업으로 설명한다. |
