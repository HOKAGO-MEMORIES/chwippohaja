# 공고와 연결 서비스

신규 공고를 등록하거나 Drive와 Notion을 갱신할 때 읽는다.

## 공고 확보

- 사용자가 제공한 공식 공고 URL, JD PDF, 이미지와 입력 가이드를 우선한다.
- 최신 공고 정보는 공식 채용 사이트와 기업 자료로 확인한다.
- 마감일은 날짜와 시간, 시간대를 함께 확인한다.
- 문항, 글자 수와 첨부 조건이 공고에 없으면 추측하지 않는다.
- 기업 일반 조사는 지원동기나 기업 이해가 필요한 문항에서만 확장한다.

## 요청 범위에 따른 출처 선택

사용자가 무엇을 확인하려는지에 따라 사이트를 선택한다.

- 공고, JD, 자격요건, 전형과 공식 첨부 조건은 기업 공식 채용 사이트를 우선한다.
- 자소서 문항, 글자 수와 직무별 질문만 필요하면 자소설닷컴의 직무별 문항 화면을 우선한다.
- 지원서의 개인정보, 학력, 경력, 자격, 자소서, 동의와 첨부 항목 전체가 필요할 때만 기업 공식 지원 페이지를 사용한다.
- 자소서 문항의 출처가 충돌하거나 사용자가 공식 검증을 요청한 경우에만 공식 지원 페이지에서 교차 확인한다.

`전체 자소서 문항`은 해당 직무의 자소서 질문을 빠짐없이 확인한다는 의미다. 이를 `지원서 전체 항목`으로 해석하지 않는다. 자소서만 요청한 상태에서 기업 공식 지원 페이지 로그인으로 이동하지 않는다.

로그인이 필요하면 해당 범위에 맞는 사이트에서 사용자가 직접 로그인하게 한다. 지원서 초안 생성, 입력 저장이나 지원 시작 기록이 생길 수 있는 동작은 외부 쓰기로 보고 실행 전에 사용자에게 알린다.

### 수집 경로

공고 분석은 특정 채용 사이트에 종속하지 않는다. 다음 경로를 모두 입력으로 사용할 수 있다.

- 기업 공식 채용 사이트
- 자소설닷컴과 같은 공고 모음 사이트
- 채용 플랫폼
- 학교와 기관의 채용 게시판
- 사용자가 제공한 PDF, 이미지와 텍스트

공고 모음 사이트와 채용 플랫폼은 공고를 발견하고 원문을 확보하는 출발점으로 사용한다. 가능하면 기업 공식 채용 사이트에서 직무, 마감일, 지원 자격, 전형과 첨부 파일을 다시 확인한다. 서로 다른 출처의 내용이 충돌하면 공식 공고를 우선하고 차이를 분석 문서에 남긴다.

페이지 접근이 제한되거나 로그인이 필요하면 우회하지 않는다. 공개된 공식 공고, 사용자가 제공한 화면이나 다운로드 파일로 전환하고 확인하지 못한 항목을 표시한다.

## 산출물 위치 계약

공고 관련 자료를 만들기 전에 산출물 종류와 기준 저장 위치를 확정한다.

| 산출물 | 기준 저장 위치 | Notion 처리 |
| --- | --- | --- |
| 공고 원본과 JD | 기업별 `01_공고_JD` | 실제 Drive URL 연결 |
| 공고 분석 | 기업별 `01_공고_JD/회사명_직무_공고분석.md` | 대응 속성 또는 주요 파일 링크만 연결 |
| 기업 리서치 | 기업별 `01_공고_JD/회사명_기업리서치.md` | 대응 속성이 없으면 주요 파일 링크만 연결 |
| 자소서 문항 | 기업별 `01_공고_JD/회사명_직무_자소서문항.md` | 자소서 문항 파일의 실제 Drive URL만 연결 |
| 공고, 마감과 지원 상태 | Notion 지원 관리 데이터베이스 | 속성으로 관리 |

사용자가 `Notion의 빈 공고를 조사해 달라`고 말해도 이는 대상 목록이 Notion에 있다는 의미이지 조사 본문을 Notion에 저장하라는 의미가 아니다. JD와 자소서 문항은 Drive 문서로 만들고 Notion에는 해당 문서 링크를 연결한다. 사용자가 상세 본문 복사까지 명시적으로 요청한 경우에만 중복 저장할 수 있다.

여러 기업에 일괄 반영하기 전에는 다음 위치 계약을 짧게 확인한다.

```text
Drive에 생성할 문서:
Notion에 생성하거나 갱신할 속성:
Notion 본문에 넣을 내용:
기존 내용 보존 범위:
```

처음 한 건을 반영한 뒤 Drive 파일의 경로와 내용, 실제 Drive URL, Notion의 대응 링크를 다시 읽어 위치 계약과 일치하는지 확인한다. 같은 방식의 일괄 작업은 이 첫 검증이 통과한 뒤 진행한다. 첫 건이 잘못된 위치나 형식이면 나머지 기업으로 확장하지 않는다.

잘못된 위치에 내용을 저장한 사실을 나중에 발견하면 올바른 위치에 복제했다는 이유만으로 정상화가 끝났다고 보고하지 않는다. 잘못된 위치의 기존 내용, 올바른 원본과 링크를 대조하고 삭제 또는 이동 대상은 사용자에게 알린 뒤 처리한다. 외부 페이지 본문 삭제는 별도 요청 또는 승인이 필요하다.

## 산출물 내용 게이트

파일 개수와 폴더 구조는 조사 완료의 근거가 아니다. 각 문서는 실제로 확인한 내용과 출처를 담아야 하며, 템플릿 항목을 반복 `TBD`, `추후 확인`, `공식 사이트 재확인 필요` 같은 문구로 채워 문서 수를 맞추지 않는다.

### 공고 분석

`공고분석.md`를 완료 산출물로 판정하려면 최소한 다음 내용이 있어야 한다.

- 기업, 공고명, 대상 직무와 공고 식별 정보
- 모집 상태, 마감일과 확인일
- 실제 출처에서 확인한 주요 업무
- 실제 출처에서 확인한 자격요건 또는 지원 조건
- 전형이나 필수 첨부 조건 중 확인 가능한 내용
- 각 사실의 출처 URL 또는 보관한 원본

공개 목록에서 회사, 직무와 마감만 확인한 상태라면 `공고 발견`까지 완료된 것이며 `공고 분석 완료`가 아니다. 공식 상세 공고가 없거나 접근할 수 없으면 확인한 범위와 빠진 필수 항목을 적고 `부분 완료`로 분류한다.

### 기업 리서치

`기업리서치.md`는 최소 한 개 이상의 기업 공식 자료를 직접 확인하고, 기업의 실제 사업 또는 서비스와 해당 직무의 관련성을 구분해 기록한 경우에만 완료로 본다.

- 검색 결과 요약이나 채용 플랫폼 소개만 옮기지 않는다.
- `공공기관`, `솔루션 개발`, `성장 가능성`처럼 어느 기업에도 적용되는 문구만으로 채우지 않는다.
- 지원자 접점은 공통자료의 확인된 사실과 대조한 경우에만 쓴다.
- 대조하지 않았다면 근거 없는 장점이나 준비 소재를 만들지 않고 접점 분석을 미수집으로 남긴다.

### 자소서 문항

`자소서문항.md`에는 다음 상태 중 하나를 명확히 기록한다.

- `확인`: 대상 직무의 실제 문항 원문, 문항별 글자 수, 필수 여부 또는 미표시 사실, 출처와 확인일을 기록함
- `준비 중`: 출처 화면이 문항 준비 중이라고 명시함
- `미등록`: 출처 화면에 해당 직무 문항이 등록되지 않았음을 확인함
- `로그인 필요`: 로그인하지 않으면 전체 문항을 볼 수 없음을 확인함
- `접근 제한`: 로그인 후에도 화면 또는 보안 제한으로 확인하지 못함
- `미확인`: 아직 직접 확인하지 않음

`준비 중`, `미등록`, `로그인 필요`, `접근 제한`과 `미확인`은 실제 문항 확보가 아니다. 상태 파일은 만들 수 있지만 `자소서 문항 확인 완료` 수에 포함하지 않는다. 실제 문항을 확인하지 못했으면 문항을 임의로 만들거나 문항별 준비 소재를 작성하지 않는다. 일반적인 프로젝트 후보를 정리할 필요가 있으면 자소서 문항 문서가 아닌 별도의 공통 소재 문서에서 다룬다.

### 일괄 생성 전 표본 검증

여러 기업의 같은 문서를 일괄 생성할 때는 첫 번째 기업의 실제 문서를 열어 다음을 확인한 뒤 나머지 대상으로 확장한다.

- 파일명에 회사와 대상 직무가 포함됐는지
- 기준 폴더와 지원 건 표식이 올바른지
- 문서 상태와 실제 내용이 일치하는지
- 필수 항목이 반복 상태 문구로 대체되지 않았는지
- 출처와 확인일이 실제 확인 내용과 연결되는지

첫 문서가 내용 게이트를 통과하지 못하면 대량 생성을 멈추고 형식이나 수집 범위를 바로잡는다. 이미 여러 파일을 만들었다면 파일 수가 아니라 각 문서의 내용 상태를 전수 집계하며, 비어 있거나 의미 없는 파일을 완료 수에서 제외한다.

## 복수 기업과 공고 탐색

사용자가 여러 기업이나 공고를 한 번에 요청하면 일부 결과를 전체 결과처럼 보고하지 않도록 기업별 작업 상태를 독립적으로 추적한다. 자동 공고 추천 기능을 새로 수행한다는 의미가 아니라, 사용자가 지정한 기업 목록, 링크 묶음 또는 명시한 탐색 범위에 적용하는 실행 기준이다.

### 시작 전 대상 고정

작업을 시작할 때 다음을 먼저 정한다.

- 전체 대상 기업 또는 공고 목록
- 기업별 요청 범위: 공고 발견, 공식 원문 확인, JD 확보, 기업 조사, 파일 생성, Drive 또는 Notion 반영
- 기업별 완료 근거
- 중복 공고와 제외 조건

대상이 많아 한 번에 처리하기 어렵더라도 임의로 일부만 선택하지 않는다. 처리 단위를 나누고 전체 목록에서 이번 묶음과 남은 묶음을 표시한다. 접근하기 쉬운 기업으로 실패한 대상을 바꾸거나 요청한 개수를 맞추기 위한 대체 공고를 추가하지 않는다.

### 기업별 상태와 판정

기업별로 `처리 상태`와 `탐색 결과`를 분리한다.

| 구분 | 값 | 의미 |
| --- | --- | --- |
| 처리 상태 | 완료 | 요청된 범위의 완료 근거를 모두 다시 확인함 |
| 처리 상태 | 부분 완료 | 일부 자료는 확보했지만 필수 항목이나 외부 반영이 남음 |
| 처리 상태 | 실패 | 시도했으나 요청 결과를 만들지 못함 |
| 처리 상태 | 미시도 | 아직 해당 대상을 처리하지 않음 |
| 탐색 결과 | 확인 | 조건에 맞는 공고 또는 공식 자료를 확인함 |
| 탐색 결과 | 없음 | 정한 범위와 출처를 실제로 확인했지만 조건에 맞는 결과가 없었음 |
| 탐색 결과 | 미확인 | 접근 제한, 출처 부족 또는 미시도로 결론을 낼 수 없음 |

`조건에 맞는 공고 없음`은 실패를 감추는 문구로 사용하지 않는다. 확인한 검색 범위, 출처와 기준일이 있을 때만 `탐색 결과: 없음`으로 판정한다. 페이지 접근 실패, 검색 중단이나 결과 미검증은 `미확인`이다.

기업별 완료는 요청 범위에 따라 다음 근거를 직접 확인한 경우에만 인정한다.

- 공고 발견: 회사, 직무, 공고 URL, 모집 상태와 확인일
- 공식 확인: 공식 공고에서 주요 업무, 자격요건과 마감 확인
- JD 확보: 실제 파일 형식, 열림 여부와 대상 직무 일치 확인
- 문서 생성: 대상 경로의 파일을 다시 읽고 필수 항목과 출처 확인
- Drive 또는 Notion 반영: 실제 메타데이터나 페이지 재조회 결과 확인

검색 결과 요약, 도구의 성공 응답, 빈 파일, 계획 문서 또는 파일명만으로 완료를 판정하지 않는다. 공식 자료를 확보하지 못한 채 보조 출처만 사용했다면 해당 한계가 요청의 필수 조건인지 판단해 `부분 완료` 또는 `실패`로 남긴다.

### 실패 처리와 전체 보고

한 기업의 실패가 다른 기업의 안전한 읽기 작업을 막지 않으면 나머지 대상은 계속 처리한다. 인증, 연결 권한 또는 공통 도구 장애처럼 모든 대상에 영향을 주는 문제라면 반복 호출하지 않고 공통 차단 요인과 미시도 대상을 보고한다.

최종 보고에는 다음 집계를 반드시 포함한다.

```text
전체 대상:
완료:
부분 완료:
실패:
미시도:
```

다섯 상태의 대상 목록과 합계가 최초 대상 수와 일치해야 한다. 기업별로 확인 근거, 생성한 파일, 외부 반영 결과와 남은 작업을 적는다. 부분 완료, 실패 또는 미시도가 하나라도 있으면 `전체 완료`, `모두 반영`, `누락 없음`이라고 표현하지 않는다. 대신 완료된 범위와 남은 범위를 분리해 보고한다.

## 전수 목록과 최신 공고 탐색

사용자가 `현재 지원 가능한 공고 전부`, `오늘 올라온 공고`, `새로 추가된 공고`를 요청하면 무엇을 전수 또는 최신으로 판단했는지 재현할 수 있어야 한다.

### 전수 범위 기록

탐색 시작 시 다음 범위를 기록한다.

```text
기준 사이트:
확인 시각과 화면 표시 시간대:
채용 구분과 경력 조건:
선택한 직무 필터:
검색어와 지역 등 추가 필터:
정렬 방식:
전체 결과 또는 페이지 표시값:
실제로 확인한 페이지 범위:
```

`전부 확인`은 다음 조건을 모두 충족할 때만 사용한다.

- 선택한 필터와 정렬이 기록돼 있다.
- 첫 결과부터 마지막 페이지 또는 더 이상 결과가 없다는 사이트 신호까지 확인했다.
- 로딩 실패, 건너뛴 페이지와 확인하지 못한 묶음이 없다.
- 같은 공고의 여러 직무와 중복 게시를 어떤 단위로 합쳤는지 설명할 수 있다.
- 원본 수에서 중복, 제외와 보류를 반영한 최종 수의 산식이 일치한다.

마지막 페이지를 확인하지 못했거나 사이트가 전체 건수를 제공하지 않으면 `확인한 범위 내`로 보고한다. 검색 결과 일부를 보고 사이트 전체 공고를 확인했다고 확대하지 않는다.

### 집계 보존

최종 목록에는 최소한 다음 집계를 남긴다.

```text
원본 결과:
중복 제거:
조건 제외:
보류 또는 미확인:
최종 포함:
산식 검증:
```

제외된 공고는 목록에서 조용히 없애지 않고 제외 기준별 개수와 대표 사유를 남긴다. 혼합 공고에서 일부 직무만 제외했다면 공고 전체 제외와 구분한다. `수시`, `보안`, `필수 어학`, `학위 조건` 같은 필터는 사용자가 정한 의미를 그대로 적용하고 공고명에 단어가 있다는 이유만으로 실제 모집 상태나 조건을 단정하지 않는다.

### 최신성과 변경 판정

동적 목록은 확인 시각의 스냅샷이다. 새 공고를 찾을 때는 현재 화면을 새로 확인하고 이전 목록과 공고 ID 또는 공식 URL을 대조한다.

- 게시일을 출처에서 직접 확인했으면 `오늘 게시` 또는 해당 게시일을 쓸 수 있다.
- 이전 목록에는 없지만 게시일을 확인하지 못했으면 `이번 확인에서 새로 발견`으로 쓴다.
- 기존 공고의 직무, 마감 또는 상태가 바뀌었으면 신규 공고가 아니라 변경 공고로 분류한다.
- 접수 시작 전 공고와 접수 중 공고를 같은 상태로 합치지 않는다.
- 공고명에 `수시채용`이 있어도 별도 마감일과 현재 접수 상태가 있으면 사용자가 정한 수시 제외 기준에 맞는지 실제 내용을 확인한다.

탐색 중 목록이 바뀔 수 있으므로 전체 순회를 마친 뒤 첫 화면이나 전체 건수를 한 번 다시 확인한다. 차이가 있으면 변동 사실과 기준 시각을 남기고 필요한 범위만 보정한다. 계속 새로고침하며 끝없이 추적하지 않는다.

플랫폼 목록만 확인한 단계는 `후보 목록 수집`이다. 각 기업의 공식 자격요건과 마감까지 확인하지 않았다면 `공식 검증 완료`라고 표현하지 않는다. 이후 기업 폴더나 Notion 항목을 만들 때도 후보 수집 상태와 공식 검증 상태를 구분한다.

### 자소설닷컴 입력

자소설닷컴 링크는 공고를 발견하고 공개 정보를 확보하는 입력으로 사용한다. 현재 상세 주소와 이전 공유 주소를 모두 받을 수 있다.

```text
https://jasoseol.com/recruit/105667
https://jasoseol.com/recruit?ec=105667
```

이전 공유 주소에 숫자로 된 `ec` 값이 있으면 그 값을 공고 ID로 읽고 `https://jasoseol.com/recruit/{공고 ID}` 형식의 상세 페이지를 확인한다. 숫자가 없거나 상세 페이지에서 같은 공고임을 확인할 수 없으면 주소를 추측해 만들지 않는다. 사용자가 제공한 주소와 실제로 확인한 상세 주소를 모두 출처에 남긴다.

비로그인 상태에서는 페이지에 공개된 기업명, 공고명, 모집 기간, 모집 직무, 공식 채용 사이트 링크와 상세 요강을 우선 추출한다. 공개 내용이 이미지라면 원본 이미지나 필요한 화면을 보관하고 텍스트 변환 결과를 화면과 대조한다.

자소서 문항은 직무별 보기 화면을 직접 확인한다. 일부 문항만 보이고 전체 문항에 로그인이 필요하면 공개된 내용을 전체 문항처럼 기록하지 않는다. 자소서만 확인하는 작업에서는 사용자가 자소설닷컴에 직접 로그인한 뒤 다시 확인하거나 화면, 파일 또는 복사한 문항을 제공받는다. 비밀번호, 쿠키와 로그인 정보를 요청하거나 저장하지 않고 접근 제한을 우회하지 않는다.

지원자 분석, 채팅, AI 기업 분석과 같은 자소설닷컴 부가 정보는 공식 공고 사실로 취급하지 않는다. 공고 ID, 직무, 마감일, 자격요건, 전형, 첨부 파일과 자소서 입력 조건은 가능하면 연결된 기업 공식 채용 사이트에서 다시 확인한다.

### 원문 보관

확보할 수 있는 원문을 회사의 `01_공고_JD`에 보관한다.

- JD PDF와 채용 안내 첨부 파일
- 공고 화면의 이미지 또는 PDF
- 공고 원문 링크
- 자소서 문항과 입력 안내

자소서 문항만 수집한 경우 `회사명_직무_자소서문항.md`에 대상 직무, 문항 원문, 글자 수, 필수 여부, 출처와 확인일을 기록한다. 필수 여부가 표시되지 않으면 모든 문항을 필수로 추측하지 않는다.

파일을 다운로드할 수 있으면 원본 형식을 보존한다. 다운로드할 수 없는 동적 페이지는 출처 URL과 확인일을 기록하고 필요한 화면만 보관한다. 파일 이름과 확장자를 URL만 보고 추측하지 않는다.

## 기업 리서치

공고를 확보한 뒤 자소서나 지원 전략에 필요한 범위에서 기업을 조사한다. 광고 문구를 모으는 것이 아니라 JD가 요구하는 업무와 지원자의 확인된 경험이 어디에서 만나는지를 찾는 것이 목적이다.

### 출처 우선순위

1. 기업 공식 홈페이지와 채용 페이지
2. 공식 사업보고서, 실적 발표와 IR 자료
3. 기업 공식 보도자료와 기술 블로그
4. 신뢰할 수 있는 언론과 산업 자료

검색 결과의 요약 문구만으로 사실을 확정하지 않는다. 각 주요 사실에는 출처 링크와 확인 기준일을 남긴다. 사실, 기업의 공식 주장과 지원 관점의 해석을 구분한다.

### 조사 항목

- 회사 개요와 주요 사업
- 미션, 핵심 가치와 인재상
- 최근 사업과 기술 동향
- 지원 직무가 속한 조직 또는 서비스
- JD의 주요 업무, 자격요건과 우대사항
- 지원자 경험과의 강한 접점
- 근거가 약한 접점
- 추가 확인이 필요한 내용

접점은 공통자료의 확인된 사실만 사용한다. 기업에 맞추기 위해 사용하지 않은 기술이나 수행하지 않은 역할을 만들지 않는다.

### 산출물

원본과 분석 결과를 분리해 다음처럼 저장한다.

```text
01_공고_JD/
├── 원본 JD 또는 공고 화면
├── 회사명_직무_공고분석.md
└── 회사명_기업리서치.md
```

`회사명_직무_공고분석.md`에는 공고 조건과 직무 요구사항을 저장한다. `회사명_기업리서치.md`에는 기업 공통 정보, 최근 동향, 인재상, 직무와 경험의 연결, 출처와 기준일을 저장한다. 같은 기업의 다른 직무를 추가하면 기존 기업 리서치를 검토해 재사용하되 오래됐거나 직무 관련성이 부족한 항목만 갱신한다.

Notion 페이지는 위 문서의 대체 저장소가 아니다. 같은 내용을 Notion 본문에 먼저 쓰거나 Notion 본문만 채운 상태를 공고 조사 완료로 판정하지 않는다.

## 회사 작업 공간

신규 지원이라면 회사 폴더와 세 하위 폴더를 만든다. 이미 존재하면 현재 구조를 유지한다.

생성 전에는 `scripts/application_workspace.py plan`으로 변경 계획을 확인하고 승인 후 `apply`를 실행한다.

같은 기업 폴더가 이미 있으면 같은 지원 건이라고 가정하지 않는다. 공고 URL, 공고 ID, 직무와 제출 단위를 대조하고 충돌하면 [예외 시나리오](exception-scenarios.md)를 따른다.

공고 원문, JD와 입력 가이드는 `01_공고_JD`에 저장한다. 공고 분석 문서에는 다음 항목을 포함한다.

지원 건 표식 `01_공고_JD/.application.json`에는 `schema_version`, 회사, 관리 직무와 공식 공고 키를 기록한다. 관리 직무와 공고 원문의 세부 직무가 다르면 둘 다 분석 문서에 남긴다.

- 회사와 공고명
- 지원 직무와 세부 직무
- 주요 업무
- 자격요건과 우대사항
- 관련 기술과 전형
- 마감일
- 지원자의 강한 접점, 약한 접점과 확인이 필요한 접점
- 출처 링크

약한 접점을 억지로 맞추거나 사용하지 않은 기술을 경험으로 서술하지 않는다.

## Google Drive

Drive는 파일 보관과 링크의 기준이다.

1. 대상 파일 또는 폴더를 이름과 부모 폴더로 찾는다.
2. 검색 결과가 여러 개면 메타데이터와 현재 로컬 경로를 대조한다.
3. 동기화된 새 파일은 검색 결과나 메타데이터로 존재를 확인한다.
4. 실제로 반환된 URL만 Notion에 저장한다.
5. 기존 파일을 이동할 때는 현재 부모를 확인하고 파일 정체성과 기존 링크를 유지하는 이동 방식을 우선한다.
6. 이동 후 실제 파일 메타데이터와 Notion 링크를 다시 확인한다. 복사 후 원본 삭제로 대체하지 않는다.
7. 업로드, 공유와 삭제 결과는 메타데이터를 다시 읽어 검증한다.

로컬 동기화 폴더의 경로를 공개 설정에 저장하지 않는다. 파일 ID와 계정 이메일도 저장소에 기록하지 않는다.

## Notion

Notion은 공고, 마감일, 지원 단계와 주요 링크의 인덱스다.

기본 속성 의미는 다음과 같다. 실제 속성 이름과 선택지는 데이터 소스를 가져와 확인한다.

| 의미 | 기본 속성 예시 |
| --- | --- |
| 공고 제목 | 공고 |
| 회사 | 회사 |
| 마감 | 마감일 |
| 상태 | 지원 단계 |
| 공고 원문 | 공고 링크 |
| 회사 자료 | 기업 폴더 |
| JD | JD 원본 |
| 기업 조사 | 기업 리서치 |
| 자소서 외 지원서 작업본 | 지원서 작성본 |
| 자소서 작업본 | 자소서 작성본 |
| 실제 제출 지원서 | 최종 제출본 |

새 데이터베이스에는 `지원서 작성본`과 `자소서 작성본`을 서로 다른 URL 속성으로 둔다. 기존 데이터베이스가 `이력서 작성본`을 자소서 외 지원서 작업본의 의미로 사용한다고 확인된 경우에는 그 속성을 대응 항목으로 채택할 수 있다. 별도 이력서 파일만을 뜻하는 속성이라면 지원서 작성본 링크로 덮어쓰지 않는다.

### 생성과 수정

1. 회사명과 공고명으로 기존 항목을 검색한다.
2. 찾은 페이지를 가져와 부모 데이터 소스를 확인한다.
3. 데이터 소스를 가져와 정확한 속성명, 유형과 선택지를 확인한다.
4. 속성만 바꿀 때는 다른 속성을 생략해 보존한다.
5. 본문을 바꿀 때는 현재 내용을 가져온 뒤 가장 작은 정확한 구간만 교체한다.
6. 수정 후 페이지를 다시 가져와 검증한다.

기업 리서치에 대응하는 속성이 없으면 임의로 속성을 추가하지 않는다. 실제 Drive URL을 Notion 본문의 주요 파일 영역에 추가한다.

지원서 전체 모드에서는 채택한 자소서 파일의 실제 Drive URL을 `자소서 작성본`에, 자소서를 제외한 지원서 파일의 실제 Drive URL을 `지원서 작성본` 또는 확인된 대응 속성에 연결한다. 두 링크 중 하나가 아직 만들어지지 않았으면 다른 파일의 URL로 대신 채우지 않는다.

### 상태 기준

- 공고만 확보한 상태는 `지원 예정` 또는 워크스페이스의 대응 값
- 작성 중인 상태는 현재 데이터베이스가 제공하는 적절한 값
- 사용자의 실제 제출 확인 또는 공식 접수 완료 결과가 있는 상태만 `지원 완료`. 지원서 PDF를 제공하지 않는 사이트는 접수 증빙과 미제공 사유를 본문에 기록한다.
- 실제 제출 없이 지원하지 않기로 했거나 마감까지 제출하지 않은 상태는 `지원 안 함`
- 실제 제출 뒤 불합격, 전형 종료 또는 제출 후 철회로 더 진행하지 않는 상태만 `종료`

기존 데이터베이스에 `지원 안 함`이 없으면 현재 스키마와 영향을 확인하고 사용자의 승인을 받아 선택지를 추가한다. `종료`를 미지원 상태의 대체값으로 사용하지 않는다.

Notion 도구를 사용할 수 없거나 권한이 부족하면 같은 호출을 반복하지 않는다. 필요한 반영 내용을 보고하고 연결을 요청한다.

연결이 나중에 복구된 경우의 재처리는 [예외 시나리오](exception-scenarios.md)를 따른다.
