# 공고와 연결 서비스

신규 공고를 등록하거나 Drive와 Notion을 갱신할 때 읽는다.

## 공고 확보

- 사용자가 제공한 공식 공고 URL, JD PDF, 이미지와 입력 가이드를 우선한다.
- 최신 공고 정보는 공식 채용 사이트와 기업 자료로 확인한다.
- 마감일은 날짜와 시간, 시간대를 함께 확인한다.
- 문항, 글자 수와 첨부 조건이 공고에 없으면 추측하지 않는다.
- 기업 일반 조사는 지원동기나 기업 이해가 필요한 문항에서만 확장한다.

## 요청 범위에 따른 출처 선택

사용자가 무엇을 확인하려는지에 따라 사이트를 선택한다.

- 공고, JD, 자격요건, 전형과 공식 첨부 조건은 기업 공식 채용 사이트를 우선한다.
- 자소서 문항, 글자 수와 직무별 질문만 필요하면 자소설닷컴의 직무별 문항 화면을 우선한다.
- 지원서의 개인정보, 학력, 경력, 자격, 자소서, 동의와 첨부 항목 전체가 필요할 때만 기업 공식 지원 페이지를 사용한다.
- 자소서 문항의 출처가 충돌하거나 사용자가 공식 검증을 요청한 경우에만 공식 지원 페이지에서 교차 확인한다.

`전체 자소서 문항`은 해당 직무의 자소서 질문을 빠짐없이 확인한다는 의미다. 이를 `지원서 전체 항목`으로 해석하지 않는다. 자소서만 요청한 상태에서 기업 공식 지원 페이지 로그인으로 이동하지 않는다.

로그인이 필요하면 해당 범위에 맞는 사이트에서 사용자가 직접 로그인하게 한다. 지원서 초안 생성, 입력 저장이나 지원 시작 기록이 생길 수 있는 동작은 외부 쓰기로 보고 실행 전에 사용자에게 알린다.

### 수집 경로

공고 분석은 특정 채용 사이트에 종속하지 않는다. 다음 경로를 모두 입력으로 사용할 수 있다.

- 기업 공식 채용 사이트
- 자소설닷컴과 같은 공고 모음 사이트
- 채용 플랫폼
- 학교와 기관의 채용 게시판
- 사용자가 제공한 PDF, 이미지와 텍스트

공고 모음 사이트와 채용 플랫폼은 공고를 발견하고 원문을 확보하는 출발점으로 사용한다. 가능하면 기업 공식 채용 사이트에서 직무, 마감일, 지원 자격, 전형과 첨부 파일을 다시 확인한다. 서로 다른 출처의 내용이 충돌하면 공식 공고를 우선하고 차이를 분석 문서에 남긴다.

페이지 접근이 제한되거나 로그인이 필요하면 우회하지 않는다. 공개된 공식 공고, 사용자가 제공한 화면이나 다운로드 파일로 전환하고 확인하지 못한 항목을 표시한다.

### 자소설닷컴 입력

자소설닷컴 링크는 공고를 발견하고 공개 정보를 확보하는 입력으로 사용한다. 현재 상세 주소와 이전 공유 주소를 모두 받을 수 있다.

```text
https://jasoseol.com/recruit/105667
https://jasoseol.com/recruit?ec=105667
```

이전 공유 주소에 숫자로 된 `ec` 값이 있으면 그 값을 공고 ID로 읽고 `https://jasoseol.com/recruit/{공고 ID}` 형식의 상세 페이지를 확인한다. 숫자가 없거나 상세 페이지에서 같은 공고임을 확인할 수 없으면 주소를 추측해 만들지 않는다. 사용자가 제공한 주소와 실제로 확인한 상세 주소를 모두 출처에 남긴다.

비로그인 상태에서는 페이지에 공개된 기업명, 공고명, 모집 기간, 모집 직무, 공식 채용 사이트 링크와 상세 요강을 우선 추출한다. 공개 내용이 이미지라면 원본 이미지나 필요한 화면을 보관하고 텍스트 변환 결과를 화면과 대조한다.

자소서 문항은 직무별 보기 화면을 직접 확인한다. 일부 문항만 보이고 전체 문항에 로그인이 필요하면 공개된 내용을 전체 문항처럼 기록하지 않는다. 자소서만 확인하는 작업에서는 사용자가 자소설닷컴에 직접 로그인한 뒤 다시 확인하거나 화면, 파일 또는 복사한 문항을 제공받는다. 비밀번호, 쿠키와 로그인 정보를 요청하거나 저장하지 않고 접근 제한을 우회하지 않는다.

지원자 분석, 채팅, AI 기업 분석과 같은 자소설닷컴 부가 정보는 공식 공고 사실로 취급하지 않는다. 공고 ID, 직무, 마감일, 자격요건, 전형, 첨부 파일과 자소서 입력 조건은 가능하면 연결된 기업 공식 채용 사이트에서 다시 확인한다.

### 원문 보관

확보할 수 있는 원문을 회사의 `01_공고_JD`에 보관한다.

- JD PDF와 채용 안내 첨부 파일
- 공고 화면의 이미지 또는 PDF
- 공고 원문 링크
- 자소서 문항과 입력 안내

자소서 문항만 수집한 경우 `회사명_직무_자소서문항.md`에 대상 직무, 문항 원문, 글자 수, 필수 여부, 출처와 확인일을 기록한다. 필수 여부가 표시되지 않으면 모든 문항을 필수로 추측하지 않는다.

파일을 다운로드할 수 있으면 원본 형식을 보존한다. 다운로드할 수 없는 동적 페이지는 출처 URL과 확인일을 기록하고 필요한 화면만 보관한다. 파일 이름과 확장자를 URL만 보고 추측하지 않는다.

## 기업 리서치

공고를 확보한 뒤 자소서나 지원 전략에 필요한 범위에서 기업을 조사한다. 광고 문구를 모으는 것이 아니라 JD가 요구하는 업무와 지원자의 확인된 경험이 어디에서 만나는지를 찾는 것이 목적이다.

### 출처 우선순위

1. 기업 공식 홈페이지와 채용 페이지
2. 공식 사업보고서, 실적 발표와 IR 자료
3. 기업 공식 보도자료와 기술 블로그
4. 신뢰할 수 있는 언론과 산업 자료

검색 결과의 요약 문구만으로 사실을 확정하지 않는다. 각 주요 사실에는 출처 링크와 확인 기준일을 남긴다. 사실, 기업의 공식 주장과 지원 관점의 해석을 구분한다.

### 조사 항목

- 회사 개요와 주요 사업
- 미션, 핵심 가치와 인재상
- 최근 사업과 기술 동향
- 지원 직무가 속한 조직 또는 서비스
- JD의 주요 업무, 자격요건과 우대사항
- 지원자 경험과의 강한 접점
- 근거가 약한 접점
- 추가 확인이 필요한 내용

접점은 공통자료의 확인된 사실만 사용한다. 기업에 맞추기 위해 사용하지 않은 기술이나 수행하지 않은 역할을 만들지 않는다.

### 산출물

원본과 분석 결과를 분리해 다음처럼 저장한다.

```text
01_공고_JD/
├── 원본 JD 또는 공고 화면
├── 회사명_직무_공고분석.md
└── 회사명_기업리서치.md
```

`회사명_직무_공고분석.md`에는 공고 조건과 직무 요구사항을 저장한다. `회사명_기업리서치.md`에는 기업 공통 정보, 최근 동향, 인재상, 직무와 경험의 연결, 출처와 기준일을 저장한다. 같은 기업의 다른 직무를 추가하면 기존 기업 리서치를 검토해 재사용하되 오래됐거나 직무 관련성이 부족한 항목만 갱신한다.

## 회사 작업 공간

신규 지원이라면 회사 폴더와 세 하위 폴더를 만든다. 이미 존재하면 현재 구조를 유지한다.

생성 전에는 `scripts/application_workspace.py plan`으로 변경 계획을 확인하고 승인 후 `apply`를 실행한다.

같은 기업 폴더가 이미 있으면 같은 지원 건이라고 가정하지 않는다. 공고 URL, 공고 ID, 직무와 제출 단위를 대조하고 충돌하면 [예외 시나리오](exception-scenarios.md)를 따른다.

공고 원문, JD와 입력 가이드는 `01_공고_JD`에 저장한다. 공고 분석 문서에는 다음 항목을 포함한다.

지원 건 표식 `01_공고_JD/.application.json`에는 `schema_version`, 회사, 관리 직무와 공식 공고 키를 기록한다. 관리 직무와 공고 원문의 세부 직무가 다르면 둘 다 분석 문서에 남긴다.

- 회사와 공고명
- 지원 직무와 세부 직무
- 주요 업무
- 자격요건과 우대사항
- 관련 기술과 전형
- 마감일
- 지원자의 강한 접점, 약한 접점과 확인이 필요한 접점
- 출처 링크

약한 접점을 억지로 맞추거나 사용하지 않은 기술을 경험으로 서술하지 않는다.

## Google Drive

Drive는 파일 보관과 링크의 기준이다.

1. 대상 파일 또는 폴더를 이름과 부모 폴더로 찾는다.
2. 검색 결과가 여러 개면 메타데이터와 현재 로컬 경로를 대조한다.
3. 동기화된 새 파일은 검색 결과나 메타데이터로 존재를 확인한다.
4. 실제로 반환된 URL만 Notion에 저장한다.
5. 기존 파일을 이동할 때는 현재 부모를 확인하고 파일 정체성과 기존 링크를 유지하는 이동 방식을 우선한다.
6. 이동 후 실제 파일 메타데이터와 Notion 링크를 다시 확인한다. 복사 후 원본 삭제로 대체하지 않는다.
7. 업로드, 공유와 삭제 결과는 메타데이터를 다시 읽어 검증한다.

로컬 동기화 폴더의 경로를 공개 설정에 저장하지 않는다. 파일 ID와 계정 이메일도 저장소에 기록하지 않는다.

## Notion

Notion은 공고, 마감일, 지원 단계와 주요 링크의 인덱스다.

기본 속성 의미는 다음과 같다. 실제 속성 이름과 선택지는 데이터 소스를 가져와 확인한다.

| 의미 | 기본 속성 예시 |
| --- | --- |
| 공고 제목 | 공고 |
| 회사 | 회사 |
| 마감 | 마감일 |
| 상태 | 지원 단계 |
| 공고 원문 | 공고 링크 |
| 회사 자료 | 기업 폴더 |
| JD | JD 원본 |
| 기업 조사 | 기업 리서치 |
| 자소서 외 지원서 작업본 | 지원서 작성본 |
| 자소서 작업본 | 자소서 작성본 |
| 실제 제출 지원서 | 최종 제출본 |

새 데이터베이스에는 `지원서 작성본`과 `자소서 작성본`을 서로 다른 URL 속성으로 둔다. 기존 데이터베이스가 `이력서 작성본`을 자소서 외 지원서 작업본의 의미로 사용한다고 확인된 경우에는 그 속성을 대응 항목으로 채택할 수 있다. 별도 이력서 파일만을 뜻하는 속성이라면 지원서 작성본 링크로 덮어쓰지 않는다.

### 생성과 수정

1. 회사명과 공고명으로 기존 항목을 검색한다.
2. 찾은 페이지를 가져와 부모 데이터 소스를 확인한다.
3. 데이터 소스를 가져와 정확한 속성명, 유형과 선택지를 확인한다.
4. 속성만 바꿀 때는 다른 속성을 생략해 보존한다.
5. 본문을 바꿀 때는 현재 내용을 가져온 뒤 가장 작은 정확한 구간만 교체한다.
6. 수정 후 페이지를 다시 가져와 검증한다.

기업 리서치에 대응하는 속성이 없으면 임의로 속성을 추가하지 않는다. 실제 Drive URL을 Notion 본문의 주요 파일 영역에 추가한다.

지원서 전체 모드에서는 채택한 자소서 파일의 실제 Drive URL을 `자소서 작성본`에, 자소서를 제외한 지원서 파일의 실제 Drive URL을 `지원서 작성본` 또는 확인된 대응 속성에 연결한다. 두 링크 중 하나가 아직 만들어지지 않았으면 다른 파일의 URL로 대신 채우지 않는다.

### 상태 기준

- 공고만 확보한 상태는 `지원 예정` 또는 워크스페이스의 대응 값
- 작성 중인 상태는 현재 데이터베이스가 제공하는 적절한 값
- 사용자의 실제 제출 확인 또는 공식 접수 완료 결과가 있는 상태만 `지원 완료`. 지원서 PDF를 제공하지 않는 사이트는 접수 증빙과 미제공 사유를 본문에 기록한다.

Notion 도구를 사용할 수 없거나 권한이 부족하면 같은 호출을 반복하지 않는다. 필요한 반영 내용을 보고하고 연결을 요청한다.

연결이 나중에 복구된 경우의 재처리는 [예외 시나리오](exception-scenarios.md)를 따른다.
