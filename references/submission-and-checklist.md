# 제출과 최종 점검

최종 문안과 실제 제출 파일을 정리할 때 읽는다.

## 제출 전 점검

### 사실

- [ ] 개인정보, 기간과 학력이 원본과 일치한다.
- [ ] 프로젝트 역할과 팀 성과가 구분된다.
- [ ] 수치, 단위와 측정 조건이 일치한다.
- [ ] 확인되지 않은 주장과 기술 경험이 없다.

### 문항

- [ ] 모든 하위 질문에 답했다.
- [ ] 지원 화면이 허용하는 경우 답변 첫 줄에 본문을 대표하는 `[핵심 요약 문구]`가 하나 있다.
- [ ] 첫 문장이나 첫 문단에서 핵심 답변이 드러난다.
- [ ] JD 연결이 실제 업무 범위와 맞는다.
- [ ] 기술 이름보다 필요, 행동과 검증이 드러난다.
- [ ] 사용자가 선택한 소재와 강조 순서를 유지했다.
- [ ] 같은 프로젝트를 재사용했다면 서로 다른 문제와 행동을 보여준다.

### 표현

- [ ] 문항별 글자 수를 실제로 계산했다.
- [ ] 대괄호 핵심 요약과 실제 입력하는 소제목을 글자 수에 포함했다.
- [ ] 연결어미 뒤 불필요한 쉼표가 없다.
- [ ] 같은 종결어미가 지나치게 반복되지 않는다.
- [ ] 불필요한 `저는`과 연결 표현이 반복되지 않는다.
- [ ] 의미 없는 포부와 미사여구로 글자 수를 채우지 않았다.
- [ ] 특수문자와 줄바꿈을 지원 화면에서 확인했다.
- [ ] 윤문 후 고유명사와 수치를 다시 대조했다.

### 첨부

- [ ] 필수 증빙이 준비됐다.
- [ ] 유효기간과 파일 페이지를 확인했다.
- [ ] 민감서류는 요구된 범위만 포함한다.

## 제출 권한

사용자가 초안 작성이나 검토만 요청했다면 실제 지원 폼을 제출하지 않는다. 사용자가 제출을 직접 완료했거나 명시적으로 제출 작업을 요청한 경우에만 제출 단계로 진행한다.

브라우저 자동화로 제출하는 경우 마지막 제출 버튼처럼 되돌리기 어려운 동작은 대상 공고와 최종 내용을 확인하고 사용자의 명시적 지시 범위 안에서 수행한다.

## 제출 이후 자료 확보

사용자가 제출 완료를 알렸거나 스킬이 명시적으로 승인된 제출을 완료하면 곧바로 제출 결과 확보 단계로 이어간다. 사용자가 파일 확보 방법을 따로 지정하지 않아도 공식 기능을 먼저 확인한다.

다음 순서로 진행하며 앞 단계에서 충분한 자료를 확보하면 불필요한 다음 단계를 반복하지 않는다.

1. 공식 지원 페이지의 `지원서 다운로드`, `지원서 출력`, `제출 내용 보기`와 접수증 기능을 찾는다.
2. 다운로드 가능한 실제 제출 지원서가 있으면 원본 PDF를 받는다.
3. 다운로드는 없지만 제출 내용 전체를 보여주는 공식 인쇄 화면이 있으면 현재 인증된 세션에서 PDF로 저장한다.
4. 지원서 본문을 제공하지 않으면 접수번호, 제출 시각, 지원 직무와 완료 상태가 보이는 접수증 또는 완료 화면을 PDF나 이미지로 확보한다.
5. 브라우저 기능이 운영체제 인쇄 대화상자를 다루지 못하면 현재 환경에 앱 UI 제어 기능이 있는지 한 번 확인한다. 현재 Codex 앱이나 인쇄 시트 접근이 차단됐으면 같은 자동화를 반복하지 않는다.
6. 자동 저장이 막히면 운영체제에 맞는 인쇄 단축키, 전체 페이지 선택, PDF 저장 방식, 정확한 대상 폴더와 파일명을 사용자에게 한 번에 안내한다.
7. 사용자가 저장 완료를 알리면 새 파일 탐색, 이름과 위치 정리, PDF 검증부터 작업을 재개한다.

로그인이 풀렸으면 사용자가 다시 로그인하도록 요청하고 비밀번호, 쿠키나 세션 값을 받지 않는다. 다운로드 제한을 우회하거나 비공개 API를 추측하지 않는다. 사용자가 제출했다고 말한 뒤 별도의 장기 모니터링을 시작하지 않는다.

### 자료 판정

- 공식 페이지에서 제출 후 내려받은 지원서나 제출 내용 전체를 인쇄한 PDF만 `실제 제출 지원서`로 판정한다.
- 제출 전에 만든 Markdown, 미리보기, 입력용 초안과 로컬에서 합성한 문서는 실제 제출 지원서가 아니다.
- 접수증과 완료 화면은 제출 사실의 증빙이지만 지원서 본문을 담지 않았다면 `실제 제출 지원서`로 부르지 않는다.
- 확보한 자료에서 회사, 직무, 접수 상태와 제출 시각을 확인한다. 지원서 PDF라면 자소서와 주요 입력값이 최종 작성본과 일치하는지도 가능한 범위에서 대조한다.
- 파일 이름은 회사, 직무, 자료 종류와 제출일을 구분할 수 있게 정하고 재제출 자료를 덮어쓰지 않는다.

### 자동 확보가 불가능한 경우

사용자가 직접 저장한 PDF나 접수증을 `99_최종제출`에 넣으면 파일의 출처와 실제 제출본 여부를 확인한 뒤 이어서 처리한다. 사이트가 지원서 PDF를 제공하지 않으면 접수 증빙을 보관하고 Notion 본문에 `공식 지원서 PDF 미제공`과 확인 근거를 남긴다. 접수증을 지원서 PDF로 바꾸어 부르거나 `최종 제출본` 링크에 대신 연결하지 않는다.

#### 수동 인쇄 인계

- macOS에서는 `⌘P`, Windows에서는 `Ctrl+P`를 안내하되 현재 운영체제를 먼저 확인한다.
- 인쇄 범위는 전체 페이지로 지정하고, 공식 `지원서 보기` 또는 같은 의미의 제출 내용 전체 화면에서 인쇄하게 한다.
- 회사, 직무, 자료 종류와 제출일을 포함한 목표 파일명과 `99_최종제출` 경로를 정확히 제시한다.
- 네이티브 인쇄 시트가 앱 접근 제한으로 차단됐으면 다른 UI 도구로 반복 시도하지 않고 사용자의 최소 조작으로 인계한다.
- 사용자가 저장을 마치면 파일을 다시 첨부하라고 요구하기 전에 워크스페이스와 사용자가 알려준 위치에서 새 PDF를 찾는다.

#### 수동 저장 파일 정리

브라우저 제목을 사용한 이름으로 시즌 폴더나 사용자가 지정한 위치에 저장될 수 있다. 새 PDF를 찾을 때는 파일명만 믿지 않고 저장 시각, PDF 형식과 대상 지원 건을 대조한다.

- 후보가 하나이고 대상이 명확하면 `99_최종제출`로 이동하면서 표준 이름으로 바꾼다.
- 같은 대상 이름이 이미 있으면 덮어쓰지 않고 `_v2`처럼 구분한다.
- 후보가 여러 개이거나 다른 지원 건일 가능성이 있으면 이동하지 않고 사용자에게 정확한 파일을 선택하게 한다.
- 이동 후 원래 위치에 중복 파일이 남지 않았고 대상 경로에 실제 PDF가 있는지 확인한다.

#### PDF 전용 검증

일반 파일 식별 명령이 표시하는 페이지 수는 최종 판정으로 사용하지 않는다. PDF 전용 기능이나 파서를 기준으로 다음을 확인한다.

- 실제 PDF 형식, 파일 크기와 페이지 수
- 첫 페이지와 마지막 페이지 렌더링
- 빈 페이지, 잘린 영역과 누락된 지원서 구역
- 회사, 직무와 제출 상태
- 가능한 범위에서 채택한 자소서와 주요 입력값의 일치 여부

개인정보와 지원서 전문은 보고에 복사하지 않는다. 로컬 검증 뒤 Google Drive의 실제 파일명과 크기를 대조하고 메타데이터에서 URL을 가져온다.

## 최종 제출 폴더

`99_최종제출`에는 실제로 제출한 파일과 공식 제출 결과를 증명하는 자료만 둔다.

- 실제 제출 지원서 PDF
- 기업이 제출받은 이력서나 포트폴리오 파일
- 기업에 실제로 제출한 증빙 사본
- 사용자가 보존을 요청한 정확한 제출 문안
- 공식 접수증 또는 접수 완료 화면

작성 중 초안이나 윤문 후보를 최종 제출 파일로 분류하지 않는다. 재제출하면 기존 파일을 덮어쓰지 않고 `_v2`처럼 구분한다.

증빙 원본은 상위 증빙서류에 보존한다. `99_최종제출`에는 실제 제출한 사본만 둘 수 있으며 상위 원본을 이동하거나 수정하지 않는다.

## Notion 링크 의미

- `지원서 작성본`: 자소서를 제외한 기본정보, 학력, 경험, 자격, 첨부 조건과 입력값을 정리한 최신 작업 파일을 연결한다.
- `자소서 작성본`: 사용자가 채택한 최신 자소서 작성 파일을 연결한다.
- `최종 제출본`: 실제 제출 지원서 PDF를 연결한다.

기존 데이터베이스의 `이력서 작성본`을 지원서 작성본과 같은 의미로 사용한다고 확인된 경우에는 그 속성에 자소서 외 지원서 작성본을 연결할 수 있다. 별도 이력서 전용 의미라면 실제 이력서 작업 파일만 연결하고, 지원서 작성본은 Notion 본문이나 별도 승인된 속성에 연결한다.

자소서 Markdown만 존재하면 이를 `최종 제출본`으로 연결하지 않는다.

공식 지원서 PDF가 없으면 `최종 제출본`은 비워 둔다. 접수 증빙 전용 속성이 있으면 실제 Drive URL을 그 속성에 연결하고, 없으면 Notion 본문의 제출 기록에 접수 증빙 링크, 제출일과 PDF 미제공 사실을 기록한다.

사용자가 채택한 자소서 작성본을 연결할 때 데이터베이스에 정확한 `작성 중` 상태가 없으면 새 선택지를 임의로 추가하지 않는다. 가장 가까운 기존 상태를 유지하고 필요한 경우 본문에 실제 작성 상태를 기록한다.

## 마감 처리

1. 사용자의 제출 확인 또는 공식 접수 완료 결과를 확인한다.
2. 공식 지원서 PDF를 우선 확보하고, 없으면 접수증이나 완료 화면을 확보한다.
3. 확보한 파일이 회사의 `99_최종제출`에 있고 자료 종류가 올바르게 구분됐는지 확인한다.
4. PDF 전용 기능으로 페이지와 렌더링을 검증하고, Drive에서 동일 파일명과 크기의 실제 URL 및 부모 폴더를 확인한다.
5. 실제 제출 지원서 PDF가 있으면 Notion의 `최종 제출본`을 그 URL로 갱신한다. 없으면 비워 두고 본문에 사유와 접수 증빙을 기록한다.
6. 실제 제출이 확인됐으면 지원 단계를 `지원 완료`로 갱신한다. 파일이 있다는 이유만으로 상태를 바꾸지 않는다.
7. Notion 페이지를 다시 가져와 상태, 속성과 본문 링크를 검증한다.
8. 제출일, 확보한 자료, PDF 제공 여부와 후속 전형을 보고한다.

실제 제출 확인이 없으면 지원 완료로 바꾸지 않는다. 사용자가 제출을 확인했지만 공식 증빙을 전혀 확보할 수 없는 경우에는 그 사실을 Notion 본문에 남기고 완료 상태를 적용할 수 있다. 이 경우 증빙이 없는 점을 결과 보고에서 분명히 알린다.

공고 종료, 지원 보류, 재지원과 Notion 상태 충돌은 [예외 시나리오](exception-scenarios.md)의 상태 우선순위를 따른다.
