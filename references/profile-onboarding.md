# 정보 온보딩

환경 설정이 끝났지만 개인 사실이 비어 있거나, 이력서와 자소서 작성에 필요한 사실이 부족할 때 읽는다.

## 상태

`.chwippohaja/workspace.json`의 `profile_status`는 개인 자료의 내용이 아니라 준비 상태만 나타낸다.

| 상태 | 의미 |
| --- | --- |
| `empty` | 확인된 개인 사실을 아직 모으지 않았다. |
| `in_progress` | 일부 사실을 확인해 공통자료에 정리하고 있다. |
| `ready` | 사용자가 현재 지원 작업에 필요한 사실이 충분하다고 확인했다. |

`ready`는 모든 경력이 영구적으로 완성됐다는 뜻이 아니다. 새로운 지원서에서 추가 사실이 필요하면 해당 부분만 다시 확인한다.

상태 확인과 변경에는 스킬 루트의 도구를 사용한다.

```bash
python scripts/workspace_setup.py profile-status --root "워크스페이스 경로"
python scripts/workspace_setup.py profile-status --root "워크스페이스 경로" --set in_progress
```

사용자가 현재 지원 작업에 필요한 사실 준비가 끝났다고 명시적으로 확인한 뒤에만 `ready`로 바꾼다. 파일이 있다는 이유만으로 자동 판정하지 않는다.

## 시작 선택

환경 설정을 마치면 다음 세 가지 중 하나를 선택하게 한다.

1. 기존 이력서 또는 포트폴리오 가져오기
2. 질문에 답하며 처음부터 정리하기
3. 지금은 건너뛰고 공고부터 등록하기

한 번에 많은 질문을 보여주지 않는다. 이미 대화나 사용자가 지정한 자료에서 확인된 내용은 다시 묻지 않는다.

## 기존 자료 가져오기

사용자가 명시적으로 선택한 파일이나 페이지에 한해 읽는다.

- 로컬 파일 또는 Google Drive 동기화 폴더의 이력서, 포트폴리오와 경력 정리 문서
- 연결된 Google Drive에서 사용자가 선택한 파일
- 연결된 Notion에서 사용자가 선택한 페이지

취업 폴더 밖의 개인 파일 전체를 탐색하지 않는다. 연결 서비스가 보인다는 이유만으로 문서를 임의로 검색하거나 가져오지 않는다.

1. 선택된 자료에서 학력, 교육, 경력, 활동, 프로젝트, 기술, 자격, 어학과 수상 후보를 추출한다.
2. 출처가 서로 다른 내용이 충돌하면 하나를 선택하지 않고 차이를 보여준다.
3. 기간, 역할, 수치와 기술 사용 근거가 불명확하면 `TBD` 후보로 표시한다.
4. 추출 결과를 항목별로 사용자에게 보여주고 확인받는다.
5. 확인된 사실만 `공통자료/경력_프로젝트_소재.md`에 반영한다.

검토 중인 후보는 대화나 임시 검토 결과로만 유지한다. 확인 전에는 공통자료에 쓰지 않는다.

## 지원서 공통정보

여러 회사의 지원서에 반복해서 입력하는 확인된 사실은 `공통자료/지원서_공통정보.md`에 분리해 관리할 수 있다. 기존 공통자료에 같은 목적의 문서나 구분된 섹션이 있으면 새 파일을 강제하지 않고 그 구조를 채택한다.

지원서 공통정보에는 다음처럼 회사와 무관하게 재사용할 수 있는 사실만 둔다.

- 한글, 한자와 영문 이름처럼 사용자가 저장을 선택한 기본 표기
- 학력, 전공, 학점과 재학기간
- 교육, 경험, 경력과 활동기간
- 자격, 어학과 수상
- 반복해서 사용하는 포트폴리오 후보와 증빙 파일 위치
- 취미, 특기와 입사가능일처럼 사용자가 공통값으로 확정한 항목

연락처, 생년월일, 상세 주소, 등록번호, 보훈, 장애, 계좌와 인증 정보는 공통자료에 저장하지 않는다. 지원서 작성본에서는 필드 존재만 남기고 `사용자 직접 입력`으로 표시한다.

공통정보의 각 사실은 가능하면 근거 문서나 확인일을 함께 기록한다. 성적, 자격 유효기간과 파일 위치처럼 바뀔 수 있는 정보는 새 지원서 작성 전에 근거를 다시 확인한다.

특정 회사, 직무, JD, 지원동기, 문항별 답변, 글자 수 제한과 회사별 포트폴리오 선택은 공통정보가 아니다. 회사별 `02_작성중` 문서에서만 관리한다.

## 질문으로 정리하기

다음 순서로 한 영역씩 진행한다.

1. 학력과 교육
2. 경력과 주요 활동
3. 프로젝트 목록
4. 선택한 프로젝트에서 맡은 역할과 결과
5. 기술과 그 기술을 사용한 근거
6. 자격, 어학과 수상

연락처, 상세 주소와 같은 민감하거나 자주 바뀌는 정보는 실제 지원서에 필요할 때 별도로 확인한다. 정보 온보딩의 첫 질문으로 요구하지 않는다.

프로젝트는 처음부터 긴 회고를 요구하지 않는다. 우선 다음 다섯 항목만 모은다.

- 프로젝트명
- 기간
- 한 줄 설명
- 본인 역할
- 확인 가능한 결과

특정 공고의 소재로 선택되면 문제, 제약, 판단, 구현, 협업, 검증과 근거 자료를 추가로 묻는다.

각 영역에서 확인된 사실을 반영하기 시작할 때 `in_progress`로 바꾼다. 사용자가 답변을 보류한 항목은 비워 두거나 `TBD`로 남긴다.

## 건너뛰기

사용자가 정보 온보딩을 건너뛰면 `profile_status`를 억지로 바꾸지 않는다.

- 공고 저장, JD 분석, 회사 폴더 생성과 Notion 공고 관리는 계속할 수 있다.
- 이력서, 지원서 입력값과 자소서처럼 개인 사실이 필요한 작업은 필요한 사실을 먼저 확인해야 한다.
- 사실이 부족한 상태에서 일반적인 문구나 가상의 성과로 채우지 않는다.

## 완료 확인

- 사용자가 지정하지 않은 개인 자료를 탐색하지 않았다.
- 출처에서 추출한 후보와 사용자가 확인한 사실을 구분했다.
- 확인된 사실만 공통자료에 있다.
- 지원서 공통정보를 만들었다면 민감정보와 회사별 내용이 포함되지 않았고 기존 동등 문서를 중복 생성하지 않았다.
- 기업명, JD 해석, 지원동기와 글자 수 조건이 공통자료에 들어가지 않았다.
- 사용자가 현재 작업에 필요한 사실이 충분하다고 확인했을 때만 상태가 `ready`다.
