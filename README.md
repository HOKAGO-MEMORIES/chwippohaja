# 취뽀하자

한국 취업 지원을 공고 등록부터 최종 제출 자료 정리까지 이어서 관리하는 에이전트 스킬입니다. Codex와 Claude Code에서 같은 폴더를 그대로 사용합니다.

로컬 파일은 사실과 작성 원본으로 사용합니다. 워크스페이스는 일반 로컬 폴더와 Google Drive 동기화 폴더 중 하나를 선택할 수 있으며 두 방식 모두 같은 폴더 구조와 작성 흐름을 제공합니다. Google Drive 연결 기능은 동기화된 파일의 링크와 메타데이터를 확인하고, Notion은 공고와 지원 상태의 인덱스로 사용합니다. 계정 ID와 개인 자료를 저장소에 넣지 않고 실행 시점에 현재 워크스페이스와 연결 서비스를 발견합니다.

전체 흐름은 공고 확인과 기업 조사, 자소서 작성, 자소서 외 지원서 작성, 제출 정리, 전형 진행·결과 관리의 다섯 단계로 관리합니다. 자소서가 없는 공고나 사용자가 공식 지원서를 직접 입력하는 경우에는 해당 단계를 건너뛰거나 Markdown 작성본 준비에서 끝낼 수 있습니다.

## 지원 범위

- 공고와 JD 보관
- 공식 자료를 바탕으로 한 기업 리서치
- 기업별 파일을 모두 작성한 뒤 네트워크 없이 한 번 실행하는 1단계 완료 검사
- 여러 기업이나 공고를 한 번에 집계해 일부 대상을 누락한 채 전체 완료로 보고하지 못하게 하는 검사
- JD와 자소서 문항은 Drive에 보관하고 Notion은 상태와 링크 인덱스로 유지하는 위치 검증
- 반복 상태 문구와 근거 없는 준비 소재로 문서 수만 채우지 않는 공고 산출물 내용 검증
- 전수 공고와 신규 공고 탐색에서 필터, 페이지 범위와 포함 및 제외 집계를 남기는 재현 가능한 검증
- 같은 기업의 여러 공고와 공고 변경 이력 관리
- 지원 건 폴더 생성과 작성 번호 계산
- 회사별 작업 폴더 생성
- 지원서 입력 항목과 증빙 정리
- 자소서 소재 수집, 판단 이유 인터뷰, 작성과 검토의 분리, 버전 관리
- 상투 표현과 단조로운 종결을 찾아 주는 표현 검사
- 여러 지원 건의 자소서를 동시에 작업할 수 있는 상태 없는 검사 도구
- 선택적인 `humanize-korean` 윤문
- 기업별 선택형 검토 기록 보관
- Drive 파일 링크 확인
- Notion 지원 단계와 주요 링크 관리
- 실제 제출 지원서와 접수 증빙 확보 및 보관

## 설치

저장소를 사용하는 에이전트의 스킬 폴더에 연결합니다. 하나의 저장소를 두 에이전트에 함께 연결해도 됩니다.

| 에이전트 | 스킬 폴더 | 호출 |
| --- | --- | --- |
| Codex | `~/.agents/skills/chwippohaja` 또는 `~/.codex/skills/chwippohaja` | `$chwippohaja` |
| Claude Code | `~/.claude/skills/chwippohaja` | `/chwippohaja` 또는 요청 내용으로 자동 선택 |

macOS와 Linux:

```bash
git clone https://github.com/HOKAGO-MEMORIES/chwippohaja.git
mkdir -p ~/.codex/skills ~/.claude/skills
ln -s "$(pwd)/chwippohaja" ~/.codex/skills/chwippohaja
ln -s "$(pwd)/chwippohaja" ~/.claude/skills/chwippohaja
```

Windows(PowerShell)에서는 디렉터리 연결을 사용합니다.

```powershell
New-Item -ItemType Junction -Path "$env:USERPROFILE\.codex\skills\chwippohaja" -Target "C:\경로\chwippohaja"
New-Item -ItemType Junction -Path "$env:USERPROFILE\.claude\skills\chwippohaja" -Target "C:\경로\chwippohaja"
```

Claude Code에서 특정 취업 폴더에서만 쓰고 싶다면 그 폴더의 `.claude/skills/chwippohaja`에 연결해도 됩니다. 연결 뒤 새 작업을 시작해야 스킬 목록에 나타납니다.

## 처음 시작

새 작업에서 다음처럼 요청합니다. Claude Code에서는 `$chwippohaja` 대신 `/chwippohaja`를 쓰거나 스킬 이름 없이 요청해도 됩니다.

```text
$chwippohaja로 처음 설정해줘.
```

스킬은 기존 워크스페이스를 먼저 찾습니다. 없으면 다음 항목을 순서대로 선택합니다.

1. 로컬 폴더 또는 Google Drive 동기화 폴더
2. 자동으로 발견한 경로 후보 또는 사용자가 지정한 경로
3. 활성 시즌 이름
4. Google Drive와 Notion 연결 기능 사용 여부

생성 계획을 확인한 뒤 승인하면 공통자료, 증빙서류와 시즌 폴더를 만듭니다. 빈 양식은 스킬 내부에서 사용합니다. 기존 파일은 덮어쓰지 않습니다.

기존 취업 자료를 가져오는 경우에는 기존 폴더와 파일을 보존합니다. 일반 작성 기준과 빈 양식은 현재 스킬 내부 자료를 사용합니다. 가져오기 과정에서는 표식과 필요한 활성 시즌 폴더만 만들며, 표준 폴더나 템플릿을 병렬로 추가하지 않습니다. 새 환경의 기본 증빙 구조는 `학력`, `자격증_어학`, `교육_수상`, `경력_병역`, `사진_서명`, `민감서류`입니다.

환경 설정 뒤에는 개인 사실을 준비하는 방식을 선택합니다.

1. 사용자가 선택한 기존 이력서 또는 포트폴리오에서 가져오기
2. 학력, 경력, 프로젝트와 기술을 한 영역씩 질문하며 정리하기
3. 정보 정리는 건너뛰고 첫 공고부터 등록하기

가져온 내용은 후보로 먼저 보여주며 사용자가 확인한 사실만 공통자료에 기록합니다. 건너뛰어도 공고와 JD 정리는 가능하지만, 이력서와 자소서 작성 전에는 필요한 사실을 확인합니다.

다음처럼 사용합니다.

```text
$chwippohaja로 이 공고를 등록하고 지원 준비를 시작해줘.
$chwippohaja로 기존 회사 자소서 작성 단계부터 이어서 진행해줘.
$chwippohaja로 제출 결과를 확인하고 최종 지원서와 접수 증빙을 확보해 Notion에 반영해줘.
```

작성 범위는 두 가지로 선택할 수 있습니다.

### 자소서만

자소설닷컴의 직무별 화면에서 자소서 문항과 글자 수를 확인한 뒤 네 단계로 진행합니다.

| 단계 | 하는 일 | 기준 문서 |
| --- | --- | --- |
| 설계 | 문항을 하위 질문으로 나누고 문항의 동사를 직접 증명하는 소재를 고릅니다. 키워드만 비슷한 소재는 쓰지 않습니다. | [주장과 문맥](references/essay-composition.md) |
| 인터뷰 | 경험형 문항에 필요한 판단·의미의 근거가 자료에 없으면 사용자에게 묻습니다. 이후 변화는 문항이나 주장에 필요한 경우에만 확인합니다. 이미 확인된 내용은 다시 묻지 않고, 원하지 않으면 건너뜁니다. | [인터뷰](references/essay-interview.md) |
| 작성 | 문장 쓰기 지침과 예시만 보고 본문을 씁니다. 하위 에이전트를 쓸 수 있으면 별도 에이전트에 맡겨 검증 규정이 글에 섞이지 않게 합니다. | [문장 쓰기](references/essay-craft.md), [예시](assets/examples/) |
| 검토 | 본문의 네 기준, 사실 대조와 읽는 사람 점검 후 본문 사전 검사를 합니다. 실제 결과를 기록하고 최종 통합검사를 하며, 문제가 있으면 관련 단계로 돌아갑니다. | [읽는 사람 점검](references/essay-reader-rubric.md), [작성 흐름](references/essay-workflow.md) |

글은 이런 방향으로 씁니다.

- 첫 문장에서 문항의 답을 말하고, 경험형 답변에는 판단이 드러나는 문장을 하나 둡니다.
- "이 경험을 통해 ~ 배웠습니다", "~하는 개발자가 되겠습니다" 같은 어디에나 붙는 결말 대신, 이 경험에서 생긴 기준이나 지금의 습관으로 닫습니다.
- 결과를 이해할 최소 시험 조건과 문항이 요구한 한계는 본문에 남깁니다. 불필요한 상세 조건만 면접 대비 메모로 옮깁니다.
- 기업이 다른 형식을 요구하지 않으면 서술식 `습니다체`로 쓰고, 지원 화면이 허용하면 첫 줄에 `[핵심 요약]` 하나를 둡니다. 요약도 글자 수에 포함합니다.

자료가 부족한 문항은 경험을 지어내지 않고 보류합니다. 쓸 수 있는 문항은 `부분초안`으로 보존하고 필요한 사실을 확인한 뒤 다음 버전에 추가합니다. 새 버전에는 수정 목적, 관련 이슈, 판단과 구조의 변화, 남은 문제와 글자 수 영향을 남깁니다. `전체 자소서 문항`을 요청해도 기업 지원 페이지의 개인정보나 학력 항목까지 확장하지 않습니다.

자동 검사는 기록의 누락과 모순, 형식과 분량을 확인할 뿐 글의 설득력을 판정하지 않습니다. 스크립트를 실행할 수 없는 환경이면 같은 항목을 직접 대조하고 자동 검사 미실행을 구분해 보고합니다.

```text
$chwippohaja로 이 공고의 자소서 문항만 확인하고 초안을 준비해줘.
```

#### 내 문체 반영하기

워크스페이스의 `공통자료`에 두 파일을 두면 작성 단계에서 함께 읽습니다. 둘 다 선택 사항이며 공개 저장소에는 넣지 않습니다.

- `사용자_작성선호.md`: 여러 공고에 적용할 표기와 문체 선호. 예: 가운데점 금지, 소괄호 금지, 대괄호 요약은 명사형.
- `자소서_좋은예시.md`: 실제로 채택하거나 제출한 답변 중 문장이 좋았던 것과 그 이유. 사용자가 확인한 답변만 추가하며, 소재나 전략이 아니라 문체와 구조의 참고로만 씁니다.

### 지원서 전체

기업 공식 지원 페이지에서 전체 입력 항목과 첨부 조건을 확인하고, 자소서 작성본과 자소서를 제외한 지원서 작성본을 따로 만듭니다. 지원서 작성본은 공식 화면 순서에 맞춰 값을 채운 복사·붙여넣기용 Markdown으로 제공하며 사용자가 직접 입력하는 방식을 기본으로 합니다. 채워진 화면에서도 현재 값은 가져오지 않고 항목 구조만 수집하며, 민감정보 입력란은 실제 값 대신 `사용자 직접 입력`으로 남깁니다. 자소서만 모드의 상위 범위이며 로그인은 사용자가 직접 수행합니다.

지원서 항목을 수집한 뒤에는 공통자료의 확인된 학력, 교육, 경력, 자격, 어학과 수상을 새 회사의 `지원서_작성본.md`에 자동으로 매핑합니다. 자동완성한 값에는 출처를 남기고, 회사별 선택이 필요하거나 확인되지 않은 값은 `TBD`로 둡니다. 연락처, 상세 주소와 등록번호 같은 민감정보는 공통자료에 저장하지 않습니다.

작성본을 만들기 전에는 상위 항목뿐 아니라 학력과 경험 등의 행 추가 화면, 필수 하위 필드, 선택지, 날짜 제한과 점수 단위를 먼저 확인합니다. 학점과 기준 평점처럼 화면에서 나뉘는 값은 붙여넣기 값도 각각 분리합니다.

공식 폼 자동 입력은 선택 기능입니다. 직접 입력을 기본으로 하고, 사용자가 원하면 민감정보는 직접 입력하면서 비민감 확정값만 에이전트가 입력하는 혼합 방식도 사용할 수 있습니다. 자동 입력 중 충돌한 값은 덮어쓰지 않고 건너뛰며 안전하게 확인 가능한 문제를 모아 한 번에 보고합니다. 값 입력, 임시저장과 최종제출은 각각 별도 단계입니다.

```text
$chwippohaja로 공식 지원 페이지의 전체 항목을 읽고 지원서 전체 초안을 준비해줘.

$chwippohaja로 채택한 지원서 작성본과 자소서 작성본을 공식 지원 페이지에 입력해줘. 임시저장과 최종제출은 하지 마.
```

## 실행 환경

Python 3.11 이상을 사용합니다. 도구는 Python 표준 라이브러리로 동작합니다.

- 온보딩에서 생성하거나 가져온 워크스페이스
- 개인 사실을 저장한 공통자료
- `.chwippohaja/workspace.json`의 정보 설정 상태
- 회사별 작업 폴더
- Notion 연결 기능
- Google Drive 연결 기능
- 선택 사항: `humanize-korean`
- 선택 사항: `공통자료/사용자_작성선호.md`, `공통자료/자소서_좋은예시.md`

워크스페이스의 `AGENTS.md`·`CLAUDE.md`와 별도 운영 문서는 선택 사항입니다. 이 파일들과 사용자 고유 설정은 존중하고 기존 파일은 보존하지만, 일반 작성법의 복사본을 추가 규칙으로 자동 적용하지 않습니다. 적용 범위는 [워크스페이스와 상태](references/workspace-and-state.md)를 따릅니다. 빈 양식은 스킬 내부에 두며 온보딩에서 별도 작성 기준이나 양식 폴더를 만들지 않습니다.

Notion과 Google Drive 연결이 없어도 설정한 로컬 워크스페이스에서 공고 조사, 자소서와 지원서 작성, 검토와 제출 자료 보관까지 같은 방식으로 수행할 수 있습니다. 외부 연결이 필요한 Notion 갱신과 Drive URL 생성만 미반영으로 남깁니다. 설정 경로가 사라지면 다른 폴더로 자동 전환하지 않으며, Git 저장소를 선택해도 커밋과 푸시는 별도 요청이 있을 때만 수행합니다.

Notion 사용을 선택했는데 기존 지원 관리 데이터베이스가 없으면 사용자가 선택한 페이지에 새 데이터베이스를 만드는 계획을 먼저 보여줍니다. Notion 사용을 유지하려면 데이터베이스가 필요하며, 사용자가 승인한 경우에만 생성하고 실제 읽기와 쓰기 권한을 확인한 뒤 연결 상태를 갱신합니다. 서류 마감 또는 다음 일정 기준 달력 보기는 같은 데이터베이스에 추가하는 선택 사항입니다. 후속 전형은 공고 하나의 현재 상태·다음 일정과 본문 이력으로 관리하며, 사용자가 Notion에서 직접 갱신한 내용도 보존합니다.

지원서 전체 모드에서도 산출물을 하나로 합치지 않습니다. `자소서 작성본`에는 문항과 답변을, `지원서 작성본`에는 자소서를 제외한 기본정보, 학력, 경험, 자격과 첨부 정보를 저장합니다. 두 파일은 각각 버전 관리하며 동기화된 실제 Drive URL을 Notion의 대응 링크에 연결합니다.

제출이 확인되면 공식 지원 페이지의 다운로드, 인쇄와 접수증 기능을 순서대로 확인해 실제 제출 지원서 PDF를 우선 확보합니다. 운영체제의 PDF 저장 대화상자를 제어할 수 없으면 정확한 경로와 이름을 안내해 사용자가 한 번 저장하고, 에이전트는 생성 파일 탐색, 이름 정리, PDF 전용 페이지 검증, Drive 링크와 Notion 반영을 이어서 수행합니다. 사이트가 지원서 본문을 제공하지 않으면 접수증이나 완료 화면을 별도 증빙으로 보관합니다.

## 현재 버전과 실행 상태

사용자가 채택한 자소서와 지원서, 최신 공고 분석 및 리서치는 지원 건의 현재 기준 파일로 기록합니다. 파일 번호가 높다는 이유로 자동 채택하지 않습니다. 기준 파일을 바꾸거나 내용을 수정하면 해당 검증과 외부 반영을 다시 확인하며 실제 제출 이력은 별도로 유지합니다.

<details>
<summary>기준 파일과 검사 도구 자세히</summary>

- `application_state.py select`: 현재 분석 또는 사용자 채택본과 선택 근거 기록
- `application_state.py status`: 자료 준비, 작성 검증, 외부 반영과 제출 상태 조회
- `application_state.py sync`: 실제 외부 재조회 후 현재 파일의 반영 결과 기록
- `essay_check.py`: 설계와 작성본의 체크포인트, 형식과 분량을 한 번에 검사

검사 도구는 실행 상태 파일을 만들지 않습니다. 여러 회사의 자소서를 서로 다른 작업에서 동시에 진행해도 서로의 검사에 영향을 주지 않습니다.

새 설계와 주요 수정본은 체크포인트 버전 2의 작성 설명과 독해 검토, 문항 ID가 붙은 답변 블록과 하위 질문별 근거 연결을 사용합니다. 기존 ID 없는 답변과 체크포인트는 호환 모드로 읽습니다. 기존 작업본을 일괄 덮어쓰지 않습니다. 새 문서를 만들 때는 스킬의 assets/templates에서 필요한 양식을 참고하고 작성된 결과만 기업별 폴더에 저장합니다.

상세한 명령과 호환 기준은 [워크스페이스와 상태](references/workspace-and-state.md), [문항별 규칙](references/essay-rules.md)에 있습니다.

</details>

<details>
<summary>이전 버전에서 업데이트할 때 (훅 제거 안내)</summary>

Codex 프로젝트 훅(`essay_hook.py`, `research_hook.py`)은 삭제됐습니다. 워크스페이스 하나에 실행 상태 파일 하나를 공유하는 구조라 여러 지원 건을 동시에 작업할 수 없었기 때문입니다. 같은 검사는 이제 `essay_check.py`와 `validate_research_stage.py`를 직접 실행해 수행합니다.

- 업데이트 전에 취업 워크스페이스의 `.codex/hooks.json`을 백업하고, 그 안에서 `chwippohaja-essay-hook`과 `chwippohaja-research-hook` 항목만 지웁니다. 다른 스킬의 훅과 설정은 보존합니다. 남겨 두면 삭제된 스크립트를 호출해 오류가 납니다.
- `.chwippohaja/runs/`의 `essay-current.json`, `research-current.json` 등 이전 실행 상태 파일은 더 이상 읽지 않습니다. 보관이 필요 없으면 지워도 됩니다.
- 글자 수 제한은 훅에 등록하던 `--limit` 대신 `01_공고_JD/자소서_규칙.json`의 `min`, `max`에 둘 수 있습니다. `--limit`도 계속 지원합니다.
- 기존 작성 설계와 작성본은 그대로 검사됩니다. 새 설계·작성본 양식에는 `reader_rubric_required`, 작성본에는 `memorable_line`이 추가됐습니다.

</details>

## 개인정보

이 저장소에는 다음 값을 커밋하지 않습니다.

- 토큰, 쿠키와 OAuth 인증 파일
- 실제 Notion 페이지와 데이터베이스 ID
- 실제 Drive 파일과 폴더 ID
- 계정 이메일과 로컬 절대 경로
- 이력서, 자소서, 성적표와 증빙서류

로컬 전용 설정과 임시 윤문 결과는 `.gitignore`로 제외합니다. 보존할 검토 결과는 워크스페이스 최상단이 아니라 해당 기업의 선택형 `03_검토기록`에 둡니다.

<details>
<summary>검사 도구와 테스트</summary>

모든 도구는 Python 표준 라이브러리만 사용하며 실행 상태 파일을 만들지 않습니다.

- `essay_check.py`: 작성 설계와 작성본의 체크포인트, 문항 ID 대응, 근거 인용, 기억에 남는 문장, 형식과 분량을 한 번에 검사합니다.
- `validate_essay_style.py`: 가운데점, 곡선 따옴표, 영어 표현, 연결어미 뒤 쉼표, 대괄호 요약, 개조식 행을 찾습니다. 상투 표현과 같은 종결이 네 번 이상 이어지는 문장도 후보로 알려 줍니다. 엄격 모드에서는 요약과 본문 구조 오류만 실패로 처리합니다.
- `validate_research_stage.py`: 기업별 공고 분석과 리서치의 필수 산출물, 출처와 최소 내용을 확인합니다. 여러 대상을 넘기면 대상별 결과와 전체 집계를 함께 반환합니다. 출처의 사실성과 열린 검색 범위의 완전성은 대신 판단하지 않습니다.

문항과 소재의 적합성, 경험에서 도출된 이해의 타당성은 설계와 검토 단계의 의미 검토에서 확인합니다. 변경 후 macOS와 Windows에서 같은 테스트를 실행합니다.

```bash
python -m unittest discover -s tests -v
```

실제 공고 조사가 끝난 지원 건에서 자소서 작성부터 검증하는 절차는 [자소서 실사용 테스트 시나리오](tests/manual/essay-drafting.md)를 따릅니다. 시나리오와 실제 실행 결과를 구분하고, 개인 자료와 대상별 결과는 공개 저장소에 보관하지 않습니다.

</details>
