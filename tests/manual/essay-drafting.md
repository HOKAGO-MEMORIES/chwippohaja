# 공고 조사 완료 후 자소서 작성 실사용 테스트

## 목적과 현재 상태

이미 공고, JD와 기업 조사가 끝난 지원 건에서 자소서 작성부터 시작해 유효한 작성본을 완성하고 사용자가 채택한 버전까지 추적한다. 자동 테스트 통과와 실제 사용 검증을 구분한다.

이 문서는 실행 계획이다. 각 항목의 초기 상태는 **미실행**이며 실제 파일과 도구 결과를 확인한 뒤에만 통과로 바꾼다.

대상 회사, 개인 경험, 계정 정보와 실제 작업 로그는 공개 저장소에 추가하지 않는다. 대상별 실행 기록은 해당 지원 건의 `03_검토기록`에 보관한다.

## 시작 조건과 범위

실행 전 다음을 대상별 기록에 채운다.

- 테스트 날짜와 시간대, 스킬 커밋 해시
- 사용자에게 확인된 회사, 직무와 기존 지원 건 폴더
- 사용자가 알려준 마감 시각과 저장된 공고의 시각 및 출처 차이
- 기존 문항 파일, JD·기업 리서치와 확인된 개인 사실 원본
- 전체 문항 수, 문항 ID, 문항별 제한과 형식 요구
- 기존 채택본과 작성 번호
- 사용한 에이전트(Codex, Claude Code)와 하위 에이전트 사용 가능 여부
- 이번 실행에 Drive 링크 확인 및 Notion 작성본 연결이 포함되는지

공고 조사와 기업 리서치를 처음부터 재실행하지 않는다. 저장된 문항과 조건을 읽고 대상 직무에 맞는지 대조한다. 문항이 미확인 상태이거나 원문과 충돌하면 그 부분만 확인한다. 오늘 마감 여부나 정확한 시간을 추정하지 않는다.

기존 워크스페이스를 재설정하거나 사용자 프로필을 다시 온보딩하지 않는다. 공통자료의 부족한 사실만 확인한다. 자소서 외 지원서 전체 입력, 자동 저장, 첨부 업로드와 최종 제출은 이 테스트의 기본 범위에 포함하지 않는다.

## 당일 진행 순서

실제 지원용 결과물 확보를 먼저 진행한다. 분량과 사실 검증을 생략하지 않되, 마감 전에 사용자가 화면 입력과 제출 점검을 할 시간을 확보한다. 보통 마감 60분 전부터는 선택적인 문체 실험과 의도적인 오류 주입을 중단한다. 남은 시간이 더 짧으면 추가 실험 없이 실제 작성과 필수 검증에 집중한다.

### S1. 기존 상태에서 재개

**작업**

1. 워크스페이스와 지원 건의 실제 경로를 발견한다. 표시 이름만으로 경로를 다시 구성하지 않는다.
2. `application_state.py status`를 확인한다. 현재 기준 파일이 없으면 문서와 사용자 채택 이력에서 판단한다.
3. 다른 지원 건을 동시에 작업 중이면 그 지원 건의 파일을 건드리지 않는다.
4. 기존 공고와 개인 사실 원본 및 기존 작성본의 파일 목록과 해시를 기록한다.

**통과 기준**: 기존 조사를 재작성하지 않고 올바른 지원 건과 채택본을 찾았다. 사용자 자료와 다른 지원 건의 파일을 덮어쓰지 않았다.

### S2. 문항 목록과 작성 설계

**작업**

1. 실제 문항 원문과 모든 필수 하위 질문을 분해하고 각 문항에 ID를 붙인다.
2. 확인된 사실에서 소재를 선택하고 버전 2의 `writing_brief`, `material_fit_reason`, `detail_selection`과 하위 질문별 `evidence_map`을 작성한다. 출처는 실제로 읽은 사실 ID 또는 파일과 섹션이다.
3. 기업별 형식 예외와 계산 규칙이 있으면 출처와 함께 규칙 JSON을 만든다. 예외가 없는 문항은 기본값을 사용한다.
4. `next-draft`로 설계 파일 번호를 정해 저장하고 `essay_check.py --plan`으로 전체 문항을 검사한다.
5. 문항에 필요한 판단·의미의 근거가 원본에 없으면 인터뷰에서 묶어서 묻는다. 이후 변화는 문항이나 핵심 주장에 필요한 경우만 확인한다. 답변 후 설계를 갱신하고 다시 검사한다.
6. 초안 전 검증이 통과한 뒤 작성 패스(가능하면 하위 에이전트)에서 답변을 작성한다.

**통과 기준**: 문항 원문·검사 대상 문항·설계의 ID가 일치한다. 인터뷰 질문은 원본에 없는 판단 이유만 물었다. 각 필수 하위 질문에 적합한 사실 근거가 연결됐다. 근거가 부족한 문항은 보류되며 경험을 새로 만들지 않았다.

### S3. 실제 자소서 작성과 검토

**작업**

1. 답변마다 `text question=문항ID` 블록을 사용하고 문항 요구에 직접 답한다.
2. 실제 답변 구절과 설계의 출처를 `answer_evidence`로 연결한다.
3. 문항과 본문만으로 직접 답변·상황·본인 행동·결과를 reader_review에 재구성하고 독해 이슈를 고친다. 이어 원본과 사실, 수치, 역할, 소재 적합성과 인과관계를 대조한다.
4. 읽는 사람 점검을 적용하고 `memorable_line`을 본문에서 옮겨 적는다. 최소 조건과 문항이 요구한 한계를 본문에 남기고 불필요한 상세만 메모로 옮긴다.
5. `essay_check.py --plan 설계.md --draft 작성본.md --body-only`에 규칙 또는 분량 제한을 전달해 본문을 사전 검사한다. 표현 후보는 실제 문맥에서 검토한다.
6. 발견한 이슈와 실제 검사 결과를 체크포인트에 기록하고 `--body-only` 없이 같은 파일·규칙으로 최종 검사한다. 내용 미검토 상태를 자동 통과시키지 않는다.

**통과 기준**: 실제 문항을 모두 추적하며 각 유효 답변이 필수 질문에 답한다. 확인되지 않은 개인 사실과 미해결 치명 이슈가 없다. 요약을 포함한 실제 본문이 기업의 형식·분량 조건을 충족한다.

### S4. 정보 부족과 추가 답변 처리

이 상황이 자연스럽게 발생한 경우에만 실제 지원 건에서 진행한다. 모든 문항의 근거가 충분하면 `해당 없음`으로 기록하고 별도 복사본 시험으로 다룬다.

**작업**

1. 답할 수 있는 문항은 유효한 부분초안으로 보존한다.
2. 보류 문항에는 답변을 만들지 않고 필요한 사실과 구체적인 확인 질문을 묶어 남긴다.
3. 사용자 답변을 받으면 다음 번호의 설계와 작성본으로 전체 문항을 다시 검사한다.

**통과 기준**: 부분초안을 전체 완료라고 보고하지 않았다. 사용자 응답 전 경험을 추정하지 않았다. 기존 유효 답변은 필요한 범위만 수정했고 이전 파일은 보존했다.

### S5. 채택과 수정 이력

**작업**

1. 사용자가 검토할 본문과 문항별 분량, 해결한 이슈와 남은 확인 사항을 제시한다. 작성 작업 전체가 완료됐다고 보고하지 않는다.
2. 사용자 피드백이 있으면 필요한 부분을 수정하고 다음 버전을 검증한다.
3. 사용자가 명시적으로 채택한 파일을 `application_state.py select --kind essay`로 기록한다.
4. 채택본 중 문장이 좋은 답변은 사용자 확인 후 `공통자료/자소서_좋은예시.md`에 추가한다.

**통과 기준**: 가장 큰 번호를 자동 채택하지 않았다. 채택본·검증 결과·본문 해시가 대응한다. 검토 종료 후 취향만을 이유로 다시 쓰지 않았다. 자소서 작성 완료를 실제 지원 완료로 바꾸지 않았다.

### S6. Drive와 Notion 반영

이번 실행에 외부 반영이 포함된 경우에 수행한다. 연결을 사용하지 않는 실행에는 `해당 없음`, 요청됐으나 실패하면 `실패` 또는 `보류`로 기록한다.

**작업**

1. 로컬 채택본의 동기화된 파일을 실제 메타데이터로 찾아 파일명, 부모 폴더와 가능한 크기 등을 대조한다.
2. 선택한 Notion 지원 건의 자소서 작성본 링크만 올바르게 갱신하고 페이지를 다시 조회한다.
3. 외부 재조회 결과를 `application_state.py sync --scope application`에 근거와 함께 기록한다.
4. 실패하면 로컬 작성 상태를 보존하고 미반영 사유와 남은 작업을 기록한다.

**통과 기준**: 실제 조회한 URL만 연결했고 다른 지원 건이나 다른 종류의 작성본 링크를 덮어쓰지 않았다. 외부 반영 실패를 전체 완료로 보고하지 않았다. 이번 범위에서 제출 상태는 변경하지 않았다.

### S7. 병렬 작업 확인

**작업**

- 다른 지원 건의 자소서를 별도 작업에서 동시에 진행한다.
- 각 작업의 `essay_check.py`가 자기 지원 건의 파일만 읽는지, 워크스페이스에 공유 상태 파일이 생기지 않는지 확인한다.

**통과 기준**: 한 작업의 검사 실패나 수정이 다른 작업의 검사 결과와 파일을 바꾸지 않았다.

## 의도적인 실패 검증: 임시 복사본에서만 실행

실제 지원용 결과물 확보 뒤 시간이 남으면 아래를 확인한다. 기업과 개인의 실제 내용이 필요 없는 검사는 가상 자료를 쓴다. 실제 워크스페이스에 문항 누락이나 손상된 상태를 주입하지 않는다.

| ID | 입력 또는 행동 | 기대 결과 |
| --- | --- | --- |
| N1 | 등록한 문항 중 하나를 설계·검토에서 제거 | 검사 실패, 누락을 복구하면 통과 |
| N2 | 태그 중복 또는 보류 문항의 답변 블록 추가 | 검사 실패 |
| N3 | 소제목 금지 또는 목록 요구 규칙 적용 | 맞는 답변은 통과, 위반 답변은 실패 |
| N4 | 문자 수·UTF-8 바이트·공백·줄바꿈 조건 변경 | 등록한 기준으로 계산, 상한 초과는 실패 |
| N5 | A와 B 지원 건을 서로 다른 작업에서 동시에 검사 | 각자의 파일만 검사, 한쪽 실패가 다른 쪽에 영향 없음 |
| N6 | 규칙 파일의 `max`를 본문보다 작게 변경 | 검사 실패, 되돌리면 통과 |
| N7 | 최신 번호보다 낮은 작성본 채택 | 지정한 이전 버전이 현재 기준 파일로 표시 |
| N8 | 선택한 파일의 내용을 변경 | 재검토 필요 또는 검사 실패, 재선택 후 재검증 |
| N9 | 과거 미완료 조사와 현재 정상 분석을 함께 보존 | 현재 파일을 명시하면 과거 자료 때문에 차단하지 않음 |
| N10 | 외부 반영을 pending으로 기록한 뒤 복구 | 로컬 결과 보존, 실제 재확인 후 외부 완료 |

N1~N10의 자동 회귀 테스트가 통과했다는 사실은 실제 에이전트 실행이나 외부 서비스 테스트의 대체 증거가 아니다. 실행하지 않은 수동 항목은 미실행으로 유지한다.

## 결과 기록 형식

대상별 `03_검토기록/날짜_자소서_실사용테스트.md`에 다음을 기록한다.

```text
스킬 커밋:
회사와 직무:
시작·종료 시각과 시간대:
문항 수 / 유효 답변 수 / 보류 수:
사용한 사실 원본과 설계:
사용자가 채택한 작성본:
문항별 계산 규칙과 실제 분량:
직접 실행한 검사 결과:
PostToolUse / Stop의 실제 호출 근거:
Drive / Notion 반영과 재조회 결과:
원본 및 이전 버전 보존 여부:
S1~S7 상태: 통과 / 실패 / 보류 / 미실행 / 해당 없음
N1~N10 상태: 통과 / 실패 / 미실행
발견한 문제와 재현 조건:
실제 지원을 위해 남은 작업:
```

문제는 입력 조건, 기대 결과, 실제 결과, 관련 파일·명령, 실제 지원에 미치는 영향과 사용한 임시 대응으로 기록한다. 오류가 반복되면 실제 작성 작업과 도구 수정 시험을 분리하고 채택본을 보존한다. 검사기를 고칠 때는 재현 테스트를 추가하고 통과한 버전을 다시 명시한다.

## 실사용 시작 요청 예시

> $chwippohaja로 [회사·직무]의 기존 자료를 사용해 자소서 작성부터 진행해줘. 공고와 기업 조사는 완료했으니 재실행하지 말고 저장된 문항, JD와 확인된 경험을 사용해줘. 전체 문항을 추적하고 근거가 부족한 문항만 질문해줘. 실제 지원용 작성본을 우선 완성하면서 문항 검증, 형식·분량, 검사 실행과 버전 보존 결과를 03_검토기록에 기록해줘. 의도적인 실패 시험은 임시 복사본에서만 해줘. 자소서 외 지원서 입력이나 최종 제출은 별도로 요청할게.

## 새 대화와 환경별 내용 품질

[별도 품질 시나리오](essay-quality.md)의 가상 자료로 반복 평가한다. 실제 지원 마감과 분리해서 수행하며 체크포인트 자동 검사 통과로 내용 평가를 대체하지 않는다.
